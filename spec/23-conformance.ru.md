# 23. Соответствие и тестирование самой среды

Ожидается, что большую часть компилятора напишет ИИ. Поэтому проверки самого `anlang` так же механичны и решающи, как проверки пользовательского кода. Этот файл задаёт наборы тестов, которые реализация `anlang` ДОЛЖНА поддерживать и проходить.

## 23.1 Набор соответствия

**conf.suite.per-rule** — Для каждого нормативного требования к программе в этой спецификации набор соответствия ДОЛЖЕН содержать хотя бы одну программу, которая нарушает правило и должна отвергаться с диагностикой, называющей идентификатор этого правила. Если правило что-то разрешает, набор ДОЛЖЕН также содержать хотя бы одну программу, которая должна компилироваться.

**conf.suite.naming** — Каждый тест соответствия ДОЛЖЕН называться по идентификатору проверяемого правила. Тест, проверяющий несколько правил, ДОЛЖЕН перечислять их все.

**conf.suite.expectation** — Отрицательный тест проходит, только если компиляция завершается неуспехом и множество идентификаторов правил в диагностиках-ошибках совпадает с ожидаемым. Положительный тест проходит, только если компиляция завершается без ошибок.

**conf.suite.shared** — Один и тот же набор соответствия ДОЛЖЕН проходить и компилятор на Go, и компилятор на Anlang.

**conf.suite.implementation-rules** — Для каждого нормативного требования к реализации (правил, ограничивающих инструментарий) в наборе СЛЕДУЕТ иметь автоматическую проверку, если требование не проверяется другим видом тестов из этого файла.

**conf.suite.layout** — Набор хранится в каталоге `conformance/testdata/` исходников инструментария в следующем виде, чтобы оба компилятора из **conf.suite.shared** читали одни и те же файлы:

1. Каждый подкаталог `testdata/` назван идентификатором правила и содержит тесты, отнесённые к этому правилу.
2. Файл `<name>.an` в каталоге правила — однофайловый тест: исходный файл пакета `main` проекта с именем модуля `conf`, собираемый для цели `linux-x86_64`.
3. Подкаталог `<name>/` каталога правила — тест-проект: корень проекта со своим `anlang.mod` и исходными файлами, собираемый для первой цели из `anlang.mod`.
4. Ожидание записывается ровно один раз среди файлов теста строчным комментарием `// want: ok` для положительного теста или `// want: <rule> {<rule>}` для отрицательного, перечисляющим ожидаемое множество идентификаторов правил из **conf.suite.expectation**.
5. Комментарий `// checks: <rule> {<rule>}` перечисляет другие правила, которые проверяет тест (**conf.suite.naming**). Отрицательный тест ДОЛЖЕН называть правило своего каталога в `want` или `checks`.
6. Диагностика без идентификатора правила никогда не совпадает с ожиданием, поэтому отрицательный тест проходит, только если каждая ошибка называет правило.
7. Файлы тестов ДОЛЖНЫ быть в канонической форме (**lex.source.canonical**), если только они не проверяют это правило.
8. В положительном тесте комментарий `// effects: <function> <effect> {<effect>}` задаёт собственные эффекты (**eff.attr.own**) функции пакета `main`, записанной как `F` или `T.M`, голыми именами в любом порядке; `none` задаёт пустое множество. Комментарий `// exec: <function> <effect> {<effect>}` так же задаёт её эффекты исполнения (**eff.attr.exec**).
9. Файл `<name>.out` рядом с положительным тестом `<name>.an` или `<name>/` делает тест эталонной программой (**conf.reference**). Файл содержит ожидаемое наблюдаемое поведение: всё, что программа пишет в стандартный вывод и стандартный поток ошибок, в порядке записи, а затем строку `exit status N`, если код возврата `N` не равен 0.
10. Рядом с эталонной программой для цели с текстовым экраном файл `<name>.screen` содержит ожидаемый экран после выполнения в формате `anlang run -screen` (**tool.emu.dos**), а файл `<name>.in` — ввод с клавиатуры эмулятора.

```go
// want: decl.func.no-init

package main

func init() {}

func main() {}
```

## 23.2 Эталонные программы

**conf.reference** — Для каждой поддерживаемой цели набор ДОЛЖЕН содержать эталонные программы с ожидаемым наблюдаемым поведением (вывод, изменения пинов с таймингом, вывод UART, содержимое экрана, код возврата). Каждая ДОЛЖНА показывать это поведение во встроенном эмуляторе цели (см. [20-toolchain](20-toolchain.ru.md), 20.10).

Эталонные программы, не зависящие от цели, хранятся как описано в **conf.suite.layout**, пункт 9; те, что не проверяют какое-то определённое правило, лежат в каталоге `conf.reference`. Они выполняются в интерпретаторе IR (**tool.emu.ir**) и, для каждой цели с бэкендом, в эмуляторе цели.

## 23.3 Перекрёстная проверка бэкендов

**conf.backend.ir** — Для каждой эталонной программы и цели результат бэкенда, исполненный в интерпретаторе архитектуры, ДОЛЖЕН давать то же наблюдаемое поведение, что и интерпретация IR программы.

**conf.backend.arch** — Эталонная программа, использующая операторы `asm` или пакеты команд, выполняется только в эмуляторе своей цели, который ДОЛЖЕН давать поведение из её файлов `.out` и `.screen`.

**conf.backend.select** — Эталонная программа выполняется на цели, если цель её принимает: её профиль допустим для платформы (**target.platform.profile**), а её эффекты предоставляет цель (**target.effects.provides**). Набор ДОЛЖЕН содержать эталонные программы в профиле `core`, чтобы на каждой цели с бэкендом выполнялись какие-то из них.

## 23.4 Сравнение с Go

**conf.go.common-subset** — Программы на общем подмножестве Anlang и Go (без `enum`, `inout`, контрактов и других конструкций из перечня новизны) ДОЛЖНЫ давать одинаковый вывод при компиляции Go и Anlang, если только их поведение не зависит от семантического отличия Anlang, которое Go молча принимает: семантики значений срезов и словарей (**mem.value.copy**), захвата копией в замыканиях (**expr.closure.capture-copy**), равенства пустого среза `nil` (**expr.cmp.nil-empty**), проверяемой целочисленной арифметики (**expr.int.checked**). Сравнение выполняет тестовые программы дистрибутива Go в интерпретаторе IR; каждая программа, исключённая из-за отличия, указывается вместе с правилом, которое объясняет разницу.

## 23.5 Фаззинг

**conf.fuzz** — Парсер, проверка типов, решатель и компоновщик ДОЛЖНЫ подвергаться фаззингу. Ни на каком входе `anlang` НЕ ДОЛЖЕН падать, зависать сверх настроенных пределов или выдавать внутреннюю ошибку; он ДОЛЖЕН либо завершаться успешно, либо сообщать диагностики.

**conf.fuzz.allocator** — Аллокатор `app` ДОЛЖЕН подвергаться фаззингу, а режим проверки памяти в тестах НЕ ДОЛЖЕН находить ошибок.

## 23.6 Проверка решателя

**conf.solver.certificate** — Каждый результат решателя «доказано» ДОЛЖЕН сопровождаться сертификатом, и небольшой независимый проверщик ДОЛЖЕН его подтверждать (см. [08-contracts](08-contracts.ru.md)). Доказательство, сертификат которого отвергнут, ДОЛЖНО считаться недоказанным, а сам случай ДОЛЖЕН сообщаться как внутренняя ошибка.

**conf.solver.exhaustive** — На малых конечных доменах результаты решателя ДОЛЖНЫ совпадать с полным перебором.

## 23.7 Самосборка

**conf.self-hosting** — Пусть *B1* — исполняемый файл, который версия компилятора на Go получает из исходников компилятора на Anlang, а *B2* — исполняемый файл, который *B1* получает из тех же исходников для той же цели. *B1* и *B2* ДОЛЖНЫ быть побайтово одинаковы (см. [22-compiler](22-compiler.ru.md), 22.9).

## 23.8 Внешние оракулы

**conf.oracle.use** — Там, где есть независимая реализация, её СЛЕДУЕТ использовать как оракул:

- интерпретаторы архитектур — против QEMU и наборов тестов процессоров;
- интерпретатор WebAssembly — против официального набора тестов спецификации WebAssembly;
- проверка типов — против go/types из дистрибутива Go на его тестовых программах, переименованных в Anlang, для общего подмножества (**conf.go.common-subset**);
- целочисленная арифметика, преобразования и проверки границ интерпретатора IR — против Go, на граничных и случайных операндах каждого целого типа: целые типы Go для циклических типов и `bits.Wrapping*`, точная арифметика для переполнения и остальных функций `an/bits`, срезы, массивы и строки Go для границ и сообщений о панике (**expr.int.checked**, **expr.wrap.ops**, **expr.bits.functions**, **expr.bounds.check**);
- интерпретатор IR — против ожидаемого вывода исполняемых («run») тестовых программ дистрибутива Go, переименованных в Anlang, для общего подмножества (**conf.go.common-subset**);
- вывод компоновщика — против стандартных утилит разбора форматов;
- шейпинг текста — против эталонного набора тестов шейпинга;
- вывод для GPU — против валидаторов форматов.

**conf.oracle.scope** — Внешние инструменты МОГУТ использоваться только в тестах самой среды. Они НЕ ДОЛЖНЫ входить в инструментарий и требоваться какой-либо командой `anlang` (см. [22-compiler](22-compiler.ru.md), **impl.single-binary**).

## 23.9 Производительность

**conf.perf** — Время компиляции, размер бинарников и скорость кода ДОЛЖНЫ измеряться по целям на фиксированном наборе тестов производительности. Регрессия сверх настроенного порога ДОЛЖНА блокировать слияние изменения.

## 23.10 Политика регрессий

**conf.regression** — Каждый тест из этого файла, будучи добавлен, ДОЛЖЕН оставаться в наборе. Изменение, из-за которого падает любой ранее проходивший тест, НЕ ДОЛЖНО сливаться.
