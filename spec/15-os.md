# 15. Operating Systems

This file specifies the facilities for writing operating system kernels in Kern: privilege, typed addresses, trap handlers, kernel threads and context switching, system call tables, multiprocessing primitives and boot targets.

Kernels are written in the `core` profile. The only new syntax is the `trap` declaration; its syntax is the production `HandlerDecl` in [03-declarations](03-declarations.md) §3.10. Rules for execution contexts, critical sections and stack analysis in [14-embedded](14-embedded.md) apply to kernels as well.

## 1. Privilege

**os.priv.effect** — An instruction that the formal instruction semantics of the architecture description ([13-targets](13-targets.md)) marks as privileged has effect `Privileged`. Examples are loading page tables, disabling interrupts and writing model-specific registers. A function of an architecture package (`kern/arch/...`) that executes such an instruction has effect `Privileged`, and the effect propagates as usual ([07-effects](07-effects.md)).

**os.priv.deny** — `Privileged` is denied in every profile by default.

**os.priv.allow** — A package MAY have effect `Privileged` only if its profile is `core` and the project's `kern.mod` allows `Privileged` for that package path ([20-toolchain](20-toolchain.md)):

```
effects (
    myos/kernel/...  allow {Privileged}
)
```

**os.priv.user** — A platform that describes the user mode of an operating system MUST NOT list `Privileged` in its `Provides` ([13-targets](13-targets.md)). Programs built for that platform therefore cannot contain privileged instructions.

## 2. Typed addresses

**os.addr.types** — The package `kern/mm` declares two distinct defined types, `PhysAddr` (physical address) and `VirtAddr` (virtual address). Their underlying type is an unsigned integer type wide enough for the physical, respectively virtual, address space of the target.

**os.addr.no-cross** — A conversion between `PhysAddr` and `VirtAddr` in either direction is an error, even though the Go specification would permit a conversion between types with the same underlying type. Translation between the two address spaces is done only by functions that consult address translation structures.

**os.addr.from-int** — An explicit conversion from an integer type to `PhysAddr` or `VirtAddr` is permitted (for example, `VirtAddr(x86_64.ReadCR2())`). It follows the narrowing rules of [02-types](02-types.md).

## 3. Trap handlers

A `trap` handler handles a processor exception: page fault, division by zero, invalid instruction and so on.

**os.trap.name** — The name of a `trap` handler MUST be the name of an exception defined in the architecture description of the target. An exception MUST have at most one handler in a program.

**os.trap.signature** — The parameter list of a `trap` handler MUST match the signature that the architecture description defines for that exception. It MAY include `frame inout TrapFrame`, the saved processor state, and a typed exception code. A trap handler has no results.

**os.trap.frame** — Changes made to `frame` take effect when the handler returns: execution resumes in the state recorded in `frame`.

**os.trap.effects** — A `trap` handler has the same implicit constraint as an `interrupt` handler: `ensures effect.Without(Alloc, Block, Panic)` (see **emb.irq.effects** in [14-embedded](14-embedded.md)).

**os.trap.profile** — `trap` declarations are permitted only in packages whose profile is `core` alone and for which `Privileged` is allowed (**os.priv.allow**).

**os.trap.no-call** — A `trap` handler MUST NOT be called, referenced as a function value or passed as an argument.

**os.trap.context** — Each `trap` handler is a separate execution context for the analysis of [14-embedded](14-embedded.md) section 2.3.

**os.trap.nested** — If an exception occurs while its handler or another trap handler is running, the behavior is defined by the architecture description (for example, a double fault exception). If the program has no handler for the resulting exception, the target's `OnPanic` behavior applies.

## 4. Kernel threads and context switching

**os.thread.type** — The package `kern/sched` provides a kernel thread type. Creating a kernel thread requires an entry function and a stack size that is a compile-time constant.

**os.thread.stack** — The stack size of a kernel thread MUST NOT be less than the maximum stack depth of its entry function computed under **emb.stack.depth**. Otherwise the build fails.

**os.switch.primitive** — Each architecture package provides exactly one context switch primitive, implemented with `asm`. It saves the registers that the internal ABI requires to be preserved, switches the stack and restores the registers of the target thread. Kernel code MUST switch threads only through this primitive.

## 5. System call tables

A system call table describes the interface between a kernel and its programs as data. From one table the implementation generates the kernel's dispatch code and the program-side functions.

```go
package kernos

import "kern/abi"

const Syscalls = abi.Table{
    Convention: abi.ByArch{X86_64: "syscall", RISCV64: "ecall", I8086: "int 0x80"},
    Calls: []abi.Call{
        abi.Fn[func(fd Handle, buf []u8) (usize, error)]{No: 1, Name: "Write", Effects: Console},
        abi.Fn[func(fd Handle, buf inout []u8) (usize, error)]{No: 2, Name: "Read", Effects: Console},
        abi.Fn[func(path string, mode OpenMode) (Handle, error)]{No: 3, Name: "Open", Effects: File},
        abi.Fn[func(code i32)]{No: 4, Name: "Exit"},
    },
}
```

**os.sys.table** — A system call table is a package-level constant of type `abi.Table`. `Convention` maps each supported architecture to its system call instruction. `Calls` lists the calls; each element is `abi.Fn[F]` where `F` is a function type, with fields `No` (call number), `Name` (exported identifier) and `Effects` (effects of the call; empty if omitted).

**os.sys.unique** — Call numbers in a table MUST be unique, and call names MUST be unique.

**os.sys.types** — Parameter and result types of `F` MUST be integer types, `bool`, `string`, slices of integer types, `inout` parameters of these types, handle types defined in the table's package, and `error` as the last result. The encoding of each type in registers and memory is defined by the table's convention and the architecture description.

**os.sys.kernel** — The kernel package that implements a table MUST declare, for each call, a function with the call's name and type `F`. A missing or mismatched function is an error. The implementation generates the dispatch code that decodes the call number and arguments and calls that function.

**os.sys.user** — A program that imports the table's package gets, for each call, a function with the call's name and type `F` that performs the system call. Its effects are the declared `Effects`. As with external functions, the compiler cannot verify declared effects ([12-ffi](12-ffi.md)).

**os.sys.platform** — A platform description MAY refer to a system call table. A program built for that platform that calls a function whose effect is not in the platform's `Provides`, or is denied by `kern.mod`, is rejected.

## 6. Multiprocessing

**os.smp.atomic** — Atomic operations in `kern/atomic` MUST accept an explicit memory order: `Relaxed`, `Acquire`, `Release`, `AcqRel` or `SeqCst`. An operation without an explicit order uses `SeqCst`.

**os.smp.percpu** — The package `kern/kernel` provides a per-CPU data type. Access to the current CPU's instance is given through range-over-func with `inout` access ([05-statements](05-statements.md)); preemption on the current CPU is disabled for the duration of the body.

**os.smp.spin** — The package `kern/sync` provides a spinlock type for use between CPUs. Its `Lock()` returns an iterator that yields `inout` access once, disables interrupts on the current CPU for the duration of the body and spins until the lock is free. `Lock()` of a spinlock does not have effect `Block`.

**os.smp.races** — Value semantics and the synchronization rules of [06-memory](06-memory.md) and [09-concurrency](09-concurrency.md) apply between CPUs: a mutable value is never reachable from two CPUs at the same time except through synchronization types.

## 7. Boot targets

**os.boot.platforms** — The implementation MUST provide platform descriptions for the following boot environments:

| Platform | Architectures | Output |
| --- | --- | --- |
| BIOS boot sector | i8086, x86-64 (real mode at start) | 512-byte boot sector loaded at `0x7C00` |
| Multiboot | x86-64 | Kernel image with a Multiboot header |
| UEFI | x86-64, arm64, riscv64 | UEFI application |
| Device Tree | arm64, riscv32, riscv64 | Kernel image that receives a Device Tree blob |

**os.boot.entry** — Each boot platform package defines the entry point of the kernel and the information passed to it (for example the boot information structure or the Device Tree blob). The kernel's entry function MUST have the signature that the platform package defines.

## 8. A Kern operating system as a platform

**os.platform.new** — An operating system written in Kern becomes a platform by providing a platform description ([13-targets](13-targets.md)) that refers to its system call table. Programs for that platform use the table's package for system calls; the kernel and the programs share the same table package.

## 9. Kernel invariants in contracts (informative)

Contracts ([08-contracts](08-contracts.md)) can state invariants that conventional kernels keep by discipline:

```go
func (s inout AddressSpace) Map(v VirtAddr, p PhysAddr, f PageFlags) {
    requires v.IsPageAligned() && p.IsPageAligned()
    requires !(f.User && kernel.Owns(p))
    ensures  s.Translate(v) == Some(p)
    ...
}
```

This is not full formal verification at the level of seL4.

## 10. Effects as capabilities (informative)

Effects are a compile-time form of capabilities, the model used by seL4 and Zircon. A driver can use only the ports, memory regions and interrupts whose effects it is allowed. A microkernel repeats the same check at run time.

Kernels of different scales that the facilities above are meant to support:

| Kind | Target | Example |
| --- | --- | --- |
| DOS-like system | i8086, real mode | Single-tasking system with a FAT file system |
| RTOS | Cortex-M, RISC-V 32 | Priority scheduler at the level of FreeRTOS or Zephyr |
| Microkernel | x86-64, riscv64, arm64 | User-space drivers, capability-based IPC |
| Unikernel | x86-64 in a virtual machine | Application and minimal kernel in one image |

## Open issues

1. **Package of `PhysAddr` and `VirtAddr`.** `kern.md` lists `kernel`, `mm` and `sched` as standard building blocks but does not assign the types. Provisional: `kern/mm`.
2. **Width of address types.** Provisional: wide enough for the respective address space of the target; the exact type per target is given by the target description.
3. **Names and APIs of the kernel thread, per-CPU and spinlock types.** `kern.md` names only the concepts. Provisional: in `kern/sched`, `kern/kernel` and `kern/sync`; exact names to be fixed in [18-stdlib](18-stdlib.md).
4. **User memory passed to system calls.** `kern.md` does not say how the kernel validates slices passed by programs. Provisional: the generated dispatch code checks that every slice argument lies in the caller's address space and returns an error otherwise; whether kernel implementations receive such arguments as `Untrusted` ([11-data-safety](11-data-safety.md)) is open.
5. **Default memory order.** Provisional: `SeqCst` when no order is given (**os.smp.atomic**).
6. **Boot platform entry signatures.** Provisional: defined by each boot platform package (**os.boot.entry**).
