# 14. Встраиваемые системы

Этот файл описывает, как программы на Anlang для микроконтроллеров и других целей без ОС обращаются к железу: описания устройств, владение периферией, обработчики прерываний, анализ стека, статические задачи и наихудшее время выполнения (WCET).

Прошивки пишутся в профиле `core`. Нового синтаксиса здесь нет, кроме объявления `interrupt`; его синтаксис — продукция `HandlerDecl` в [03-declarations](03-declarations.ru.md) §3.10.

## 1. Описания устройств

*Описание устройства* описывает периферию, регистры и векторы прерываний конкретного чипа. Оно входит в описание цели ([13-targets](13-targets.ru.md)) через поле `Device` структуры `target.Desc`.

**emb.device.source** — Описание устройства ДОЛЖНО строиться при компиляции. Стандартный источник — SVD-файл производителя, загружаемый через `svd.Load(path)`; `svd.Load` выполняется по правилам вычислений при компиляции и генераторов ([10-compile-time](10-compile-time.ru.md)).

**emb.device.package** — Для цели, в описании которой есть `Device`, реализация ДОЛЖНА предоставлять пакет `an/device`, сгенерированный из этого описания. Содержимое `an/device` зависит от выбранной цели. Импорт `an/device` при цели без `Device` — ошибка.

**emb.device.granularity** — Описание устройства задаёт *единицы владения*: каждый экземпляр периферии (например, `TIM2`, `USART1`) — единица. Там, где железо позволяет менять части периферии независимо, без чтения-изменения-записи (например, пины GPIO с регистрами атомарной установки и сброса), описание МОЖЕТ объявить каждую часть (каждый пин) отдельной единицей.

### 1.1 Регистры

**emb.reg.types** — Для каждого регистра и битового поля из описания устройства сгенерированный пакет ДОЛЖЕН объявить отдельный тип. Поле, для которого описание перечисляет допустимые значения, ДОЛЖНО иметь тип, значения которого — ровно эти значения.

**emb.reg.values** — Запись в поле недопустимого значения — ошибка компиляции. Неконстантное значение более широкого типа ДОЛЖНО преобразовываться по правилам сужения из [02-types](02-types.ru.md): преобразование компилируется, только если диапазон доказан, иначе оно даёт пару «значение, ok».

**emb.reg.volatile** — Каждое чтение и каждая запись регистра устройства — *volatile-доступ*: реализация НЕ ДОЛЖНА удалять, дублировать, объединять или переставлять volatile-доступы относительно других volatile-доступов того же контекста исполнения.

**emb.reg.unsafe** — Отображение регистров ДОЛЖНО генерироваться через `unsafe.Map` внутри `an/device` ([06-memory](06-memory.ru.md)). Коду программы, который обращается к периферии через `an/device`, НЕ ДОЛЖЕН требоваться импорт `unsafe`.

### 1.2 Области памяти и константы

**emb.mem.regions** — Области памяти цели (`target.Desc.Memory`, см. [13-targets](13-targets.ru.md)) — единственная память, которую может занимать программа. Если код, константы, статические данные, стеки задач или основной стек не помещаются в свои области, сборка ДОЛЖНА завершиться ошибкой, а диагностика ДОЛЖНА показать размер содержимого каждой области с разбивкой по пакетам.

**emb.mem.const** — Константа уровня пакета, значение которой вычислено при компиляции (таблицы, таблицы CRC, делители тактовой частоты), ДОЛЖНА размещаться в области только для чтения (flash), если она есть у цели, и НЕ ДОЛЖНА копироваться в RAM.

## 2. Владение периферией

### 2.1 Периферия как значения

**emb.periph.global** — Каждая единица владения доступна как значение уровня пакета `an/device`: `device.TIM2`, `device.USART1`, `device.GPIOC.Pin13`. Эти значения — отображения железа и допустимы как переменные уровня пакета в профиле `core` ([06-memory](06-memory.ru.md)).

**emb.periph.identity** — У каждой единицы владения свой тип нулевого размера. Значение, полученное из единицы (например, `led := device.GPIOC.Pin13.Output(gpio.PushPull)`), имеет тип, который статически фиксирует эту единицу. Копирование такого значения не создаёт новой единицы: все копии обозначают одну и ту же единицу.

**emb.periph.no-take** — Операции передачи владения единицей нет. Единственность доступа устанавливается анализом из разделов 2.2–2.4, а не системой типов.

### 2.2 Эффекты экземпляров

**emb.periph.effect** — Каждая единица владения `U` задаёт эффект с тем же именем `U`. Каждая операция над `U` или над значением, полученным из `U` (доступ к регистру, вызов метода), имеет эффект `U`. Эффекты экземпляров распространяются как любые другие эффекты ([07-effects](07-effects.ru.md)), в том числе через параметрические ссылки.

**Примечание** — Эффекты экземпляров дополняют классовые эффекты, которые предоставляет цель (`Gpio`, `Uart`, `Timers`, …).

### 2.3 Контексты исполнения

**emb.ctx.def** — *Контекст исполнения* — это одно из:

1. *основной контекст*: выполнение `main` и всего, что она вызывает;
2. *контекст задачи*: один работающий экземпляр задачи, запущенный через `go` или `task.Go` ([09-concurrency](09-concurrency.ru.md));
3. *контекст прерывания*: выполнение одного обработчика `interrupt`;
4. *контекст ловушки*: выполнение одного обработчика `trap` ([15-os](15-os.ru.md)).

**emb.ctx.instances** — Оператор `go`, который может запустить несколько одновременно живущих экземпляров задачи, задаёт столько же контекстов задач. Два экземпляра одного оператора `go` — разные контексты по отношению друг к другу.

**emb.ctx.reach** — Для каждой единицы владения `U` реализация ДОЛЖНА вычислить множество `C(U)` контекстов исполнения, в которых достижим эффект `U`, не считая обращений во время фазы инициализации (2.5).

### 2.4 Один и несколько контекстов

**emb.ctx.single** — Если в `C(U)` не больше одного элемента, программа МОЖЕТ обращаться к `U` без синхронизации.

**emb.ctx.multi** — Если в `C(U)` больше одного элемента, каждое обращение к `U` вне фазы инициализации ДОЛЖНО происходить внутри критической секции `U`:

```go
for t := range device.TIM2.Lock() {
    t.ClearUpdateFlag()
}
```

Любое другое обращение — ошибка. Диагностика ДОЛЖНА назвать как минимум два контекста из `C(U)` и путь обращения в каждом, например: `TIM2 is used in main (after interrupts.Enable) and in interrupt TIM2 without a critical section`.

**emb.lock.form** — `Lock()` единицы владения возвращает итератор, который выдаёт `inout`-доступ к единице ровно один раз, как задано для range-over-func с `inout` в [05-statements](05-statements.ru.md).

**emb.lock.ceiling** — *Потолок приоритета* `U` — наивысший приоритет среди контекстов из `C(U)`. Пока выполняется тело критической секции `U`, реализация ДОЛЖНА исключать вытеснение любым контекстом, приоритет которого не выше потолка (например, повышением маски приоритета прерываний или запретом прерываний, если у архитектуры нет маскирования по приоритетам). Потолок ДОЛЖЕН вычисляться при компиляции.

**emb.lock.no-block** — Тело критической секции НЕ ДОЛЖНО иметь эффект `Block`.

**emb.prio.order** — При вычислении потолка любой контекст прерывания имеет более высокий приоритет, чем любой контекст задачи и основной контекст. Приоритеты контекстов прерываний между собой берутся из описания устройства. Приоритеты контекстов задач — уровни приоритета задач из [09-concurrency](09-concurrency.ru.md). Основной контекст работает с приоритетом задачи `task.Normal` (**conc.prio.inherit**).

### 2.5 Фаза инициализации

**emb.init.start** — На целях с прерываниями `main` начинает выполняться с глобально запрещёнными прерываниями и неработающим планировщиком задач.

**emb.init.end** — *Фаза инициализации* `main` состоит из точек программы, достижимых от входа в `main` по пути, который не проходит через вызов `interrupts.Enable()` или `task.Run()`. Обращение к единице владения в фазе инициализации не добавляет основной контекст в `C(U)`.

**emb.init.calls** — `interrupts.Enable()` и `task.Run()` ДОЛЖНЫ вызываться только непосредственно из `main`.

### 2.6 Общие переменные

**emb.shared.var** — Переменная уровня пакета, достижимая более чем из одного контекста исполнения, ДОЛЖНА иметь атомарный тип или использоваться только внутри критической секции. Переменные уровня пакета и так ограничены такими видами ([06-memory](06-memory.ru.md)); это правило распространяет ограничение на контексты прерываний и ловушек.

**emb.shared.mutex** — На одноядерной цели в профиле `core` `sync.Mutex[T]` ДОЛЖЕН реализовываться по протоколу потолка приоритетов: его `Lock()` поднимает приоритет до потолка мьютекса, вычисленного по всем его пользователям, и никогда не ждёт. На таких целях у `Lock()` нет эффекта `Block`, поэтому мьютекс МОЖЕТ использоваться в обработчиках прерываний.

## 3. Обработчики прерываний

**emb.irq.name** — Имя обработчика `interrupt` ДОЛЖНО совпадать с именем вектора прерывания из описания устройства. У вектора ДОЛЖНО быть не больше одного обработчика.

**emb.irq.signature** — У обработчика `interrupt` нет параметров и результатов.

**emb.irq.effects** — У обработчика `interrupt` есть неявное ограничение `ensures effect.Without(Alloc, Block, Panic)` ([07-effects](07-effects.ru.md), [08-contracts](08-contracts.ru.md)). Поэтому проверки переполнения и границ в обработчике ДОЛЖНЫ быть доказаны или обработаны явно.

**emb.irq.profile** — Объявления `interrupt` допустимы только в пакетах, профиль которых — только `core`.

**emb.irq.no-call** — Обработчик `interrupt` НЕ ДОЛЖЕН вызываться, использоваться как функциональное значение или передаваться как аргумент.

**emb.irq.vectors** — Реализация ДОЛЖНА генерировать таблицу векторов прерываний по описанию устройства и объявленным обработчикам. Векторы без обработчика ДОЛЖНЫ связываться с обработчиком по умолчанию, который ведёт себя как паника с поведением `OnPanic` цели ([19-runtime](19-runtime.ru.md)).

## 4. Статические задачи

**emb.task.static** — В профиле `core` каждая задача статическая: наибольшее число одновременно живущих экземпляров каждого оператора `go` и размер стека каждого экземпляра ДОЛЖНЫ быть известны при компиляции. Оператор `go`, число живых экземпляров которого не ограничено при компиляции, — ошибка.

**Примечание** — Планирование статических задач (вытеснение между уровнями приоритета, очередь внутри уровня) описано в [09-concurrency](09-concurrency.ru.md).

## 5. Анализ стека

**emb.stack.depth** — Реализация ДОЛЖНА вычислять наибольшую глубину стека основного контекста, каждого контекста задачи и каждого обработчика прерывания и ловушки. Вызовы через функциональные значения и интерфейсы разрешаются множеством возможных целей в программе ([07-effects](07-effects.ru.md)).

**emb.stack.nesting** — Потребность стека, общего для нескольких контекстов (на большинстве микроконтроллеров основной стек общий с обработчиками прерываний), — глубина его базового контекста плюс наибольшая сумма глубин обработчиков вдоль любой цепочки вложенных вытеснений, допустимой приоритетами прерываний.

**emb.stack.limit** — Если потребность стека превышает доступный ему размер (`Stack` цели для основного стека, вычисленный стек задачи для задачи), сборка ДОЛЖНА завершиться ошибкой, а диагностика ДОЛЖНА показать самую глубокую цепочку вызовов.

**emb.stack.recursion** — Рекурсия в профиле `core` подчиняется [19-runtime](19-runtime.ru.md): рекурсия без доказанной границы глубины в задаче или обработчике — ошибка.

## 6. Наихудшее время выполнения

**emb.wcet.contract** — Функция, в том числе обработчик `interrupt`, МОЖЕТ задать верхнюю границу своего времени выполнения через `ensures wcet.Within(d)`, где `d` — константная длительность, известная при компиляции ([08-contracts](08-contracts.ru.md)).

**emb.wcet.model** — Граница проверяется по модели тактов из описания архитектуры цели ([13-targets](13-targets.ru.md)) и тактовой частоте процессора цели. Если у цели нет модели тактов или частоты, `wcet.Within` — ошибка.

**emb.wcet.isolation** — `wcet.Within(d)` ограничивает время выполнения функции самой по себе: время в обработчиках, которые её вытесняют, не учитывается.

**emb.wcet.loops** — У каждого цикла на пути функции с `wcet.Within` ДОЛЖНА быть граница числа итераций, которую может доказать решатель; иначе граница времени не доказана.

**emb.wcet.sound** — Вычисленная граница НЕ ДОЛЖНА быть меньше любого фактического времени выполнения, допустимого моделью тактов. Для процессоров с кэшем или конвейером анализ ДОЛЖЕН быть консервативным.

**emb.wcet.report** — Если граница не доказана, диагностика ДОЛЖНА показать самый долгий найденный путь выполнения с числом тактов по каждому базовому блоку.

## 7. Пример

```go
package main

profile core

import (
    "an/atomic"
    "an/cpu"
    "an/device"
    "an/gpio"
    "an/interrupts"
    "an/timer"
)

var ticks atomic.U32

func main() {
    led := device.GPIOC.Pin13.Output(gpio.PushPull)               // initialization phase
    device.TIM2.Start(timer.Config{Freq: Hz(2), Interrupt: true})
    interrupts.Enable()                                           // end of initialization phase

    for {                                                         // C(TIM2) = {interrupt TIM2}
        if ticks.Load()%2 == 0 { led.Low() } else { led.High() }
        cpu.WaitForInterrupt()
    }
}

interrupt TIM2() {
    device.TIM2.ClearUpdateFlag()
    ticks.Add(1)
}
```

| STM32, RP2040, nRF52 | ARM Cortex-M | Самый массовый класс |

## Открытые вопросы


1. **Переопределение приоритетов прерываний.** Отложено до реализации — шаг 33. Приоритеты берутся из описания устройства; способ их переопределить проектируется вместе с приоритетами задач.
2. **Многоядерные микроконтроллеры (RP2040, ESP32).** Отложено до реализации — шаг 52. **emb.shared.mutex** относится к одноядерным целям; многоядерные цели `core` описываются вместе с целью RP2040.
3. **Анализ времени отклика.** Отложено до реализации — шаг 53. Проверка того, что все задачи укладываются в сроки (WCET плюс периоды задач и вытеснение), проектируется вместе с WCET.
