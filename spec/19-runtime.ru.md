# 19. Рантайм

Рантайм — код, который инструментарий компонует в программу помимо её собственного кода: старт, управление памятью, планирование задач, обработка паники, загрузка внешних библиотек и, в профиле `ui`, подсистема интерфейса.

## 19.1 Общие требования

**rt.lang.anlang** — Рантайм ДОЛЖЕН быть написан на Anlang в профиле `core` и поставляться исходниками вместе со стандартной библиотекой (см. [18-stdlib](18-stdlib.ru.md)).

**rt.lang.not-importable** — Пользовательский код НЕ ДОЛЖЕН импортировать пакет рантайма `an/runtime`. Его возможности доступны только через язык и стандартную библиотеку.

**rt.no-gc** — Рантайм НЕ ДОЛЖЕН содержать сборщик мусора. Памятью управляют семантика значений, копирование при записи и арены (см. [06-memory](06-memory.ru.md)).

**rt.no-rtti** — Рантайм НЕ ДОЛЖЕН содержать информацию о типах и рефлексию во время выполнения. Рефлексия существует только при компиляции (см. [10-compile-time](10-compile-time.ru.md)). Отладочные таблицы записываются в отдельный файл и не входят в образ программы (см. [20-toolchain](20-toolchain.ru.md), **tool.debug.side-table**).

**rt.link.piecewise** — Рантайм ДОЛЖЕН компоноваться по частям: компонент рантайма ДОЛЖЕН попадать в результат, только если программа его использует.

- Программа, которая не запускает задач, НЕ ДОЛЖНА содержать планировщик задач.
- Программа для DOS, которая не запускает задач, ДОЛЖНА содержать из рантайма только код старта и обработчик паники.

**rt.cow.inline** — Подсчёт ссылок для значений с копированием при записи ДОЛЖЕН быть реализован кодом в местах использования, а не отдельной службой рантайма. Счётчик ДОЛЖЕН быть атомарным только для значений, переданных между задачами (см. [22-compiler](22-compiler.ru.md)).

## 19.2 Отличия от рантайма Go

*Справочный раздел.*

| Компонент рантайма Go | Anlang |
| --- | --- |
| сборщик мусора | нет |
| рефлексия во время выполнения | нет; только при компиляции (`meta`) |
| информация о типах во время выполнения | нет; только отладочные таблицы в отдельном файле |
| планировщик горутин | свой планировщик для каждого профиля |
| стеки, растущие копированием | нет: размер стека вычисляется статически, иначе резерв с защитной страницей |
| подсчёт ссылок | встроенный код копирования при записи, а не отдельная служба |

## 19.3 Состав по профилям

**rt.profile.composition** — Рантайм программы в данном профиле ДОЛЖЕН состоять из компонентов следующей таблицы с учётом **rt.link.piecewise**.

| Компонент | `core` | `app` | `ui` |
| --- | --- | --- | --- |
| старт | из описания цели: вектор сброса, точка входа .COM, точка входа Multiboot | точка входа ОС | точка входа платформы |
| память | только статическая, пулы фиксированного размера | аллокатор общего назначения и арены | как в `app` |
| задачи | статический планировщик с приоритетами | планировщик M:N поверх потоков ОС с асинхронным вводом-выводом | как в `app`, плюс главный поток интерфейса |
| паника | по полю `OnPanic` цели: сброс, остановка, выход в DOS | сообщение со стектрейсом, затем завершение процесса | как в `app` |
| внешние функции | `ffi.At`, статическая компоновка | плюс загрузка динамических библиотек при старте | как в `app` |
| интерфейс | — | — | рендер, раскладка, доступность, ввод текста |

Поведение каждого компонента описано в других файлах: память — в [06-memory](06-memory.ru.md), задачи — в [09-concurrency](09-concurrency.ru.md), внешние функции — в [12-ffi](12-ffi.ru.md), последовательность запуска и выбор `OnPanic` — в [13-targets](13-targets.ru.md), действия при панике — в §19.4, интерфейс — в [17-ui](17-ui.ru.md).

## 19.4 Паника

**rt.panic.core** — В профиле `core` паника ДОЛЖНА выполнять действие, заданное полем `OnPanic` описания цели (см. [13-targets](13-targets.ru.md)).

**rt.panic.actions** — Значения `target.PanicAction` ведут себя так:

1. `PrintAndExit` — вывести причину паники и трассировку стека (**rt.panic.trace**) на консоль платформы, затем вернуть управление окружению с ненулевым статусом: завершение процесса в операционной системе, возврат в DOS на `dos` (`int 21h`, функция `4Ch`).
2. `Reset` — сбросить устройство способом, заданным описанием архитектуры или устройства. Если у цели есть отладочный канал, реализация МОЖЕТ сначала вывести туда причину.
3. `Halt` — запретить прерывания и остановиться в цикле ожидания с низким энергопотреблением. Если у цели есть отладочный канал, реализация МОЖЕТ сначала вывести туда причину.

**rt.start.data** — На целях, где области памяти разделяют код и изменяемые данные (**target.memory.placement**), код запуска ДОЛЖЕН скопировать начальные значения изменяемых данных из области `Exec` в RAM и обнулить остальные изменяемые данные до выполнения любого кода на Anlang.

**rt.panic.app** — В профилях `app` и `ui` паника ДОЛЖНА выводить в стандартный поток ошибок сообщение с причиной паники и стектрейсом, а затем завершать процесс с ненулевым кодом возврата.

**rt.panic.trace** — Стектрейсы ДОЛЖНЫ содержать имена функций, файлов и номера строк на всех целях. На целях, где отладочная таблица не входит в образ, стектрейс ДОЛЖЕН содержать адреса, которые `anlang` разрешает по отдельной таблице (см. [20-toolchain](20-toolchain.ru.md), **tool.debug.side-table**).

**Примечание** — Какие операции могут вызвать панику и как распространяется эффект `Panic`, описано в [04-expressions](04-expressions.ru.md) и [07-effects](07-effects.ru.md).

## 19.5 Стеки задач

**rt.stack.static** — Для каждой задачи, обработчика прерывания и `main` компилятор ДОЛЖЕН вычислять максимальную глубину стека, если она ограничена: рекурсии нет, а косвенные вызовы разрешаются в известный набор функций. Стек такой задачи ДОЛЖЕН иметь ровно этот размер, округлённый до выравнивания цели.

**rt.stack.reserve** — В профилях `app` и `ui` задача, максимальную глубину стека которой вычислить нельзя (рекурсия, неограниченная глубина), ДОЛЖНА получать резерв виртуальной памяти с защитной страницей. Физическая память выделяется по мере использования. Переполнение стека ДОЛЖНО обнаруживаться и сообщаться как паника; оно НЕ ДОЛЖНО портить память.

**rt.stack.report** — Компилятор ДОЛЖЕН сообщать о каждой задаче, которой понадобился резерв по **rt.stack.reserve**, в отчёте `anlang size` и в отчёте сборки `-json` (см. [20-toolchain](20-toolchain.ru.md)).

**rt.stack.core-recursion** — В профиле `core` рекурсия в задаче, обработчике прерывания или `main` без доказанной границы глубины ДОЛЖНА отвергаться при компиляции (сравнение глубины стека с размером `Stack` цели — см. [14-embedded](14-embedded.ru.md)).

## 19.6 Компоненты только для разработки

**rt.dev.only** — Детерминированный планировщик для тестов (см. [09-concurrency](09-concurrency.ru.md), [20-toolchain](20-toolchain.ru.md)) и интерпретатор для горячей перезагрузки (см. [17-ui](17-ui.ru.md)) НЕ ДОЛЖНЫ присутствовать в выпускной сборке.

**rt.dev.builds** — *Выпускная сборка* — результат `anlang build`. *Отладочная сборка* — сборка, которую делают `anlang test`, `anlang dev`, `anlang debug` или `anlang run` с параметрами разработки. Компоненты только для разработки МОГУТ присутствовать только в отладочных сборках.
