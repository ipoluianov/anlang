# 9. Конкурентность

Этот файл описывает задачи, структурированную конкурентность, каналы, типы синхронизации, отмену, приоритеты и модели исполнения профилей.

У конкурентности синтаксис Go — `go`, каналы, `select`, — а семантика структурированная: функция возвращается только после того, как завершились все запущенные ею задачи. Гонки данных невозможны по построению: между задачами значения копируются, а разделяемое состояние существует только внутри типов синхронизации.

## 9.1 Задачи

**conc.task.unit** — *Задача* — единица конкурентного исполнения. Потоки операционной системы в языке не видны.

**conc.task.go** — Синтаксис оператора `go` — как в Go. Он вычисляет функциональное значение и аргументы в запускающей задаче, как в Go, и запускает новую задачу, которая выполняет вызов. Оператор `go` имеет эффект `Tasks` ([07-effects](07-effects.ru.md)).

**conc.task.owner** — Каждая задача, запущенная оператором `go` или через `task.Go`, *принадлежит* вызову функции, в теле которой стоит этот оператор. Функциональные литералы для этого правила считаются функциями; тело цикла range-over-func не является функциональным литералом и относится к объемлющей функции ([05-statements](05-statements.ru.md)).

**conc.task.config** — `task.Go(cfg task.Config, f F)` запускает задачу, как `go f()`, с параметрами из `cfg` (§9.8); `F` — это `func()` или `func() error`. `go f(args)` равносилен `task.Go(task.Config{}, …)` с приоритетом запускающей задачи.

**conc.task.error** — У вызова в операторе `go` или переданного в `task.Go` МОЖЕТ быть последний результат типа `error`. Эта ошибка — *результат-ошибка* задачи; она передаётся вызову-владельцу через `task.Wait` (§9.2). Остальные результаты отбрасываются, как в Go.

## 9.2 Структурированная конкурентность

**conc.struct.wait** — `task.Wait() error` блокируется, пока не завершатся все задачи, принадлежащие вызывающему вызову.

1. Если задача завершается с ненулевым результатом-ошибкой, первая такая ошибка в порядке завершения запоминается, все остальные задачи вызова отменяются (§9.4), и `Wait` возвращает запомненную ошибку после того, как эти задачи остановились.
2. Если ошибка не запомнена, а дедлайн вызова (**conc.cancel.deadline**) истёк, `Wait` возвращает `task.ErrDeadline`.
3. Иначе `Wait` возвращает `nil`.

После возврата из `Wait` вызову не принадлежит ни одной работающей задачи; последующие операторы `go` запускают новые принадлежащие ему задачи.

**conc.struct.exit** — Когда вызов завершается — через `return`, по достижении конца тела или паникой, — а ему принадлежат незавершённые задачи, эти задачи отменяются (§9.4), и выход завершается только после их остановки. Результаты-ошибки остановленных так задач отбрасываются. Ни один вызов не возвращается раньше, чем завершатся все принадлежащие ему задачи.

**conc.struct.error-wait** — Если в функции есть оператор `go` или вызов `task.Go`, который может запустить задачу с результатом-ошибкой, то на каждом пути от такого оператора до выхода из функции без паники программа ДОЛЖНА вызвать `task.Wait()` или `task.Cancel()` после последнего такого оператора на этом пути. На ошибку, которую возвращает `task.Wait()`, распространяется **stmt.error.unused** ([05-statements](05-statements.ru.md)). Это расширение правила о неиспользованной ошибке: результат-ошибка задачи никогда не теряется молча.

**conc.struct.panic** — Если задача паникует, рантайм отменяет все остальные задачи того же вызова-владельца (§9.4), ждёт их завершения, а затем вызов-владелец паникует с тем же значением в ближайшей точке ожидания (включая `task.Wait`) или при выходе — что наступит раньше.

**conc.struct.nested** — Правила действуют рекурсивно: задача, владеющая задачами, перед своим завершением отменяет их или ждёт.

**conc.struct.no-leak** — Как следствие, ни одна задача не переживает вызов, которому принадлежит, кроме задач, запущенных через `task.Detach` (§9.3).

```go
func Serve(reqs []Request) (Stats, error) {
    var stats sync.Mutex[Stats]
    for _, r := range reqs {
        go process(r, stats)              // process returns error
    }
    if err := task.Wait(); err != nil {
        return Stats{}, err               // the other tasks have been cancelled
    }
    return stats.Load(), nil
}
```

## 9.3 Отсоединённые задачи

**conc.detach.call** — `task.Detach(f func())` запускает задачу, которая не принадлежит вызывающему вызову и МОЖЕТ его пережить. Вызов `task.Detach` имеет эффект `Detach`, объявленный в `an/task`.

**conc.detach.profile** — `Detach` запрещён в профиле `core` ([07-effects](07-effects.ru.md), **eff.profile.allowed**).

**conc.detach.no-inout** — Отсоединённая задача НЕ ДОЛЖНА получать `inout`-доступ (§9.6). Значения, захваченные `f`, — копии; объекты синхронизации, достижимые из `f`, размещаются в куче (**conc.sync.placement**).

## 9.4 Отмена и дедлайны

**conc.cancel.tree** — Отмена вызова отменяет все принадлежащие ему задачи и рекурсивно все задачи, которыми владеют они. Отмена распространяется от родителя к детям автоматически; программы не передают значение контекста.

**conc.cancel.delivery** — Отменённая задача не прерывается между точками ожидания. В ближайшей точке ожидания (§9.5) задача сворачивается: выполняются отложенные вызовы, итераторы освобождают то, что держат (§9.7), как при панике, но сворачивание не является ошибкой и не передаётся владельцу. `task.Cancelled() bool` сообщает, отменена ли текущая задача, — для вычислений без точек ожидания.

**conc.cancel.deadline** — `task.Deadline(d time.Duration)` устанавливает для вызывающего вызова дедлайн через `d` от текущего момента и возвращает канал, который становится готовым при наступлении дедлайна. При наступлении дедлайна отменяются все задачи, принадлежащие вызову. Дедлайн, установленный владельцем, действует на все задачи под ним; действующий дедлайн задачи — самый ранний из её собственного и дедлайнов её владельцев.

**conc.cancel.explicit** — `task.Cancel()` отменяет все задачи, принадлежащие вызывающему вызову, ждёт их остановки и отбрасывает их результаты-ошибки. Сам вызов не отменяется. Это явный способ бросить задачи с результатами-ошибками перед выходом (**conc.struct.error-wait**); задачи без результатов-ошибок и так отменяются при выходе (**conc.struct.exit**).

```go
func FetchAll(urls []string) ([]Page, error) {
    results := make(chan result, len(urls))
    for _, u := range urls {
        go func() {
            page, err := http.Get(u)
            results <- result{page, err}
        }()
    }

    pages := []Page{}
    for range urls {
        select {
        case r := <-results:
            if r.err != nil {
                return nil, r.err            // the exit cancels the remaining requests
            }
            pages = append(pages, r.page)
        case <-task.Deadline(5 * time.Second):
            return nil, ErrTimeout           // the deadline has cancelled the remaining tasks
        }
    }
    return pages, nil
}
```

## 9.5 Точки ожидания

**conc.wait.points** — *Точка ожидания* — операция, в которой задача может быть приостановлена:

1. отправка в канал или приём из канала, а также оператор `select` без готовой ветки `default`;
2. захват блокировки (§9.7), кроме одноядерных целей `core`, где блокировки работают по протоколу потолка приоритетов и никогда не ждут ([14-embedded](14-embedded.ru.md), **emb.shared.mutex**);
3. `task.Sleep` и `task.Yield`;
4. блокирующая операция ввода-вывода стандартной библиотеки;
5. `task.Wait`, `task.Cancel` и выход, пока принадлежащие задачи останавливаются (**conc.struct.wait**, **conc.struct.exit**);
6. вызов внешней функции, которую цель считает блокирующей (**conc.os.blocking-ffi**).

Точка ожидания имеет эффект `Block` ([07-effects](07-effects.ru.md), **eff.source.wait**).

## 9.6 Значения между задачами

**conc.value.copy** — Аргументы вызова в `go` и значения, захваченные функциональным литералом, копируются, как при присваивании ([06-memory](06-memory.ru.md)). Отправка значения в канал копирует его: у отправителя остаётся своя копия, и получатель не видит её последующих изменений.

**conc.value.cow** — Реализация НЕ ДОЛЖНА физически копировать большие значения, если может разделить их копированием при записи. Буферы копирования при записи, достижимые более чем из одной задачи, ДОЛЖНЫ использовать атомарные счётчики ссылок.

**conc.value.no-shared-mutable** — Кроме объектов синхронизации (§9.7), между задачами нет разделяемого изменяемого состояния.

**conc.inout.borrow** — Если оператор `go` передаёт аргумент как `inout`, аргумент *заимствуется* новой задачей до конца вызова-владельца. От оператора `go` до конца вызова вызов-владелец НЕ ДОЛЖЕН обращаться к заимствованному значению или к любой его части.

**conc.inout.disjoint** — Два оператора `go` одного вызова МОГУТ заимствовать части одного значения, только если части не пересекаются. Для срезов и массивов непересечение диапазонов индексов — обязательство доказательства ([08-contracts](08-contracts.ru.md)); если решатель его не доказал, программа отвергается.

**conc.inout.capture** — Функциональный литерал, используемый в операторе `go` или передаваемый в `task.Go`, НЕ ДОЛЖЕН захватывать `inout`-параметр объемлющей функции. `inout`-доступ попадает в задачу только как явный `inout`-аргумент.

```go
func SortParallel(xs inout []i32) {
    mid := len(xs) / 2
    go Sort(xs[:mid])        // parts are disjoint:
    go Sort(xs[mid:])        // proved by the solver
    // xs[0] = 1             // rejected: xs is borrowed by tasks
}
```

## 9.7 Типы синхронизации

**conc.sync.types** — Типы синхронизации — это `chan T`, `sync.Mutex[T]`, `sync.RWMutex[T]` и типы пакета `an/atomic` (`atomic.U32`, `atomic.I64`, `atomic.Bool` и другие).

**conc.sync.handle** — Значение типа синхронизации — *дескриптор*: присваивание, передача, захват функциональным литералом и отправка в канал копируют дескриптор, и все копии ссылаются на один объект ([06-memory](06-memory.ru.md)). Это единственное исключение из семантики значений.

**conc.sync.zero** — Нулевое значение `sync.Mutex[T]`, `sync.RWMutex[T]` и атомарных типов — готовый объект с нулевым значением содержимого. Нулевое значение `chan T` — `nil`; каналы создаются через `make`. Канал `nil` блокирует навсегда при отправке и приёме, как в Go.

**conc.sync.lock** — Значение внутри `sync.Mutex[T]` доступно только через `m.Lock()` — итератор для range-over-func, который захватывает блокировку, выдаёт один `inout T`-доступ и освобождает блокировку при выходе из тела цикла любым путём: обычным завершением, `break`, `return`, паникой или отменой ([05-statements](05-statements.ru.md)).

**conc.sync.load** — `m.Load() T` возвращает копию значения, взятую под блокировкой.

**conc.sync.lock-no-wait** — Тело цикла по `m.Lock()` значения `sync.Mutex[T]` или `sync.RWMutex[T]` НЕ ДОЛЖНО иметь эффекта `Block` ([07-effects](07-effects.ru.md)): в нём нет точек ожидания (§9.5). Поэтому отмена, которая сворачивает задачу только в точке ожидания (**conc.cancel.delivery**), не может прервать тело между двумя изменениями значения и оставить состояние, нарушающее инвариант его типа ([08-contracts](08-contracts.ru.md), **contract.type.assume**), для следующей задачи, которая захватит блокировку. Это обобщает **emb.lock.no-block** из [14-embedded](14-embedded.ru.md).

**conc.sync.poison** — Если тело цикла по `m.Lock()` прерывает паника, блокировка освобождается, а мьютекс становится *отравленным*: каждый последующий `m.Lock()`, `m.Load()` и захват на запись этого мьютекса вызывает панику. Ни одна задача не видит значения, изменение которого прервала паника.

**conc.sync.rwmutex** — `sync.RWMutex[T]` предоставляет `Lock()`, как `sync.Mutex[T]`, и `RLock()` — итератор, который выдаёт копию значения под разделяемой блокировкой.

**conc.sync.atomic** — Атомарные типы предоставляют `Load`, `Store`, `Add`, `Swap` и `CompareAndSwap`, как атомарные типы `sync/atomic` в Go. Явные порядки памяти описаны в [15-os](15-os.ru.md). На одноядерной цели профиля `core` операция выполняется с запрещёнными прерываниями. Пока дескрипторы (**conc.sync.handle**) не реализованы, атомарные значения — переменные уровня пакета, а их методы принимают их как `inout`-получатели.

**conc.sync.placement** — Объект синхронизации размещается:

- в кадре создавшего его вызова, если ни один дескриптор объекта не может пережить этот вызов: структурированная конкурентность гарантирует, что все задачи, которые им пользуются, завершатся до освобождения кадра ([06-memory](06-memory.ru.md), **mem.sync.frame**);
- иначе — дескриптор возвращается, сохраняется в более долгоживущем значении, отправляется более долгоживущей задаче или передаётся в `task.Detach` — в куче с атомарным счётчиком ссылок ([06-memory](06-memory.ru.md), **mem.sync.heap**); это требует эффекта `Alloc` и поэтому недоступно в `core`, кроме переменной уровня пакета.

Переменные синхронизации уровня пакета размещаются статически.

```go
var stats sync.Mutex[Stats]

func Record(d time.Duration) error {
    for s := range stats.Lock() {
        if s.count == MaxRecords {
            return ErrFull           // the lock is released on every exit
        }
        s.count++
        s.total += d
    }
    return nil
}
```

## 9.8 Приоритеты

**conc.prio.levels** — Приоритеты задач — `task.Low`, `task.Normal` и `task.High`. В профиле `core` есть ещё уровень `task.Critical`; использование `task.Critical` в другом профиле отвергается.

**conc.prio.inherit** — Задача, запущенная через `go`, получает приоритет запускающей задачи. `task.Go` с `task.Config{Priority: p}` запускает задачу с приоритетом `p`. `main` выполняется с приоритетом `task.Normal`.

**conc.prio.meaning** — Смысл приоритетов зависит от модели исполнения (§9.9):

| Модель исполнения | Смысл |
| --- | --- |
| `core` | Готовая задача более высокого уровня вытесняет задачу более низкого; задачи одного уровня выполняются по очереди |
| `app` | Подсказка планировщику; задача, привязанная к потоку ОС, получает соответствующий приоритет потока |
| `ui` | Главная задача интерфейса выше всех остальных; фоновые задачи выполняются с `Low` |
| кооперативная (DOS, браузер без потоков) | Порядок выбора следующей готовой задачи |

**conc.prio.inversion** — В `app` и `ui` задача, держащая блокировку `sync.Mutex` или `sync.RWMutex`, выполняется с приоритетом не ниже, чем у самой приоритетной задачи, ждущей этой блокировки (наследование приоритета).

**conc.prio.ceiling** — В `core` компилятор вычисляет для каждой блокировки *потолок приоритета* — наивысший приоритет среди всех задач и обработчиков прерываний, которые её используют. Захват блокировки поднимает держателя до потолка до освобождения. На одном процессоре это исключает инверсию приоритетов и взаимоблокировку на этих блокировках. Относительный приоритет контекстов прерываний, задач и `main` для потолка задаёт **emb.prio.order** ([14-embedded](14-embedded.ru.md)).

**conc.prio.starvation** — В `app` и `ui` планировщику СЛЕДУЕТ постепенно поднимать приоритет задач, которые давно готовы, но не выполнялись. В `core` компилятор ДОЛЖЕН предупреждать о задаче с приоритетом `High` или `Critical`, в которой есть цикл без точки ожидания.

## 9.9 Модели исполнения

**conc.model.core** — В `core` множество задач статично: компилятор определяет каждую задачу, которую программа может запустить, и её размер стека ([19-runtime](19-runtime.ru.md)). Оператор `go` ДОЛЖЕН выполняться число раз, которое компилятор может ограничить: он НЕ ДОЛЖЕН стоять в цикле без доказанной границы числа итераций или в рекурсивной функции. Планирование вытесняющее между уровнями приоритета и по очереди внутри уровня. Задачи, запущенные до `task.Run()`, начинают выполняться при вызове `task.Run()`; `task.Run()` не возвращается.

**conc.model.core-chan** — В `core` размер буфера в `make(chan T, n)` ДОЛЖЕН быть константным выражением.

**conc.model.app** — В `app` задачи выполняются планировщиком M:N поверх потоков ОС с асинхронным вводом-выводом (epoll, kqueue, IOCP, io_uring) и выполняются параллельно, где позволяет железо.

**conc.model.ui** — В `ui` есть одна главная задача интерфейса и фоновые задачи. Состояние интерфейса обновляется только в главной задаче интерфейса ([17-ui](17-ui.ru.md)).

**conc.model.web** — На платформе `web` задачи выполняются в цикле событий браузера и в потоках WebAssembly там, где браузер их предоставляет.

**conc.model.cooperative** — Там, где нет потоков ОС или нескольких ядер (DOS, браузер без потоков), задачи выполняются кооперативно: переключение задачи происходит только в точке ожидания. Смысл программы тот же; меняется только скорость.

**conc.model.cooperative-warning** — При компиляции для кооперативной модели компилятор ДОЛЖЕН предупреждать о цикле в теле задачи, число итераций которого не доказано меньшим определяемой реализацией границы и в теле которого нет точки ожидания.

## 9.10 Задачи и потоки ОС

**conc.os.lock-thread** — `task.LockThread()` привязывает вызывающую задачу к её текущему потоку ОС до завершения задачи. Предназначено для внешних библиотек с привязанным к потоку состоянием, графических контекстов и главного потока интерфейса.

**conc.os.blocking-ffi** — Реализация с потоками ОС ДОЛЖНА выполнять вызов внешней функции, которая может надолго заблокироваться, так, чтобы он не останавливал остальные задачи, например вынося его на отдельный поток.

## 9.11 Детерминированное планирование в тестах

**conc.test.deterministic** — `anlang test` ДОЛЖЕН предоставлять детерминированный планировщик, который заменяет планировщик цели в тестах. Он ДОЛЖЕН перебирать чередования задач в точках ожидания, и каждое найденное им чередование ДОЛЖНО воспроизводиться по его идентификатору.

**conc.test.findings** — Детерминированный планировщик ДОЛЖЕН сообщать о взаимоблокировках (все оставшиеся задачи ждут) и ДОЛЖЕН позволять тестам проверять свойства порядка на разных чередованиях.

**Примечание** — Анализ планируемости реального времени — доказательство при компиляции, по границам WCET и периодам задач, что все задачи укладываются в свои сроки, — цель будущих версий ([14-embedded](14-embedded.ru.md)).
