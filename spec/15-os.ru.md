# 15. Операционные системы

Этот файл описывает средства для написания ядер операционных систем на Anlang: привилегии, типизированные адреса, обработчики ловушек, потоки ядра и переключение контекста, таблицы системных вызовов, примитивы многопроцессорности и загрузочные цели.

Ядра пишутся в профиле `core`. Единственный новый синтаксис — объявление `trap`; его синтаксис — продукция `HandlerDecl` в [03-declarations](03-declarations.ru.md) §3.10. Правила о контекстах исполнения, критических секциях и анализе стека из [14-embedded](14-embedded.ru.md) действуют и для ядер.

## 1. Привилегии

**os.priv.effect** — Команда, которую формальная семантика команд из описания архитектуры ([13-targets](13-targets.ru.md)) помечает как привилегированную, имеет эффект `Privileged`. Примеры: загрузка таблиц страниц, запрет прерываний, запись в регистры, специфичные для модели процессора. Функция пакета архитектуры (`an/arch/...`), выполняющая такую команду, имеет эффект `Privileged`, и эффект распространяется как обычно ([07-effects](07-effects.ru.md)).

**os.priv.deny** — По умолчанию `Privileged` запрещён во всех профилях.

**os.priv.allow** — Пакет МОЖЕТ иметь эффект `Privileged`, только если его профиль — `core` и `anlang.mod` проекта разрешает `Privileged` для пути этого пакета ([20-toolchain](20-toolchain.ru.md)):

```
effects (
    myos/kernel/...  allow {Privileged}
)
```

**os.priv.user** — Платформа, описывающая пользовательский режим операционной системы, НЕ ДОЛЖНА перечислять `Privileged` в своём `Provides` ([13-targets](13-targets.ru.md)). Поэтому программы для такой платформы не могут содержать привилегированных команд.

## 2. Типизированные адреса

**os.addr.types** — Пакет `an/mm` объявляет два разных определённых типа: `PhysAddr` (физический адрес) и `VirtAddr` (виртуальный адрес). Их базовый тип — беззнаковый целый тип, достаточный для физического и, соответственно, виртуального адресного пространства цели.

**os.addr.no-cross** — Преобразование между `PhysAddr` и `VirtAddr` в любую сторону — ошибка, хотя спецификация Go допускает преобразование между типами с одинаковым базовым типом. Перевод между двумя адресными пространствами делают только функции, которые обращаются к структурам трансляции адресов.

**os.addr.from-int** — Явное преобразование из целого типа в `PhysAddr` или `VirtAddr` допустимо (например, `VirtAddr(x86_64.ReadCR2())`). Оно подчиняется правилам сужения из [02-types](02-types.ru.md).

## 3. Обработчики ловушек

Обработчик `trap` обрабатывает исключение процессора: page fault, деление на ноль, недопустимую команду и так далее.

**os.trap.name** — Имя обработчика `trap` ДОЛЖНО совпадать с именем исключения, определённого в описании архитектуры цели. У исключения ДОЛЖНО быть не больше одного обработчика в программе.

**os.trap.signature** — Список параметров обработчика `trap` ДОЛЖЕН соответствовать сигнатуре, которую описание архитектуры задаёт для этого исключения. Он МОЖЕТ включать `frame inout TrapFrame` — сохранённое состояние процессора — и типизированный код исключения. У обработчика ловушки нет результатов.

**os.trap.frame** — Изменения в `frame` вступают в силу при возврате из обработчика: выполнение продолжается в состоянии, записанном в `frame`.

**os.trap.effects** — У обработчика `trap` то же неявное ограничение, что у обработчика `interrupt`: `ensures effect.Without(Alloc, Block, Panic)` (см. **emb.irq.effects** в [14-embedded](14-embedded.ru.md)).

**os.trap.profile** — Объявления `trap` допустимы только в пакетах, профиль которых — только `core` и для которых разрешён `Privileged` (**os.priv.allow**).

**os.trap.no-call** — Обработчик `trap` НЕ ДОЛЖЕН вызываться, использоваться как функциональное значение или передаваться как аргумент.

**os.trap.context** — Каждый обработчик `trap` — отдельный контекст исполнения для анализа из раздела 2.3 файла [14-embedded](14-embedded.ru.md).

**os.trap.nested** — Если исключение возникает во время работы его обработчика или другого обработчика ловушки, поведение определяется описанием архитектуры (например, исключение двойной ошибки). Если в программе нет обработчика получившегося исключения, действует поведение `OnPanic` цели.

## 4. Потоки ядра и переключение контекста

**os.thread.type** — Пакет `an/sched` предоставляет тип потока ядра. Для создания потока ядра нужны функция входа и размер стека — константа, известная при компиляции.

**os.thread.stack** — Размер стека потока ядра НЕ ДОЛЖЕН быть меньше наибольшей глубины стека его функции входа, вычисленной по **emb.stack.depth**. Иначе сборка завершается ошибкой.

**os.switch.primitive** — Каждый пакет архитектуры предоставляет ровно один примитив переключения контекста, реализованный через `asm`. Он сохраняет регистры, которые внутренний ABI требует сохранять, переключает стек и восстанавливает регистры целевого потока. Код ядра ДОЛЖЕН переключать потоки только через этот примитив.

## 5. Таблицы системных вызовов

Таблица системных вызовов описывает интерфейс между ядром и его программами как данные. По одной таблице реализация генерирует код диспетчеризации в ядре и функции на стороне программ.

```go
package kernos

import "an/abi"

const Syscalls = abi.Table{
    Convention: abi.ByArch{X86_64: "syscall", RISCV64: "ecall", I8086: "int 0x80"},
    Calls: []abi.Call{
        abi.Fn[func(fd Handle, buf []u8) (usize, error)]{No: 1, Name: "Write", Effects: Console},
        abi.Fn[func(fd Handle, buf inout []u8) (usize, error)]{No: 2, Name: "Read", Effects: Console},
        abi.Fn[func(path string, mode OpenMode) (Handle, error)]{No: 3, Name: "Open", Effects: File},
        abi.Fn[func(code i32)]{No: 4, Name: "Exit"},
    },
}
```

**os.sys.table** — Таблица системных вызовов — константа уровня пакета типа `abi.Table`. `Convention` сопоставляет каждой поддерживаемой архитектуре её команду системного вызова. `Calls` перечисляет вызовы; каждый элемент — `abi.Fn[F]`, где `F` — тип функции, с полями `No` (номер вызова), `Name` (экспортируемый идентификатор) и `Effects` (эффекты вызова; пусто, если не указано).

**os.sys.unique** — Номера вызовов в таблице ДОЛЖНЫ быть уникальны, и имена вызовов ДОЛЖНЫ быть уникальны.

**os.sys.types** — Типы параметров и результатов `F` ДОЛЖНЫ быть целыми типами, `bool`, `string`, срезами целых типов, `inout`-параметрами этих типов, типами дескрипторов, объявленными в пакете таблицы, и `error` последним результатом. Представление каждого типа в регистрах и памяти определяется соглашением таблицы и описанием архитектуры.

**os.sys.kernel** — Пакет ядра, реализующий таблицу, ДОЛЖЕН объявить для каждого вызова функцию с именем вызова и типом `F`. Отсутствующая или несовпадающая функция — ошибка. Реализация генерирует код диспетчеризации, который декодирует номер вызова и аргументы и вызывает эту функцию.

**os.sys.user** — Программа, которая импортирует пакет таблицы, получает для каждого вызова функцию с именем вызова и типом `F`, выполняющую системный вызов. Её эффекты — объявленные `Effects`. Как и у внешних функций, компилятор не может проверить объявленные эффекты ([12-ffi](12-ffi.ru.md)).

**os.sys.platform** — Описание платформы МОЖЕТ ссылаться на таблицу системных вызовов. Программа для этой платформы, вызывающая функцию, эффекта которой нет в `Provides` платформы или который запрещён в `anlang.mod`, отвергается.

## 6. Многопроцессорность

**os.smp.atomic** — Атомарные операции в `an/atomic` ДОЛЖНЫ принимать явный порядок памяти: `Relaxed`, `Acquire`, `Release`, `AcqRel` или `SeqCst`. Операция без явного порядка использует `SeqCst`.

**os.smp.percpu** — Пакет `an/kernel` предоставляет тип данных на процессор. Доступ к экземпляру текущего процессора даётся через range-over-func с `inout`-доступом ([05-statements](05-statements.ru.md)); на время тела вытеснение на текущем процессоре запрещено.

**os.smp.spin** — Пакет `an/sync` предоставляет тип спин-блокировки для синхронизации между процессорами. Его `Lock()` возвращает итератор, который один раз выдаёт `inout`-доступ, на время тела запрещает прерывания на текущем процессоре и крутится, пока блокировка не освободится. У `Lock()` спин-блокировки нет эффекта `Block`.

**os.smp.races** — Семантика значений и правила синхронизации из [06-memory](06-memory.ru.md) и [09-concurrency](09-concurrency.ru.md) действуют между процессорами: изменяемое значение никогда не достижимо с двух процессоров одновременно, кроме как через типы синхронизации.

## 7. Загрузочные цели

**os.boot.platforms** — Реализация ДОЛЖНА предоставлять описания платформ для следующих загрузочных сред:

| Платформа | Архитектуры | Результат |
| --- | --- | --- |
| Загрузочный сектор BIOS | i8086, x86-64 (реальный режим на старте) | 512-байтовый загрузочный сектор, загружаемый по адресу `0x7C00` |
| Multiboot | x86-64 | Образ ядра с заголовком Multiboot |
| UEFI | x86-64, arm64, riscv64 | Приложение UEFI |
| Device Tree | arm64, riscv32, riscv64 | Образ ядра, получающий Device Tree blob |

**os.boot.entry** — Пакет каждой загрузочной платформы определяет точку входа ядра и передаваемую ему информацию (например, структуру загрузочной информации или Device Tree blob). Функция входа ядра ДОЛЖНА иметь сигнатуру, которую определяет пакет платформы.

**os.boot.bios** — Платформа загрузочного сектора BIOS предоставляется как цель `an/target/bios-boot`: архитектура i8086, формат `target.BootSector` ([13-targets](13-targets.ru.md)), профиль `core`, `OnPanic` останавливает процессор. Точка входа программы — `func main()` пакета `main`. Перед `main` код старта устанавливает `CS:IP` в `0000:7C00`, `DS`, `ES` и `SS` в `0`, а `SP` в `0x7C00`; номер загрузочного диска, который BIOS передаёт в `DL`, доступен через `bios.BootDrive()`. Возврат из `main` останавливает процессор. Программа, которая не помещается в 510 байт, — ошибка компиляции с разбивкой размера по пакетам (**target.memory.overflow**).

## 8. Операционная система на Anlang как платформа

**os.platform.new** — Операционная система, написанная на Anlang, становится платформой, когда предоставляет описание платформы ([13-targets](13-targets.ru.md)), ссылающееся на её таблицу системных вызовов. Программы для этой платформы выполняют системные вызовы через пакет таблицы; ядро и программы используют один и тот же пакет таблицы.

## 9. Инварианты ядра в контрактах (справочный раздел)

Контракты ([08-contracts](08-contracts.ru.md)) позволяют записать инварианты, которые в обычных ядрах держатся на дисциплине:

```go
func (s inout AddressSpace) Map(v VirtAddr, p PhysAddr, f PageFlags) {
    requires v.IsPageAligned() && p.IsPageAligned()
    requires !(f.User && kernel.Owns(p))
    ensures  s.Translate(v) == Some(p)
    ...
}
```

Это не полная формальная верификация уровня seL4.

## 10. Эффекты как возможности (справочный раздел)

Эффекты — это возможности (capabilities), проверяемые при компиляции; ту же модель используют seL4 и Zircon. Драйвер может использовать только те порты, области памяти и прерывания, эффекты которых ему разрешены. Микроядро повторяет ту же проверку во время выполнения.

Ядра разного масштаба, на которые рассчитаны описанные средства:

| Вид | Цель | Пример |
| --- | --- | --- |
| DOS-подобная система | i8086, реальный режим | Однозадачная система с файловой системой FAT |
| RTOS | Cortex-M, RISC-V 32 | Планировщик с приоритетами уровня FreeRTOS или Zephyr |
| Микроядро | x86-64, riscv64, arm64 | Драйверы в пространстве пользователя, IPC на возможностях |
| Unikernel | x86-64 в виртуальной машине | Приложение и минимальное ядро в одном образе |

## Открытые вопросы


1. **Имена и API типов потока ядра, данных на процессор и спин-блокировки.** Отложено до реализации — шаг 54. Они лежат в `an/sched`, `an/kernel` и `an/sync`; точные имена фиксируются в [18-stdlib](18-stdlib.ru.md) на этом шаге.
2. **Память программы, передаваемая в системные вызовы.** Отложено до реализации — шаг 54. Сгенерированный код диспетчеризации проверяет, что каждый срез-аргумент лежит в адресном пространстве вызывающего; получает ли реализация ядра такие аргументы как `Untrusted` ([11-data-safety](11-data-safety.ru.md)), решается на этом шаге.
