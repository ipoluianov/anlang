# 20. Инструментарий

Вся работа с Kern идёт через одну команду `kern`, как в Go. Этот файл задаёт проекты, файлы, которые читает инструментарий (`kern.mod`, `REQUIREMENTS`), команды, сборку, тесты, эмуляторы, отладку, документацию, `kern port` и `kern diff`.

## 20.1 Общие требования

**tool.single-command** — Каждая операция из этого файла ДОЛЖНА быть доступна как подкоманда единого исполняемого файла `kern`.

**tool.net.none** — Команда `kern` НЕ ДОЛЖНА обращаться к сети. Все входные данные — каталог проекта, стандартная библиотека и файлы, указанные в командной строке.

**Примечание** — Пакетного менеджера, внешних источников пакетов и метаданных зависимостей нет. Чужой код копируется в проект и становится кодом проекта (см. [03-declarations](03-declarations.ru.md)).

**tool.output.json** — Каждая команда ДОЛЖНА поддерживать флаг `-json`. С ним команда ДОЛЖНА выводить в стандартный вывод один машиночитаемый результат в JSON, схема которого публикуется вместе со спецификацией (см. [21-protocol](21-protocol.ru.md)). Без флага команда выводит текст для человека.

**tool.output.diagnostics** — Команды, сообщающие о проблемах в исходном коде, ДОЛЖНЫ сообщать о них диагностиками в смысле [21-protocol](21-protocol.ru.md), **proto.diag.shape**; каждая диагностика называет идентификатор нарушенного правила.

**tool.exit-status** — Команда ДОЛЖНА завершаться с кодом 0 при успехе, 1 — если она отработала, но нашла проблемы (ошибки компиляции, падающие тесты, невыполненные проверки), и 2 — при неверном использовании или внутренней ошибке.

## 20.2 Проекты

**tool.project.root** — Проект — каталог, содержащий файл `kern.mod`. Команда, запущенная внутри проекта, ДОЛЖНА считать корнем проекта ближайший каталог-предок (включая текущий), в котором есть `kern.mod`.

**tool.project.package** — Пакет — каталог внутри корня проекта, содержащий хотя бы один файл `.kn`. Его путь импорта — имя модуля, за которым следует путь каталога относительно корня проекта с разделителем `/` (см. [03-declarations](03-declarations.ru.md)). Сам корень проекта — пакет, путь импорта которого равен имени модуля.

**tool.project.reserved** — Каталог `out/` в корне проекта зарезервирован для результатов сборки и НЕ ДОЛЖЕН содержать пакетов.

### 20.2.1 Структура

*Справочный раздел.*

```
weather/
├── kern.mod
├── REQUIREMENTS
├── main.kn
├── server/
│   ├── server.kn
│   ├── server_linux.kn
│   └── server_test.kn
├── jsonparse/              // copied foreign library: an ordinary project package
├── internal/
└── out/                    // build outputs, one directory per target
```

## 20.3 kern.mod

`kern.mod` — строчный файл в стиле `go.mod`: одна директива на строку, комментарии `//` до конца строки.

### 20.3.1 Грамматика

*(new)*

```
KernModFile      = { newline } { Directive { newline } } .
Directive        = ModuleDirective | EditionDirective | TargetsDirective | EffectsDirective | GenerateDirective .

ModuleDirective  = "module" ModuleName newline .
ModuleName       = ascii_lower { ascii_lower | decimal_digit | "_" } .

EditionDirective = "kern" Edition newline .
Edition          = decimal_digits "." decimal_digits .

TargetsDirective = "targets" TargetName { "," TargetName } newline .
TargetName       = ascii_lower { ascii_lower | decimal_digit | "-" | "_" } .

EffectsDirective = "effects" "(" newline { EffectRule } ")" newline .
EffectRule       = PackagePattern ( "allow" | "deny" ) EffectSet newline .
PackagePattern   = "..." | PackageDir [ "/..." ] .
PackageDir       = path_element { "/" path_element } .
path_element     = ascii_lower { ascii_lower | decimal_digit | "_" } .
EffectSet        = "{" [ EffectName { "," EffectName } ] "}" .
EffectName       = identifier .

GenerateDirective = "generate" GeneratorPath InputPattern { InputPattern } "->" OutputPath newline .
GeneratorPath    = ImportPath .
InputPattern     = PackageDir [ "/" FilePattern ] | FilePattern .
FilePattern      = { path_char | "*" } .
OutputPath       = ImportPath .

ascii_lower      = "a" … "z" .
```

Лексемы разделяются пробелами или табуляциями; `newline` — перевод строки. `decimal_digit`, `decimal_digits` и `identifier` — как в спецификации Go.

### 20.3.2 Правила

**tool.mod.module** — `kern.mod` ДОЛЖЕН содержать ровно одну директиву `module`. Имя модуля и элементы путей пакетов подчиняются **decl.import.module** и **decl.import.paths** ([03-declarations](03-declarations.ru.md)); в частности, имя НЕ ДОЛЖНО быть `kern`.

**tool.mod.edition** — `kern.mod` ДОЛЖЕН содержать ровно одну директиву `kern`. Она фиксирует редакцию языка для проекта (см. 20.8).

**tool.mod.targets** — `kern.mod` МОЖЕТ содержать одну директиву `targets`. Она перечисляет цели по умолчанию для `kern build`, `kern check` и `kern test`, когда флаг `-target` не указан. Каждое имя ДОЛЖНО разрешаться в описание цели (см. [13-targets](13-targets.ru.md)).

**tool.mod.effects** — `kern.mod` МОЖЕТ содержать одну директиву `effects`. Шаблоны и смысл правил `deny` и `allow`, включая приоритет при совпадении нескольких правил, заданы в [07-effects](07-effects.ru.md) (**eff.mod.pattern**, **eff.mod.deny**, **eff.mod.allow**, **eff.mod.precedence**).

**tool.mod.effects.names** — Каждое имя эффекта в `kern.mod` ДОЛЖНО называть эффект, известный в программе: встроенный эффект, эффект из описания устройства цели или эффект, объявленный через `effect.Declare` (см. [07-effects](07-effects.ru.md)).

**tool.mod.generate** — `kern.mod` МОЖЕТ содержать любое число директив `generate`. Каждая объявляет генератор ([10-compile-time](10-compile-time.ru.md), §10.8): пакет генератора (пакет `main` проекта), его входные файлы в виде шаблонов относительно корня проекта и путь импорта выходного пакета, который ДОЛЖЕН лежать под именем модуля. Пример: `generate gen/svdgen boards/stm32/*.svd -> myprogram/device`.

**tool.mod.generate.unique** — Две директивы `generate` НЕ ДОЛЖНЫ называть один выходной пакет, а выходной пакет НЕ ДОЛЖЕН быть каталогом, существующим в проекте.

**tool.mod.format** — `kern fmt` ДОЛЖЕН форматировать канонически и `kern.mod`: директивы в порядке `module`, `kern`, `targets`, `effects`, `generate`; правила эффектов отсортированы по шаблону; имена эффектов отсортированы; директивы `generate` отсортированы по выходному пути.

### 20.3.3 Пример

*Справочный раздел.*

```
module  weather
kern    1.0
targets linux-x86_64, macos-arm64, web

effects (
    jsonparse/...  deny  {File, Network, Panic}
    kernel/...     allow {Privileged}
)
```

## 20.4 Выбор файлов

Выбор файлов задан в [03-declarations](03-declarations.ru.md) §3.4 (**decl.file.ext**, **decl.file.ignored**, **decl.file.suffix**, **decl.file.names**, **decl.file.profile**). Тестовые файлы (`_test.kn`) включаются только при сборке тестов: командой `kern test` и операцией `test` протокола ([21-protocol](21-protocol.ru.md)).

**Примечание** — Ограничения на импорт пакетов команд архитектур (`kern/arch/<архитектура>` только в файлах с соответствующим суффиксом) заданы в [13-targets](13-targets.ru.md).

## 20.5 REQUIREMENTS

`REQUIREMENTS` — необязательный строчный файл в корне проекта. В нём лежат тексты требований и тесты, которые проверяют каждое требование. Текст свободный, пишется для людей и МОЖЕТ быть на любом языке.

### 20.5.1 Грамматика

*(new)*

```
RequirementsFile = { BlankOrComment } { Requirement { BlankOrComment } } .
Requirement      = RequirementID spaces Text newline { indent Text newline } indent TestsLine newline .
RequirementID    = ascii_upper { ascii_upper | decimal_digit } "-" decimal_digit { decimal_digit } .
TestsLine        = "tests:" spaces TestRef { "," [ spaces ] TestRef } .
TestRef          = [ PackageDir "." ] TestName .
TestName         = "Test" { letter | unicode_digit } .
Text             = { unicode_char } .
BlankOrComment   = [ spaces ] [ "//" Text ] newline .
indent           = spaces .
spaces           = ( " " | "\t" ) { " " | "\t" } .

ascii_upper      = "A" … "Z" .
```

### 20.5.2 Правила

**tool.req.unique** — Идентификаторы требований ДОЛЖНЫ быть уникальны в пределах файла.

**tool.req.has-tests** — Каждое требование ДОЛЖНО перечислять хотя бы один тест.

**tool.req.test-exists** — Каждая ссылка на тест ДОЛЖНА называть существующую тестовую функцию: функцию в файле `_test.kn`, имя которой начинается с `Test`, с сигнатурой `func(t inout testing.T)`. Ссылка без каталога пакета ДОЛЖНА соответствовать ровно одной тестовой функции в проекте.

**tool.req.test-passes** — Когда `kern test` запускает все тесты проекта, каждый тест, на который ссылается требование, ДОЛЖЕН проходить.

**tool.req.check** — `kern test` ДОЛЖЕН проверять **tool.req.unique**, **tool.req.has-tests** и **tool.req.test-exists** при каждом запуске, а **tool.req.test-passes** — когда запускает все тесты проекта. Нарушение ДОЛЖНО сообщаться диагностикой с названием требования и ДОЛЖНО приводить к неуспеху `kern test`.

**Примечание** — Код, не покрытый ни одним требованием, допустим, и о нём не сообщается.

### 20.5.3 Пример

*Справочный раздел.*

```
// REQUIREMENTS
AUTH-3  The user logs in with a login and a password
        tests: TestLoginSuccess, TestLoginWrongPassword
AUTH-4  After five failed attempts, login is locked for 15 minutes
        tests: auth.TestLockAfterFiveFailures, auth.TestUnlockAfter15Minutes
```

## 20.6 Команды

**tool.cmd.set** — `kern` ДОЛЖЕН предоставлять следующие команды.

| Команда | Назначение |
| --- | --- |
| `kern build [-target T[,T…]] [-verify]` | Сборка программы для одной или нескольких целей |
| `kern check [-target T[,T…]]` | Проверка типов, эффектов и контрактов без генерации кода |
| `kern fmt [-check] [пути]` | Каноническое форматирование |
| `kern test [-target T] [-emu E] [пакеты]` | Модульные, property-based и визуальные тесты; проверка требований |
| `kern run [-target T] [-emu E] [-record F]` | Сборка и запуск на машине разработчика или в эмуляторе |
| `kern flash [-target T] [-probe P]` | Запись прошивки в устройство через SWD/JTAG или UF2 |
| `kern size [-target T]` | Flash, RAM и стек по пакетам |
| `kern query <запрос>` | Запросы к семантическому API |
| `kern diff <старое> <новое>` | Семантический дифф двух версий кода |
| `kern debug [-target T] [-emu E] [-probe P] [-replay F]` | Отладка на машине разработчика, в эмуляторе или на устройстве |
| `kern doc [-html] [пакеты]` | Документация |
| `kern dev [-target T]` | Запуск с горячей перезагрузкой |
| `kern port -from go\|c <источник> <назначение>` | Перенос кода с Go или C |
| `kern gen -show <пакет>` | Вывести исходный код сгенерированного пакета |
| `kern serve` | Сервер протокола среды (см. [21-protocol](21-protocol.ru.md)) |
| `kern lsp` | Сервер Language Server Protocol (см. [21-protocol](21-protocol.ru.md)) |

**tool.cmd.build** — `kern build` ДОЛЖЕН проверить программу (как `kern check`) и при отсутствии ошибок записать результаты для каждой цели в `out/<цель>/`. Если `-target` не указан, используются цели из директивы `targets`; если её нет — цель машины разработчика.

**tool.cmd.build.multi** — При нескольких целях проверки, не зависящие от цели (типы, эффекты без подстановки цели, контракты), ДОЛЖНЫ выполняться один раз, а зависящие от цели шаги — по разу на цель.

**tool.cmd.check** — `kern check` ДОЛЖЕН выполнять все проверки `kern build`, предшествующие генерации кода, включая проверку эффектов против каждой выбранной цели, и НЕ ДОЛЖЕН записывать результаты.

**tool.cmd.fmt** — `kern fmt` ДОЛЖЕН переписывать каждый исходный файл Kern и `kern.mod` в каноническом форматировании (см. [01-lexical](01-lexical.ru.md)). С флагом `-check` он НЕ ДОЛЖЕН изменять файлы и ДОЛЖЕН завершаться неуспехом, если какой-либо файл отформатирован не канонически. Форматирование ДОЛЖНО быть идемпотентным.

**tool.cmd.size** — `kern size` ДОЛЖЕН сообщать для каждого пакета его вклад во flash (код и константные данные) и RAM (статические данные), а для `main`, каждой задачи и каждого обработчика прерывания — вычисленную максимальную глубину стека или то, что понадобился резерв (см. [19-runtime](19-runtime.ru.md), **rt.stack.report**).

**tool.cmd.query** — `kern query` ДОЛЖЕН отвечать на запросы семантического API: кто вызывает функцию; какие эффекты достижимы из точки и какая цепочка вызовов вносит каждый; что сломается при изменении типа или функции; какое условие контракта не доказано и почему. Те же запросы доступны как операция `query` протокола (см. [21-protocol](21-protocol.ru.md)).

**tool.cmd.gen** — `kern gen -show <package>` ДОЛЖЕН запустить генератор указанного выходного пакета, если его результат в кэше устарел, и вывести сгенерированные исходные файлы в каноническом форматировании. Без `-show` `kern gen` ДОЛЖЕН обновить все сгенерированные пакеты в кэше сборки, не собирая программу.

**tool.cmd.flash** — `kern flash` ДОЛЖЕН сначала собрать цель так же, как `kern build`, а затем записать образ цели `core` в устройство через отладочный адаптер (SWD или JTAG) или, для целей с форматом UF2, записью файла UF2.

## 20.7 Сборка

**tool.build.offline** — Сборка ДОЛЖНА использовать только проект, стандартную библиотеку и инструментарий. См. также **tool.net.none**.

**tool.build.reproducible** — При одинаковых исходниках проекта, одинаковой версии `kern` и одинаковой цели `kern build` ДОЛЖЕН давать побайтово одинаковые результаты независимо от времени, абсолютного пути проекта, машины и переменных окружения.

**tool.build.no-stamps** — Результаты НЕ ДОЛЖНЫ содержать меток времени и путей файловой системы машины, на которой шла сборка.

**tool.build.verify** — `kern build -verify` ДОЛЖЕН собрать каждую цель дважды, с нуля и независимо от кэша сборки, и завершиться неуспехом, если результаты различаются хотя бы в одном байте.

**tool.build.outputs** — Результаты для цели ДОЛЖНЫ записываться только в `out/<цель>/`. Набор и имена файлов задаются форматами бинарников цели (см. [13-targets](13-targets.ru.md)) и отдельной отладочной таблицей (см. 20.11).

**Примечание** — Кэширование результатов сборки описано в [22-compiler](22-compiler.ru.md); кэш никогда не меняет результат (**impl.cache.transparent**).

## 20.8 Редакции

**tool.edition.fixed** — Директива `kern` в `kern.mod` фиксирует редакцию. Компилятор ДОЛЖЕН применять правила этой редакции ко всему проекту.

**tool.edition.migrate** — Версия `kern`, поддерживающая более новую редакцию, ДОЛЖНА предоставлять автоматические миграции с каждой более старой поддерживаемой редакции. Миграции ДОЛЖНЫ применяться только по явному запросу (флаг `-edition` команды `kern fmt`), ДОЛЖНЫ обновлять директиву `kern` и ДОЛЖНЫ давать код, который компилируется в новой редакции.

**tool.edition.codes** — Идентификаторы правил в диагностиках ДОЛЖНЫ быть стабильны в пределах редакции (см. [21-protocol](21-protocol.ru.md), **proto.stability**).

## 20.9 Тестирование

**tool.test.files** — Тесты — функции с сигнатурой `func(t inout testing.T)`, имя которых начинается с `Test`, объявленные в файлах `_test.kn`, как в Go. Тип `testing.T` предоставляет пакет `kern/testing`.

**tool.test.examples** — Примеры кода в документирующих комментариях ДОЛЖНЫ компилироваться и исполняться как тесты при `kern test`. Пример с комментарием ожидаемого вывода ДОЛЖЕН выдавать этот вывод.

**tool.test.property** — `kern test` ДОЛЖЕН поддерживать property-based тесты: тест получает сгенерированные входные данные из `kern/testing` и при неудаче сообщает минимизированный контрпример. Генерация ДОЛЖНА быть детерминированной при заданном зерне, и зерно ДОЛЖНО сообщаться.

**tool.test.substitution** — В тестах источники эффектов `Clock` и `Random`, а также ввод-вывод ДОЛЖНЫ подменяться тестовыми реализациями. Поскольку эффекты выводятся, компилятор знает, какой код от них зависит; подмена НЕ ДОЛЖНА требовать изменений в тестируемом коде.

**tool.test.scheduler** — Тесты, запускающие задачи, ДОЛЖНЫ иметь возможность выполняться под детерминированным планировщиком, который перебирает чередования задач для поиска взаимоблокировок и ошибок порядка (см. [09-concurrency](09-concurrency.ru.md)). Неудача ДОЛЖНА сообщаться вместе с воспроизводящим её чередованием.

**tool.test.visual** — Тест МОЖЕТ отрисовать компонент интерфейса и сравнить изображение с эталонным, хранящимся в проекте. При несовпадении `kern test` ДОЛЖЕН завершаться неуспехом и записывать в `out/` фактическое изображение и изображение разницы.

**tool.test.emu** — С флагами `-target` и `-emu` команда `kern test` ДОЛЖНА выполнять тесты для цели во встроенном эмуляторе (см. 20.10).

**tool.test.requirements** — `kern test` ДОЛЖЕН выполнять проверки требований из 20.5.

## 20.10 Эмуляторы

**tool.emu.builtin** — Эмуляторы для тестов ДОЛЖНЫ быть встроены в `kern` и НЕ ДОЛЖНЫ требовать сторонних программ.

**tool.emu.generated** — Интерпретатор каждой архитектуры ДОЛЖЕН генерироваться из формальной семантики команд в её описании архитектуры — того же описания, из которого строятся бэкенд, ассемблер и пакет команд архитектуры (см. [13-targets](13-targets.ru.md)).

**tool.emu.coverage** — `kern` ДОЛЖЕН предоставлять как минимум:

| Цель | Встроенная эмуляция |
| --- | --- |
| 8086, Cortex-M, AVR, RISC-V | интерпретатор архитектуры плюс модели периферии: таймер, UART, GPIO, текстовая видеопамять, `int 21h` |
| `web` | интерпретатор WebAssembly; интерфейс отрисовывается рендером Kern в изображение, браузер не нужен |
| iOS, Android | логика и интерфейс проверяются на машине разработчика тем же рендером |

**tool.emu.observable** — Тесты в эмуляторе проверяют наблюдаемое поведение: изменения пинов и их тайминг, вывод UART, текст на экране DOS, отрисованные экраны. Эмулятор ДОЛЖЕН делать эти наблюдения доступными тестам через `kern/testing`.

**tool.emu.limits** — От встроенных эмуляторов не требуется точность до такта, полная модель периферии и проверка системной интеграции (камера, разрешения, поведение настоящего iOS). Документация каждого эмулятора ДОЛЖНА называть его ограничения. Внешние эмуляторы (DOSBox, QEMU, Renode), симуляторы Apple и Android и реальные устройства МОГУТ использоваться через `kern run` и `kern debug`, но `kern test` их никогда не требует.

## 20.11 Отладка

**tool.debug.formats** — Сборки для отладки ДОЛЖНЫ записывать отладочную информацию в формате цели:

| Цель | Отладочная информация | Отладчик |
| --- | --- | --- |
| Linux, macOS | DWARF | `kern debug`; GDB и LLDB через их удалённые протоколы |
| Windows | PDB / CodeView | то же |
| DOS | CodeView | через отладочный порт DOSBox |
| `web` | source maps, DWARF для WebAssembly | инструменты браузера |
| микроконтроллеры | DWARF + SVD | SWD/JTAG через `kern debug -probe` |

**tool.debug.side-table** — На каждой цели, включая `core`, сборка ДОЛЖНА создавать отдельную таблицу в отдельном файле в `out/<цель>/`, сопоставляющую адреса кода функциям, файлам и строкам. Эта таблица НЕ ДОЛЖНА входить в образ программы.

**tool.debug.values** — Отладчик ДОЛЖЕН показывать значения типов Kern в терминах Kern: `enum` — с вариантом и полями, `Option` — как `None` или `Some`, типы синхронизации — как дескрипторы. Значение `Secret` ДОЛЖНО показываться как `***`.

**tool.debug.record** — `kern run -record F` ДОЛЖЕН записывать в файл `F` все недетерминированные входы выполнения (часы, случайность, ввод-вывод, чередование задач). `kern debug -replay F` ДОЛЖЕН точно воспроизводить выполнение.

**tool.debug.protocol** — Отладчик ДОЛЖЕН быть доступен через операцию `debug` протокола среды: точки останова, пошаговое выполнение, чтение состояния (см. [21-protocol](21-protocol.ru.md)).

## 20.12 Горячая перезагрузка

**tool.dev.hot-reload** — `kern dev` ДОЛЖЕН запускать программу профиля `ui` и применять изменения её функций `View` и `Update` без перезапуска с сохранением состояния. Если изменился тип `State`, `kern dev` ДОЛЖЕН предложить функцию миграции или перезапуск. Механизмы для разных целей заданы в [17-ui](17-ui.ru.md).

**tool.dev.release** — Горячая перезагрузка НЕ ДОЛЖНА быть доступна в выпускных сборках (см. [19-runtime](19-runtime.ru.md), **rt.dev.only**).

## 20.13 Документация

**tool.doc.content** — `kern doc` ДОЛЖЕН генерировать документацию из исходников: для каждого экспортируемого объявления — сигнатуру, выведенные эффекты (включая параметрические ссылки, см. [07-effects](07-effects.ru.md)), контракты, документирующий комментарий и примеры.

**tool.doc.formats** — `kern doc` ДОЛЖЕН выдавать HTML с флагом `-html` и JSON с флагом `-json`. Форма JSON предназначена для ИИ-инструментов и несёт ту же информацию.

**tool.doc.examples** — Примеры в документации — исполняемые тесты (**tool.test.examples**).

## 20.14 kern port

`kern port` переводит код с Go или C на Kern. Перевод выполняет ИИ-модель, компилятор проверяет результат, а тесты исходного проекта прогоняются на обеих версиях.

**tool.port.check** — Результат `kern port` ДОЛЖЕН проверяться компилятором. `kern port` ДОЛЖЕН сообщать каждую диагностику перенесённого кода.

**tool.port.tests** — Если у исходного проекта есть тесты, `kern port` ДОЛЖЕН перенести их, запустить на исходной и на перенесённой версиях и сообщить о каждом тесте, результат которого различается.

**tool.port.go.auto** — При переносе с Go `kern port` ДОЛЖЕН автоматически переводить: синтаксис, структуры, интерфейсы, горутины и каналы, обработку ошибок, а также пути импорта стандартной библиотеки Go (`"fmt"` → `"kern/fmt"`) и переносимого проекта (`"example.com/x/y"` → `"<модуль>/y"`).

**tool.port.go.decide** — При переносе с Go `kern port` ДОЛЖЕН отмечать как требующие решения: указатели и нулевые указатели, функции `init`, значения типа `interface{}` / `any` и изменяемые переменные уровня пакета (которые он МОЖЕТ обернуть в `sync.Mutex[T]` или перенести в структуру, см. [06-memory](06-memory.ru.md)).

**tool.port.c** — При переносе с C `kern port` ДОЛЖЕН переводить функции, структуры и арифметику и ДОЛЖЕН отмечать как требующие решения: ручное управление памятью, использование препроцессора и код, поведение которого в C не определено.

## 20.15 kern diff

**tool.diff.inputs** — `kern diff <старое> <новое>` сравнивает две версии кода: два каталога или два набора пакетов одного проекта в двух состояниях файловой системы.

**tool.diff.content** — Результат ДОЛЖЕН перечислять по пакетам:

- добавленные, удалённые и изменённые экспортируемые объявления со старыми и новыми сигнатурами;
- функции, у которых изменилась реализация при неизменной сигнатуре;
- изменения выведенных эффектов каждой функции, включая новые параметрические ссылки;
- изменения контрактов: ослабленные или усиленные `requires` и `ensures`;
- изменения объявлений внешних функций (`ffi`), включая их объявленные эффекты, — отдельным списком, потому что компилятор не может их проверить (см. [12-ffi](12-ffi.ru.md)).

**tool.diff.effects-highlight** — Новый эффект экспортируемой функции ДОЛЖЕН заметно выделяться в выводе для человека.

### 20.15.1 Пример

*Справочный раздел.*

```
kern diff old/ new/

jsonparse

API:
  + func DecodeStream(r io.Reader) (Value, error)
  ~ func Parse(s string) (Value, error)        implementation changed

Effects:
  ! Parse: {} → {Network}                    NEW EFFECT
```
