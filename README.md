# Anlang

Anlang (short: an) is a programming language and development environment where intent, behavior and the proof that they match are written side by side and checked by the machine. Site: [anlang.dev](https://anlang.dev).

Source files have the extension `.an`, the standard library lives under `an/...`, the command is `anlang` and a project is described by `anlang.mod`.

- [spec/](spec/) — the specification (English, with Russian translations).
- [examples/](examples/) — example programs.
- `anlang.md` — the original design document (Russian).

## Status

- **Step 1 of the roadmap is done:** the lexer and parser accept the whole Anlang grammar (Go plus the novelty inventory), and `anlang fmt` prints the canonical form. Both are checked against the Go sources: all 6230 `.go` files of the Go 1.25 distribution parse and are formatted byte for byte as `gofmt` formats them, and formatting is fuzzed for idempotence and preservation of the syntax tree.
- **Step 2 is done:** the type checker covers the Go subset: the numeric and string types of Anlang, constants with exact untyped arithmetic, arrays, slices, maps, channels, structs with embedded fields, function types, function literals (closures, with captured variables read-only in them), methods, interfaces with embedding, type assertions and type switches, generic functions and types with constraints, type sets and type inference, project packages imported by the program (checked in dependency order, with exported names, `internal` and import cycles), declarations at package and function level, expressions, conversions, built-in functions and all statements. It is checked against Go: the test programs of the Go distribution are renamed into Anlang (`int8` → `i8` and so on) and the checker must accept or reject each one as go/types does; of 2965 files, 1926 fall into the supported subset and all but one known case agree. Other constructs are reported as not supported yet, with the roadmap step that adds them ([spec/24-roadmap.md](spec/24-roadmap.md)).
- **Step 3 is done:** `enum` types with variants and fields, generic enums and the predeclared `Option` with `None`, `Some` and `Get`; variant values, constructors and literals with type inference; variant switches with patterns and bindings, exhaustiveness (adding a variant breaks every switch without `default`), duplicates and terminating switches; types without a zero value and every operation that would produce one implicitly; the inferred constraint "requires a zero value" of type parameters, propagated through generic calls and reported at the instantiation with the chain to the operation.
- **Step 4 is done:** `inout` parameters and receivers, function types with `inout` parameters; `inout` arguments must be addressable operands of the parameter's type, and the `inout` accesses of one call must not overlap (paths compared by fields, constant indices and constant subranges until the solver proves more); methods with `inout` receivers are called only directly on addressable operands; function literals capture `inout` variables by reference and are then second-class: they may only be called directly; iterators yielding `inout` access, with the loop holding the iterator's operand while the body runs.
- **Step 5 is done:** `nil` safety by flow analysis over access paths: a method of an interface operand is selected, or a function value is called, only where the operand is proven non-nil — by a conversion, a function literal or named function, a check `x != nil` (also in `&&`, `||` and early returns) or a type switch case, invalidated by assignments and `inout` accesses; parameters of function type are non-nil in their function, and the caller proves the arguments for them non-nil.
- **Step 6 is done:** the checked program is translated into a shared SSA intermediate representation with storage cells for variables, explicit copies for value semantics and monomorphized generics ([spec/22-compiler.md](spec/22-compiler.md), 22.10); `anlang build -ir` prints it in the textual format and `anlang run -emu ir` runs it in the IR interpreter, which implements copy-on-write, checked arithmetic and the run-time checks of the language. Reference programs with expected output (`conformance/testdata/*/<name>.out`) run in the interpreter. It is checked against Go: of the "run" test programs of the Go distribution, 135 fall into the supported subset; 129 print exactly what Go prints, and the other 6 differ only by deviations of Anlang (integer overflow panics, value semantics of maps, copy capture, empty slices equal to `nil`). Channels, `go` and `select` wait for step 30.
- **Step 7 is done:** checked integer arithmetic panics on overflow (including `min / -1` and `min % -1`), float-to-integer conversions panic out of range, and index and slice bounds are checked with Go's panic messages; package `an/wrap` provides the wrapping types `wrap.U8` … `wrap.I64` (arithmetic modulo 2ⁿ, constants included, no mixing with other integer types) and `an/bits` the functions `Wrapping*`, `Saturating*` and `Checked*` for `Add`, `Sub` and `Mul`. An arithmetic oracle checks every integer type and operator on boundary and random operands against Go and exact arithmetic, and a bounds oracle runs the same index and slice expressions on Go values.
- **Step 8 is done:** effect inference (package `effects`): per-package summaries with concrete effects, parametric references to parameters and type parameters and open references to interface methods and function types; static calls substitute arguments and type arguments, conversions to interfaces and function values record implementations, and whole-program substitution resolves open references into execution effects. Package `an/effect` provides the base effects, `effect.Declare`, `effect.Mark` and `effect.Defer`. `anlang query effects [symbol]` prints the summaries with the call chain to each source. Package results are cached by the hash of the package and its imports; a test checks that recomputation after a change matches a full recomputation.
- **Step 9 is done:** effect constraints at boundaries: the profiles `core`, `app` and `ui` of each package and the rule that a package imports only packages with the same or a stricter profile; the `effects` directive of `anlang.mod` with `deny` and `allow` rules and their precedence; `ensures effect.Without(...)`, checked at the declaration and at every call with the effects of the arguments; the environment effects of the target (from the target descriptions shown in the specification until steps 11 and 13). Each violation names the constraint, the effect and the call chain to its source.
- **Step 10 is done:** compile-time evaluation: constants computed by function calls and composite literals, of any constant type (arrays, slices, maps, structs, enums), evaluated in the IR interpreter with the integer sizes of the target and fixed step and memory limits, after a check that the initializer has only evaluable effects; the CRC table of the specification equals Go's `crc32.IEEETable`. `...any` parameters are compile-time tuples: functions and methods with them, and generic functions using `an/meta`, are checked and compiled per instance; `for const` loops are unrolled over tuples, integer constants, constant arrays and `an/meta` sequences; type switches on tuple elements and type parameters are resolved statically; `an/meta` provides `Name`, `Fields`, `Variants` and `Reject` with field and variant descriptors. `fmt.Printf` and `fmt.Sprintf` check their format at compile time and format as Go does (compared with Go on 14 000 directives). Until roadmap step 20, narrowing conversions are proven from a fixed set of interval facts. Calls of templates of other packages wait for step 29.
- **Step 11 is done:** architecture descriptions are Anlang data: package `an/arch` (the first standard library package compiled from Anlang sources, embedded in `anlang` from `lib/`) declares the schema, and `arch.I8086` describes the 8086 with its registers, operand kinds, the ModRM byte as a fragment with 25 alternatives, prefixes and 228 instruction forms, each with a bit-pattern encoding, Sail-like semantics over bit vectors and a cycle count ([spec/13-targets.md](spec/13-targets.md), 13.5.3–13.5.5). Package `arch/desc` evaluates the description at compile time, parses and checks its encodings and the widths of its semantics, and decodes instructions; a test checks that every documented 8086 opcode and every reg value of the opcode groups decodes to exactly one instruction form.
- **Step 12 is done:** from the description, package `arch/desc` derives an interpreter that executes the semantics on a machine state, an assembler and a disassembler (every encoding round-trips through its text), and the instruction package `an/arch/i8086` (functions such as `i8086.Int(0x21, i8086.Regs{AX: 0x0900})`, importable only from files with the suffix `_i8086`). The interpreter agrees with the [SingleStepTests 8086 processor test suite](https://github.com/SingleStepTests/8086), recorded on a real Intel 8086, on all 558,000 tests of the documented instructions; the description models the 8086's own behavior, such as `IDIV` quotients of -127 to 127, the REP prefix negating them, and words wrapping within a segment. `scripts/fetch-8086-tests.sh` downloads the suite (MIT license) into `external/`, which is not committed; `go test` runs a tenth of it, `ANLANG_8086_ALL=1` all. On random instructions it also agrees with QEMU: a boot image assembled with the derived assembler sets the registers, executes each instruction and writes the registers to the debug port, and QEMU and the interpreter must write the same, apart from the flags the 8086 leaves undefined (5,037 instructions; the test leaves out what differs between the 8086 and later processors). `scripts/fetch-qemu.sh` downloads QEMU into `external/`; without it the test is skipped.
- **Step 13 is done:** targets are Anlang data too: `an/platform` describes the `dos` platform (its effects, profiles, formats and its operations `start`, `exit` and `write` as rules) and `an/target/dos-com` the target, which the toolchain reads instead of built-in tables; the `main` package must have a profile the platform allows. The code generator (package `codegen`) contains nothing about the 8086: it lays out values and frames, expresses the IR as machine operations (`add.s` of 16 bits, `load`, `branch`, `call`, …) and replaces each by the instruction template of a rule of the architecture description; `arch.I8086` has 128 rules, and operations without a rule, such as 64-bit division, call the runtime package `an/runtime`, written in Anlang ([spec/22-compiler.md](spec/22-compiler.md), 22.11). Every data rule is checked against the formal semantics in the generated interpreter, exhaustively for 8-bit operands. `anlang build` writes a DOS `.COM` file for `dos-com`, and `anlang run` runs it in the built-in emulator: the 8086 interpreter with a model of `int 20h` and `int 21h`; the interpreter now compiles the semantics into closures and caches decoded instructions. Twelve reference programs in the `core` profile (integers of all widths, control flow, arrays, strings, enums, generics, interfaces, iterators, deferred calls and panics) give the same output in the emulator as in the IR interpreter. Floating point, `fmt.Printf` and `asm` follow in steps 14–15.
- **Step 14 is done:** the DOS emulator models the text screen at `B800:0000` (written by `int 10h` and by the console output of DOS), the keyboard (`int 16h` and the input functions of `int 21h`, fed from standard input), the timer (`int 1Ah`, the time of day from the executed cycles) and more functions of `int 21h`; `anlang run -screen` shows the screen. Packages `an/dos` and `an/bios` wrap these services in Anlang over the instruction package: calls such as `i8086.Int(0x21, i8086.Regs{AX: 0x0900, DX: …})` compile to the instruction with the registers moved by rules, and `asm` statements with input and output registers and local labels compile too. Package `an/unsafe` provides pointer kinds, `unsafe.Data` and hardware mappings, package-level variables bound by `unsafe.Map` to memory such as the video memory at a far address; `encoding.CP866` converts constant text at compile time, and `dstring` constants get their `$`. The examples [hello-dos](examples/hello-dos) and [video-dos](examples/video-dos) run in the emulator, and tests check the screen, the keyboard and the timer through expected `.screen`, `.in` and `.out` files. `fmt.Printf` compiles for the 8086 with its common directives.
- **A walking skeleton:** `anlang build` compiles `examples/hello` into a static Linux x86-64 executable without external tools. Until the backend of step 26, code generation covers functions without parameters or results that call each other and `fmt.Print` / `fmt.Println` with constant arguments.

## Build and run

Requires Go 1.25.

```
go build -o anlang ./cmd/anlang
cd examples/hello
../../anlang run
```

`anlang build -target linux-x86_64` writes the executable to `out/linux-x86_64/`, and `anlang build -target dos-com` a DOS `.COM` file to `out/dos-com/`; `anlang run` runs a program for a target that cannot run on this machine, such as `dos-com`, in the built-in emulator. `anlang run -emu ir` runs the program in the IR interpreter, and `anlang build -ir` prints its IR. `anlang fmt` rewrites the project's files in canonical form; `anlang build` rejects files that are not.

## Layout

| Package | Content |
| --- | --- |
| `cmd/anlang` | the `anlang` command |
| `build` | project loading, file selection, build driver |
| `modfile` | `anlang.mod` parser |
| `syntax` | lexer, parser and syntax tree |
| `format` | canonical formatting (`anlang fmt`), based on go/printer |
| `types` | type checker |
| `effects` | effect inference: package summaries and whole-program substitution |
| `ct` | compile-time evaluation of computed constants |
| `lower` | translation of the checked program to IR |
| `ir` | intermediate representation and its textual format |
| `interp` | IR interpreter (`anlang run -emu ir`) |
| `arch/desc` | architecture descriptions: checking, decoding, the generated interpreter, assembler, disassembler and instruction packages |
| `codegen` | the code generator of all architectures, driven by instruction selection rules, and the linker |
| `emu/dos` | the built-in emulator of the `dos` targets: the 8086 interpreter with a model of DOS |
| `arch/x86_64` | x86-64 code generation and the Linux runtime routines |
| `lib` | the Anlang sources of the standard library packages that are not built into the compiler (`lib/an/...`): architecture, platform and target descriptions, the runtime package |
| `link/elf` | ELF writer |
| `conformance` | the conformance suite (`conformance/testdata/<rule>/`, spec/23-conformance.md, **conf.suite.layout**) and checks that tie the code to the specification |

Tests: `go test ./...` (add `-short` to skip the corpus tests over the Go sources). Rules without conformance tests: `go test ./conformance -run Coverage -v`. The comparisons with Go (`TestGoOracle` for the checker, `TestGoRunOracle` for the output of programs in the IR interpreter) read the Go sources in `GOROOT`; `TestArithmeticOracle` and `TestBoundsOracle` compare integer arithmetic and bounds checks with Go. Fuzzing: `go test ./format -run '^$' -fuzz FuzzFormat`.
