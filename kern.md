# Kern — дизайн среды разработки

Oct 25, 2026 · @Ivan

## 1. Назначение и принципы

Kern — среда разработки, в которой намерение, поведение и доказательство их соответствия записаны рядом и проверяются машиной. Один язык и один инструментарий покрывают диапазон от .COM-программ для MS-DOS и прошивок микроконтроллеров до интерактивных веб-страниц.

Среда рассчитана на связку «ИИ пишет — машина проверяет — человек проверяет результат». Для ИИ подробность дешева, а неоднозначность дорога; для человека код должен оставаться читаемым и проверяемым.

Название — **Kern**; для поиска, домена и тегов — **kernlang** (как golang для Go). Исходные файлы имеют расширение `.kn`.

### Принципы

1. **Проверяемость важнее краткости.** Ошибку должно быть невозможно не заметить: контракты, эффекты и типы ловят правдоподобные, но неверные решения.
2. **Локальность рассуждений.** Всё, что нужно для понимания функции, видно из её сигнатуры и тела, а эффекты выводит компилятор и показывают инструменты. Глобальное состояние строго ограничено (раздел 4); нет неявных преобразований, `init()` и магии на расстоянии.
3. **Один канонический способ записи.** Минимум синтаксического сахара, обязательное каноническое форматирование.
4. **Знакомый синтаксис, новая семантика.** Синтаксис близок к Go; новизна — в эффектах, контрактах, модели памяти и инструментах.
5. **Бюджет новизны.** Всё новое относительно Go перечислено в закрытом перечне (раздел 3): три ключевых слова, контекстные слова и несколько конструкций. Новая строка в перечне требует такого же обоснования, как новое ключевое слово.
6. **Детерминизм по умолчанию.** Воспроизводимые сборки, отсутствие гонок данных по построению, полностью офлайн-сборка.
7. **Механика решает, суждение дополняет.** Решающие проверки (хэши, эффекты, контракты, тесты) выполняет инструмент; обзор ИИ — дополнительный уровень, а не арбитр.
8. **Всё, что описывает железо и окружение, — данные.** Цели, архитектуры и форматы бинарников описываются декларативно кодом на Kern: в стандартной библиотеке или в пакетах проекта.
9. **Независимость от сторонних сервисов.** Среда не полагается ни на какие внешние сервисы: реестры пакетов, прокси, облачные решатели, хостинги кода. Внешних зависимостей нет: весь код лежит в проекте и в стандартной библиотеке, поэтому сборка, проверка и тесты работают на одной машине без сети.

## 2. Обзор среды

Среда Kern состоит из пяти частей, связанных одной системой типов и эффектов: языка, компилятора, описаний целей, стандартной библиотеки и инструментов проверки.

```
 исходники .kn ─┐
 stdlib        ─┼─▶ разбор ─▶ типы и эффекты ─▶ контракты ─▶ общее SSA ─┬─▶ i8086   ─▶ .COM, MZ
 описание цели ─┘                                                       ├─▶ armv7m  ─▶ ELF, BIN, HEX, UF2
                                                                        ├─▶ x86-64, arm64 ─▶ ELF, PE, Mach-O
                                                                        └─▶ wasm32  ─▶ .wasm
```

Все цели проходят одни и те же проверки; различаются только последние шаги — лоуеринг и запись формата.

| Компонент | Что делает |
| --- | --- |
| Язык | Go-подобный синтаксис, эффекты, контракты, семантика значений, профили |
| Компилятор | Проверка типов, эффектов и контрактов; общее SSA-представление; бэкенды под архитектуры |
| Цели | Декларативные описания архитектур, платформ и форматов бинарников |
| Стандартная библиотека | Поставляется с `kern`; включает описания целей; внешних зависимостей нет (раздел 19) |
| Инструменты | Команда `kern`: сборка, тесты, эмуляторы, аудит, семантический диф |

## 3. Синтаксис

Синтаксис Kern — это Go с тремя новыми ключевыми словами. Всё остальное берётся из Go без изменений: `package`, `import`, `func`, `struct`, `interface`, `switch`, `for`, `defer`, `go`, дженерики, `gofmt`-подобное обязательное форматирование.

### Новые ключевые слова

| Слово | Назначение |
| --- | --- |
| `enum` | Суммарный тип с вариантами, несущими данные |
| `inout` | Изменяемый параметр или получатель метода без указателей |
| `profile` | Уровень языка для пакета |

Кроме трёх ключевых слов есть **контекстные слова**: они имеют смысл только в определённой позиции и остаются доступными как обычные имена. Это `requires`, `ensures` и `invariant` (контракты, распознаются по позиции в начале тела функции, цикла или структуры), `interrupt` и `trap` (обработчики, разделы 13 и 14), `gpu` (функция для GPU, раздел 12), `layout` (раскладка структуры, раздел 7). Внешние функции объявляются без новых слов (раздел 11).

### Перечень новизны

Бюджет новизны (принцип 5) — это закрытый перечень всего, что отличает синтаксис и семантику Kern от Go. Добавить строку в перечень — решение того же уровня, что новое ключевое слово, и оно записывается в таблицу принятых решений (раздел 27).

| Вид | Что |
| --- | --- |
| ключевые слова | `enum`, `inout`, `profile` |
| контекстные слова | `requires`, `ensures`, `invariant`, `interrupt`, `trap`, `gpu`, `layout` |
| синтаксические конструкции | `for const`; внешняя функция `func f(...) T = expr`; блок `asm`; шаблоны в `case` (`case Circle{r}:`); варианты в теле `enum` |
| семантика без нового синтаксиса | `nil` без разыменования; `inout`-переменная в range-over-func; `...any` как кортеж при компиляции; типы синхронизации как дескрипторы; `inout` в `go`; `const` от функций |
| известные компилятору типы с операторами | `simd`, `fixed`, `wrap` |

### Контракты

В Go фигурная скобка обязана стоять на одной строке с сигнатурой из-за автоматической вставки точек с запятой. Поэтому контракты — первые строки тела функции:

```go
func Clamp(x, lo, hi int) int {
    requires lo <= hi
    ensures  lo <= result && result <= hi

    if x < lo { return lo }
    if x > hi { return hi }
    return x
}
```

Контракты проверяются статически встроенным решателем (раздел 17). Если доказательство не найдено автоматически, компилятор сообщает, какое условие не доказано, и предлагает либо уточнить код, либо добавить промежуточное утверждение `assert`.

Внутри `ensures` доступно одно особое имя: `result` — возвращаемое значение. Ограничения, которые не являются постусловиями, записываются вызовом функции пакета, которую понимает компилятор: `effect.Without(...)` (раздел 5), `secret.ConstantTime()` (раздел 10), `wcet.Within(...)` — наихудшее время выполнения (раздел 13).

Контрактные слова позиционные: строка вида `requires <выражение>` в начале тела не может быть ничем иным, потому что идентификатор, за которым сразу идёт выражение, в Go-синтаксисе недопустим. Поэтому `requires`, `ensures` и `invariant` не зарезервированы и остаются доступными как имена. Отдельного блока `contract` нет: одна строка на условие, в плоском стиле Go.

`invariant` в начале тела цикла задаёт инвариант цикла, без которого решатель не может доказать свойства кода с циклами. В теле `struct` он задаёт инвариант типа.

**Инвариант цикла** записывается в начале тела, потому что в заголовке `for` места нет, но по смыслу это инвариант заголовка: он выполняется перед каждой проверкой условия цикла, включая последнюю. Для `for i := range xs` на выходе он подставляется с `i == len(xs)`. Решатель проверяет три вещи: инвариант верен до первой итерации, сохраняется одной итерацией, а вместе с условием выхода даёт то, что нужно после цикла.

**Инвариант типа** проверяется на границах, а не после каждого присваивания: после составного литерала, в конце каждой функции, получившей значение через `inout` (включая методы), и в каждой точке, где значение передаётся в другую функцию, возвращается, отправляется или сохраняется. Внутри функции временное нарушение допустимо: `r.lo = 5; r.hi = 10`. Поля с маленькой буквы снаружи пакета не изменить, поэтому контроль сосредоточен в пакете типа.

Если нулевое значение нарушает инвариант (например, `invariant lo < hi`), у типа нет нулевого значения: `var r T` и пропуск такого поля в литерале — ошибка компиляции.

```go
func Sum(xs []i32) i64 {
    ensures result == math.Sum(xs)

    var s i64
    for i := range xs {
        invariant s == math.Sum(xs[:i])
        s += i64(xs[i])
    }
    return s
}

type Range struct {
    invariant lo <= hi
    lo, hi int
}
```

### Суммарные типы и исчерпывающий switch

```go
type Shape enum {
    Circle{r f64}
    Rect{w, h f64}
}

func Area(s Shape) f64 {
    switch s {
    case Circle{r}:  return math.Pi * r * r
    case Rect{w, h}: return w * h
    }
}
```

`default` не требуется: компилятор проверяет, что разобраны все варианты. Добавление нового варианта ломает компиляцию во всех неполных `switch`.

### Ошибки

Ошибки обрабатываются так же, как в Go: ошибка — это значение, проверка — обычный `if err != nil`. Сокращённого синтаксиса (`try`, `?`) нет: явная проверка легко читается и не прячет точку выхода из функции. Единственное отличие от Go — неиспользованная ошибка является ошибкой компиляции. Отбросить её можно только явно, присвоив `_`: такое место видно при чтении и находится поиском.

```go
func LoadConfig(path string) (Config, error) {
    data, err := fs.ReadFile(path)
    if err != nil {
        return Config{}, err
    }

    cfg, err := config.Parse(data)
    if err != nil {
        return Config{}, fmt.Errorf("конфигурация %s: %w", path, err)
    }
    return cfg, nil
}
```

### nil без разыменования

В Kern `nil` — только литерал нулевого значения интерфейсов, срезов, словарей и каналов. Разыменовать его нельзя по построению:

1. **Указателей нет**, поэтому нет ни нулевых указателей, ни «типизированного `nil` в интерфейсе».
2. **Срез и словарь** со значением `nil` — обычные пустые значения: `len` даёт 0, `append` и запись в словарь работают. Канал со значением `nil`, как в Go, блокирует навсегда.
3. **Вызов метода у интерфейса** компилируется, только если доказано, что значение не пустое: обычно это проверка `if x != nil` или `if x == nil { return }` выше по потоку управления. Если доказать не удалось, это ошибка компиляции, а не паника.

Идиома ошибок Go (`if err != nil`, `return x, nil`) сохраняется без изменений.

### Отсутствие значения

У структур и чисел `nil` нет, потому что нет указателей. Отсутствие значения выражается как в Go:

1. **Результат функции — пара «значение, ok»**, как поиск в словаре: `func Find(...) (User, bool)`.
2. **Поле или элемент коллекции — `Option[T]`**: `parent Option[arena.Ref[Node]]`. Значение достаётся тем же способом: `p, ok := n.parent.Get()`. `Option` — обычный `enum` стандартной библиотеки, поэтому по нему работает и `switch`.

```go
user, ok := Find(users, "alice")
if !ok {
    return ErrNotFound
}

if p, ok := n.parent.Get(); ok {
    visit(p)
}
```

```go
var w io.Writer          // nil
w.Write(buf)             // ошибка компиляции: w может быть пустым

if w != nil {
    w.Write(buf)         // можно: w не пустой
}
```

### Нулевые значения

Как в Go, у каждого типа есть нулевое значение: его получают `var x T` и неуказанные поля структуры. Поэтому параметры, передаваемые структурой, имеют значения по умолчанию. У интерфейсов, срезов и словарей это `nil`, у новых типов: `Option` — `None`, `enum` — первый вариант, если он без данных, `Secret` и `Untrusted` — пустое значение внутри обёртки.

Если первый вариант `enum` несёт данные (`Circle{r f64}`), нулевого значения у типа нет: иначе забытое поле выглядело бы как правдоподобный круг радиуса 0. Тогда `var s Shape` и пропуск такого поля в литерале — ошибка компиляции, как у типов, чьё нулевое значение нарушает инвариант. Автор `enum` управляет этим порядком вариантов. Опасность нулевых значений в Go связана в основном с разыменованием `nil`, а в Kern оно невозможно.

```go
var sum u8                       // 0
var h ffi.Handle                 // пустой дескриптор
timer.Config{Freq: Hz(2)}        // Interrupt не указан → false
```

### Что убрано из Go

- функции `init()` и любые побочные эффекты импорта;
- build-теги в комментариях — их заменяют профили, выведенные эффекты и суффиксы архитектуры в именах файлов;
- значения типа `interface{}` / `any` как обходной путь вместо дженериков и `enum`; как ограничение дженерика (`[T any]`) и как разнотипные аргументы `...any`, разворачиваемые при компиляции (раздел 9), `any` остаётся;

### Система типов

Система типов — это Go плюс `enum`, `inout` и выводимые эффекты. Всё, что не описано иначе, ведёт себя как в Go.

| Конструкция | Поведение в Kern |
| --- | --- |
| структуры и встраивание | как в Go, включая встраивание полей; наследования нет |
| методы | получатель — значение или `inout` вместо `*T`; метод с `inout`-получателем изменяет значение вызывающего |
| интерфейсы | как в Go, реализация неявная; значение интерфейса хранит копию значения; вызов через интерфейс получает объединение эффектов возможных реализаций |
| дженерики | как в Go: параметры-типы с ограничениями-интерфейсами, включая `any` и `comparable` |
| `enum` | суммарный тип с вариантами-данными, исчерпывающий `switch`; может быть дженериком; нулевое значение — первый вариант, если он без данных |
| `Option` и ошибки | `type Option[T any] enum { None; Some{value T} }` в стандартной библиотеке, метод `Get() (T, bool)`; результаты функций — пара «значение, ok», как в Go; ошибки — интерфейс `error`, как в Go |
| замыкания | захватывают значения копией; замыкание, захватившее `inout`-параметр, нельзя сохранить или вернуть — только вызвать на месте |
| range-over-func | как в Go 1.23; итератор может выдавать `inout`-доступ — так контейнеры дают доступ к своей части: `for s := range stats.Lock() {...}` |
| видимость | как в Go: заглавная буква — экспорт, каталог `internal/` ограничивает импорт |
| словари | как в Go, но значения не адресуемы; копирование при записи |
| каналы | `chan T` как в Go; отправка логически копирует значение |
| типы синхронизации | `chan T`, `sync.Mutex[T]`, `sync.RWMutex[T]`, `atomic.*` — разделяемые дескрипторы: копия ссылается на тот же объект; содержимое доступно только через операции синхронизации |
| перегрузка операторов, исключения, наследование | нет, как в Go |

### Отличия от Go: сводка

| Что | Go | Kern |
| --- | --- | --- |
| новые ключевые слова | — | `enum`, `inout`, `profile` |
| контекстные слова | — | `requires`, `ensures`, `invariant`, `interrupt`, `trap`, `gpu`, `layout` |
| указатели | `*T`, `&x` | нет в обычном коде; `inout`, `unsafe.Map` в `core` |
| `nil` | есть, разыменование — паника | только пустое значение интерфейсов, срезов, словарей, каналов; вызов метода у пустого интерфейса не компилируется; для остального — «значение, ok» и `Option` в полях |
| сборщик мусора | есть | нет; копирование при записи и арены |
| горутины | неструктурированные | структурированные задачи с приоритетами |
| неиспользованная ошибка | разрешена | ошибка компиляции |
| переполнение целых | перенос | ошибка; `bits.WrappingAdd` и типы `wrap.U32` и др. для переноса |
| `init()` | есть | нет |
| глобальные переменные | любые | только атомарные, мьютексы, отображения железа |
| build-теги | комментарии | профили, эффекты, суффиксы файлов |
| рефлексия | во время выполнения | при компиляции (`meta`) |
| генерация кода | `go generate`, без проверок | вычисления при компиляции и изолированные генераторы |
| внешний код | cgo | `ffi` в стиле purego |
| зависимости | модули, прокси, sumdb | нет: только стандартная библиотека и код проекта |

## 4. Модель памяти

Kern использует изменяемую семантику значений (по образцу языка Hylo): безопасность памяти уровня Rust без времён жизни в синтаксисе и без сборщика мусора.

### Правила

1. Значения логически копируются при присваивании и передаче; компилятор устраняет фактические копии там, где это не меняет смысла. Единственное исключение — типы синхронизации (раздел 8): они существуют ради разделения, и копия ссылается на тот же объект.
2. Изменить значение вызывающего можно только через явный параметр `inout`.
3. Ссылки второго класса: их нельзя сохранять в структурах и возвращать из функций. Поэтому времена жизни не нужны.
4. Гонки данных невозможны по построению: одно изменяемое значение не может одновременно быть доступно из двух задач.

```go
func Append(buf inout Buffer, b u8) {
    if buf.len == buf.cap {
        buf.grow()
    }
    buf.data[buf.len] = b
    buf.len++
}
```

| Профиль | Модель |
| --- | --- |
| `core` | Только статическая память и стек; явные регионы и пулы фиксированного размера |
| `app` | Аллокация, регионы и арены; копирование при записи для больших значений |
| `ui` | Как `app`, плюс неизменяемые деревья состояния с разделением структуры |

### Почему без сборщика мусора

Сборщик мусора нужен прежде всего для циклических структур, а в модели Kern циклы образоваться не могут: ссылки нельзя сохранять в структурах, значение не может ссылаться само на себя. Остальное закрывается двумя механизмами:

1. **Копирование при записи.** Большие значения (строки, срезы, словари) разделяются между копиями и копируются только при изменении. Внутри это счётчик ссылок, невидимый для программиста и неспособный зациклиться.
2. **Арены для графов.** Граф, дерево со ссылками на родителя, сцена игры живут в арене, а связи между узлами — дескрипторы `arena.Ref[T]` из индекса и поколения. Обращение к удалённому узлу обнаруживается по несовпадению поколения, а не портит память. Арена освобождается целиком одной операцией.

```go
type Node struct {
    name     string
    parent   Option[arena.Ref[Node]]
    children []arena.Ref[Node]
}

func (n inout Node) AddChild(c arena.Ref[Node]) {
    n.children = append(n.children, c)
}

func BuildTree(a inout arena.Arena[Node]) arena.Ref[Node] {
    root := a.New(Node{name: "root"})
    child := a.New(Node{name: "child", parent: Some(root)})
    for n := range a.Edit(root) {
        n.AddChild(child)
    }
    return root
}
```

Итог: одна модель памяти во всех профилях, нет рантайма сборщика, пауз и его настройки, память освобождается в предсказуемый момент. Цена — графы с произвольными связями строятся через арены и дескрипторы, а не через прямые указатели.

### Изменение частей значения

Отдельного механизма для доступа «внутрь» значения (проекций, как в Hylo) нет. Изменение части значения выражается тремя правилами, а логика изменения живёт в методах самой сущности — это инкапсуляция:

1. **Элементы массивов и срезов, поля структур — как в Go.** Они адресуемы: компилятор сам даёт временный `inout`-доступ, поэтому `xs[i].Increment()` и `p.pos.x = 0` работают.
2. **Словари — как в Go.** Значение в словаре не адресуемо: его читают, изменяют и записывают обратно.
3. **Свои контейнеры — итератором с `inout`-доступом.** Контейнер даёт доступ к своей части методом, который возвращает итератор, как range-over-func в Go 1.23, только переменная цикла получает `inout`-доступ: `for n := range a.Edit(root) {...}`, `for s := range stats.Lock() {...}`. Итератор выдаёт доступ один раз; переменная цикла — временный `inout`, её нельзя сохранить. `return`, `break` и обработка ошибок внутри тела работают как в обычном коде, а завершающие действия (снятие блокировки) итератор выполняет при любом выходе, как `defer`. Компилятор встраивает такие итераторы, накладных расходов нет.

```go
xs[i].Increment()                          // срез: элемент адресуем

u := users["alice"]                        // словарь: прочитать, изменить, записать
u.SetAge(31)
users["alice"] = u

for n := range a.Edit(root) {              // свой контейнер: итератор с inout-доступом
    n.AddChild(child)
}
```

Цена простоты: свой контейнер не может иметь индексацию, которая ведёт себя как встроенная (`a[root].AddChild(child)`).

### Глобальное состояние

Глобальные переменные не запрещены, но строго ограничены тремя правилами:

1. **На уровне пакета разрешены только безопасные виды переменных:** атомарные типы (`atomic.U32` и подобные), контейнеры с синхронизацией (`sync.Mutex[T]`, доступ только через `Lock`) и отображения железа (видеопамять, регистры) — последние только в профиле `core`. Обычная изменяемая переменная на уровне пакета — ошибка компиляции.
2. **Инициализация только константным выражением.** Раз нет `init()`, начальное значение вычисляется при компиляции; проблемы порядка инициализации пакетов нет.
3. **Доступ к глобальному состоянию — выведенный эффект `Global`.** Видно, какой код зависит от общего состояния.

```go
var ticks atomic.U32                    // можно: атомарный тип
var stats sync.Mutex[Stats]             // можно: доступ только через Lock
var count int                           // ошибка: обычная изменяемая переменная

type Server struct {                    // изменяемое состояние живёт в структуре
    count int
}

func (s inout Server) Handle(r Request) {
    s.count++
}
```

При переносе кода с Go `kern port` оборачивает глобальные переменные в `sync.Mutex[T]` или переносит их в структуру.

### Низкий уровень: unsafe и виды указателей

Для драйверов, видеопамяти и регистров есть сырые указатели. Они доступны только в профиле `core` и только через пакет `unsafe`, как в Go: отдельных блоков `unsafe` нет, импорт пакета и есть отметка небезопасного кода.

В обычном коде нет ни `*T`, ни `&x`. Для внешних функций вместо указателей используются `inout` (выходные параметры), срезы (буферы) и `ffi.Handle` (непрозрачные объекты), см. раздел 11.

Отображение железа (видеопамять, регистры, разделяемые буферы) объявляется один раз через `unsafe.Map` — это единственное место, где программист утверждает то, что компилятор проверить не может: «по этому адресу лежат данные такого вида». Результат — обычное типизированное значение, работа с которым безопасна: индексы проверяются или доказываются решателем. Регистры микроконтроллеров отображаются генератором по SVD-файлу, поэтому в пользовательском коде `unsafe` нет вовсе. Всё небезопасное в программе находится поиском по `unsafe`.

Вид указателя определяется целью и встречается только внутри unsafe и пакетов архитектур:

| Цель | Виды указателей |
| --- | --- |
| i8086 (DOS) | `near` (16 бит, внутри сегмента), `far` (сегмент:смещение, 32 бита) |
| AVR | указатель на RAM, указатель на flash (чтение специальной командой) |
| 32/64-битные цели | один плоский вид |

```go
// Текстовая видеопамять DOS: сегмент B800h
var screen = unsafe.Map[[2000]Cell](i8086.Far(0xB800, 0))
```

Один механизм «вид указателя в типе» обслуживает и сегментную память 8086, и гарвардскую архитектуру AVR.

## 5. Эффекты и возможности

Компилятор знает, что делает каждая функция: работает ли она с сетью, файлами, памятью, может ли упасть. Эффекты не пишутся в сигнатурах: компилятор выводит их сам по графу вызовов всей программы и проверяет ограничения на границах. Код выглядит как обычный Go, а механизм безопасности сохраняется полностью.

### Как выводятся эффекты

1. Источники эффектов — примитивы: системные вызовы и нижний уровень стандартной библиотеки, внешние функции (раздел 11), `asm`, аллокация, проверки, которые могут вызвать панику.
2. Эффекты функции — объединение эффектов всего, что она вызывает. Весь код — проекта и стандартной библиотеки — доступен исходниками, поэтому граф вызовов виден целиком.
3. **Эффект принадлежит тому, кто передал функцию.** Если функция вызывает свой параметр — функциональное значение, метод интерфейса, метод параметра-типа, — её сводка содержит не конкретные эффекты, а ссылку на эффекты этого параметра. Подставляются они в точке вызова и засчитываются вызывающему.
4. Интерфейсные значения, сохранённые в структурах данных (маршрутизатор со списком `Handler`), дают в сводке открытую ссылку «эффекты реализаций `Handler`». Она разрешается при сборке всей программы и тоже засчитывается тому, кто положил реализацию.
5. Эффекты внешних функций компилятор узнать не может, поэтому они задаются данными в объявлении: `lib.Symbol("sqlite3_open", ffi.Effects{File})`. Без указания — эффект `Foreign` («может всё»).

```go
func Fetch(url string) ([]u8, error)                   // выведено: Network, Alloc
func Hash(data []u8) u64                               // выведено: эффектов нет
func Slice[T any](xs inout []T, less func(a, b T) bool) // выведено: {} ∪ less
func Serve(l Listener, h Handler) error                // выведено: {Network} ∪ h.ServeHTTP
```

Поэтому сводка пакета зависит только от самого пакета и сводок его зависимостей, но не от тех, кто его вызывает. На этом держатся кэш по пакетам и честная атрибуция: пакет без собственных эффектов остаётся таким, даже если ему передали колбэк с сетью.

### Где задаются ограничения

Ограничения пишутся только на границах, а не в каждой функции:

| Граница | Что ограничивает |
| --- | --- |
| описание цели | что даёт платформа (`Provides`, `Lacks`) |
| профиль пакета | набор допустимых эффектов (раздел 6) |
| `interrupt`, `trap` | автоматически без `Alloc`, `Block` и `Panic` |
| манифест приложения | разрешения iOS и Android выводятся из эффектов (раздел 15) |
| строка `ensures` в функции | ограничения конкретной функции: без паники, без аллокаций, постоянное время, наихудшее время выполнения |

### Свои эффекты и ограничения функций

Библиотека объявляет свой эффект константой и помечает функцию-источник вызовом `effect.Mark`, который понимает компилятор и который ничего не стоит во время выполнения. Дальше эффект протекает вверх, как любой другой. Эффекты нижнего уровня при этом сохраняются, поэтому скрыть сетевое обращение за другим именем нельзя. Так устроены `SQL`, `Camera`, `ExposeSecret`, `Detach`, `Privileged`.

```go
package sql

import "kern/effect"

const SQL = effect.Declare("SQL")

func (db DB) Query(q string, args ...any) (Rows, error) {
    effect.Mark(SQL)
    ...
}
```

Ограничение конкретной функции записывается строкой `ensures`, как остальные контракты. `interrupt` и `trap` — готовые сокращения для `ensures effect.Without(Alloc, Block, Panic)`.

```go
func Compare(a, b Secret[[]u8]) bool {
    ensures secret.ConstantTime()
    ...
}

func HandleFrame(f Frame) {
    ensures effect.Without(Alloc, Panic)
    ...
}
```

### Как эффекты видны

- `kern doc` и подсказки редактора показывают эффекты каждой функции.
- `kern query` отвечает, откуда взялся эффект.
- Ошибка показывает цепочку вызовов: `TIM2 → buffer.Push → grow → Alloc`.
- Семантический диф двух версий кода показывает появившиеся эффекты.

### Базовый набор эффектов

| Группа | Эффекты |
| --- | --- |
| Память | `Alloc`, `StaticAlloc` |
| Ввод-вывод | `Console`, `File`, `Network`, `Video`, `Keyboard` |
| Исполнение | `Panic`, `Block`, `Tasks`, `Interrupts` |
| Железо | `Gpio`, `Uart`, `Timers` и другие, из описания устройства; плюс эффект на каждый экземпляр периферии (`TIM2`, `USART1`) для проверки владения (раздел 13) |
| Недетерминизм | `Clock`, `Random` |
| Общее состояние | `Global` |

Набор расширяемый: эффекты периферии берутся из описаний устройств, библиотеки могут объявлять свои через effect.Declare.

### Цена

По сигнатуре не видно, что функция работает с сетью, — это показывают инструменты. Изменение глубоко внутри может добавить эффект многим функциям выше; это ловят семантический диф и ограничения профилей.

## 6. Профили

Профиль — это набор ограничений на эффекты, объявляемый для пакета одной строкой `profile`. Три профиля позволяют одному языку покрыть всё от .COM-файла на 2 КБ до веб-интерфейса без FFI и сериализации на стыках.

| Профиль | Разрешено | Запрещено | Для чего |
| --- | --- | --- | --- |
| `core` | статическая память, `unsafe`, `asm`, прерывания | куча, зависимость от ОС | DOS, микроконтроллеры, ядра, драйверы |
| `app` | аллокация, арены, задачи на нескольких ядрах, системные вызовы | прерывания, привилегированные команды | сервисы, утилиты, бэкенд, СУБД |
| `ui` | всё из `app`, декларативный UI, реактивное состояние | прямой доступ к железу | веб, десктоп, iOS, Android |

Граница между профилями проходит по простому признаку: есть ли под программой ОС и есть ли у неё интерфейс. Более тонкие ограничения (например, никаких прямых системных вызовов в библиотеке) задаются эффектами в `kern.mod`.

### Правило вызова

Код из более строгого профиля можно вызывать из более мягкого; обратное запрещено типами. Пакет `crc` с профилем `core` годится и для прошивки, и для веб-страницы. Пакет `httpclient` с профилем `app` в прошивку не попадёт.

Пакет может объявить несколько профилей, если не использует ничего за пределами самого строгого из них:

```go
package crc

profile core, app, ui
```

### UI-профиль

- Интерфейс — чистая функция от состояния: `View(State) ui.Node`.
- Переходы — явный `Update(State, Msg) (State, Cmd)` с исчерпывающим `switch` по `enum`.
- Раскладка задаётся ограничениями, а не подбором стилей.
- Доступность в типах: интерактивный элемент без текстовой метки не компилируется.
- Хуки визуальной проверки: компонент можно отрендерить в тесте и сравнить с эталоном.

Интерфейс на всех целях рисуется собственным рендером Kern: GPU, программный растеризатор или текстовый режим (подробно — раздел 15).

```go
func Update(s State, m Msg) (State, Cmd) {
    switch m {
    case Inc:   return State{s.count + 1}, cmd.None
    case Dec:   return State{s.count - 1}, cmd.None
    case Reset: return State{0}, cmd.None
    }
}

func View(s State) ui.Node {
    return ui.Column(
        ui.Text(fmt.Sprint("Счёт: ", s.count)),
        ui.Row(ui.Button("−", Dec), ui.Button("+", Inc)),
    )
}
```

## 7. Числа, строки и данные

Переполнение целого числа в Kern — ошибка, а не тихий перенос. Где возможно, отсутствие переполнения доказывается при компиляции; где нет — вставляется проверка. Циклическая и насыщающая арифметика записывается явно.

### Целые числа

| Тип | Размер |
| --- | --- |
| `i8`, `i16`, `i32`, `i64` | знаковые фиксированного размера |
| `u8`, `u16`, `u32`, `u64` | беззнаковые фиксированного размера |
| `int`, `uint` | машинное слово цели |
| `usize` | размер адресного пространства цели: индексы и длины |

Правила:

1. `+`, `-`, `*` проверяют переполнение. Компилятор сначала пытается доказать его отсутствие; если не удалось — вставляет проверку с эффектом `Panic`.
2. Если отсутствие переполнения не доказано, функция получает выведенный эффект `Panic`. Там, где паника запрещена — в обработчиках `interrupt` и `trap`, а также в пакетах, для которых это задано в `kern.mod` или профилем, — переполнение должно быть доказано или обработано явно. Что делает паника, задаёт цель (`OnPanic`): на сервере — сообщение и завершение, на микроконтроллере — сброс или остановка, в DOS — сообщение и выход в DOS.
3. Другое поведение для отдельных операций — функциями пакета `bits`, как в Go: `bits.WrappingAdd(a, b)`, `bits.SaturatingAdd(a, b)`, `bits.CheckedAdd(a, b)` с результатом «значение, ok». Это дженерики: одна функция на все целые типы. Методов у встроенных типов нет.
4. Для кода, где перенос — норма (хэши, CRC, ГПСЧ, криптография), есть циклические типы пакета `wrap`: `wrap.U8`…`wrap.U64`, `wrap.I8`…`wrap.I64`. Их операторы `+`, `-`, `*`, `<<` переносят без паники. Это такие же известные компилятору типы, как `simd.F32x4` и `fixed.Q16`, а не перегрузка операторов. Смешивать их с обычными целыми можно только через явное преобразование, поэтому перенос виден в типе переменной.
5. Сужающее преобразование `u8(x)` компилируется, только если диапазон доказан; иначе — `conv.Narrow[u8](x)` с результатом `(u8, bool)`.

```go
func Checksum(data []u8) u8 {
    var sum u8
    for _, b := range data {
        sum = bits.WrappingAdd(sum, b)     // единичный перенос: функция
    }
    return sum
}

func FNV1a(data []u8) u64 {
    var h wrap.U64 = 0xcbf29ce484222325
    for _, b := range data {
        h = (h ^ wrap.U64(b)) * 0x100000001b3   // перенос — свойство типа
    }
    return u64(h)
}
```

### Дробные числа

- `f32`, `f64` по IEEE 754.
- Цель объявляет `floats = hard | soft | none`. При `soft` используется программная эмуляция, при `none` использование дробных чисел — ошибка компиляции.
- Тип `decimal` в стандартной библиотеке для денег и точных расчётов.
- Фиксированная точка — готовые типы `fixed.Q16` (16.16), `fixed.Q8` (8.8) и другие для микроконтроллеров без FPU.

### SIMD

Векторные типы — готовые типы пакета `simd`: `simd.F32x4`, `simd.U8x16` и другие, с поэлементными операциями. Компилятор отображает их на SSE/AVX, NEON, RVV или SIMD в WebAssembly, а на целях без векторных команд — на обычный цикл.

### Строки и кодировки

| Тип | Назначение |
| --- | --- |
| `string` | неизменяемая строка UTF-8 |
| `[]u8` | байты без кодировки |
| `cstring` | строка с нулём в конце, для C |
| `dstring` | строка с `$` в конце, для функций DOS |

Перекодировка константной строки выполняется при компиляции обычной функцией: `encoding.CP866("Привет")` даёт байты в кодировке DOS, а при передаче в функцию, принимающую `dstring`, `$` добавляется автоматически. Перекодировка во время выполнения — тот же пакет `encoding`. Префиксов у строковых литералов нет.

```go
dos.Print(encoding.CP866("Привет из Kern!\r\n"))   // вычислено при компиляции: CP866, $ добавлен
```

### Порядок байтов и раскладка структур

Раскладка структур по умолчанию остаётся за компилятором. Для форматов файлов, сетевых протоколов и регистров её можно зафиксировать: `layout packed`, `layout c`, а поля — объявить с порядком байтов `u32be`, `u16le`.

## 8. Конкурентность

Конкурентность в Kern выглядит как в Go — `go`, каналы, `select`, — но она структурированная: функция не возвращается, пока не завершились все задачи, запущенные в ней. Утечек горутин и гонок данных нет по построению.

### Правила

1. `go f()` даёт функции эффект `Tasks` и привязывает задачу к текущей функции.
2. Функция ждёт завершения всех своих задач перед возвратом. Ошибка или паника в задаче отменяет остальные и передаётся наверх.
3. Задача, которая должна пережить функцию, запускается явно через `task.Detach` с эффектом `Detach`.
4. Отмена и дедлайны распространяются от родителя к детям автоматически, без ручной передачи `context`.
5. По каналу передаются значения: отправка логически копирует значение, как присваивание; отправитель может и дальше пользоваться своей копией, а получатель её изменений не видит. Большие значения при этом не копируются фактически: копирование при записи для значений, переданных между задачами, использует атомарный счётчик ссылок. Разделяемого изменяемого состояния между задачами нет.
6. Общие данные, если они нужны, живут внутри `sync.Mutex[T]` или атомарных типов; доступ — только через блокировку, выдающую `inout`-доступ.
7. Типы синхронизации — `chan T`, `sync.Mutex[T]`, `sync.RWMutex[T]`, `atomic.*` — разделяемые дескрипторы: при копировании, захвате в замыкание и передаче в задачу все копии ссылаются на один объект. Гонок это не создаёт, потому что содержимое доступно только через `Lock`, атомарные операции, отправку и приём.
8. `inout`-аргумент в `go f(x)` — исключительное заимствование до конца функции, запустившей задачу. Это безопасно, потому что по правилу 2 задача завершится раньше. После `go` родитель не может обращаться к `x`; два `inout` в разные задачи на части одного среза допустимы, если решатель доказал, что части не пересекаются. В `task.Detach` `inout`-аргументы запрещены: такая задача может пережить родителя.

```go
func SortParallel(xs inout []i32) {
    mid := len(xs) / 2
    go Sort(xs[:mid])        // части не пересекаются:
    go Sort(xs[mid:])        // доказано решателем
    // xs[0] = 1             // ошибка компиляции: xs отдан задачам
}
```

### Пример

```go
type result struct {
    page Page
    err  error
}

func FetchAll(urls []string) ([]Page, error) {
    results := make(chan result, len(urls))

    for _, u := range urls {
        go func() {
            page, err := http.Get(u)
            results <- result{page, err}
        }()
    }

    pages := []Page{}
    for range urls {
        select {
        case r := <-results:
            if r.err != nil {
                return nil, r.err
            }
            pages = append(pages, r.page)
        case <-task.Deadline(5 * Second):
            return nil, ErrTimeout       // незавершённые задачи отменяются
        }
    }
    return pages, nil
}
```

### Общие данные

```go
var stats sync.Mutex[Stats]

func Record(d Duration) error {
    for s := range stats.Lock() {
        if s.count == MaxRecords {
            return ErrFull                   // блокировка снимается при любом выходе
        }
        s.count++
        s.total += d
    }
    return nil
}
```

Обратиться к `Stats` без блокировки невозможно: значение доступно только как переменная цикла `range stats.Lock()`. Копию под блокировкой даёт `stats.Load()`.

Общие данные не обязаны быть глобальными: мьютекс, объявленный в функции, разделяют все её задачи.

```go
func Serve(reqs []Request) Stats {
    var stats sync.Mutex[Stats]          // готовый объект
    for _, r := range reqs {
        go func() {
            d := handle(r)
            for s := range stats.Lock() {
                s.total += d             // тот же мьютекс во всех задачах
            }
        }()
    }
    // здесь функция ждёт завершения своих задач (правило 2)
    return stats.Load()
}
```

У типов синхронизации нулевое значение — готовый объект: `var m sync.Mutex[T]` создаёт мьютекс. Исключение — `chan T`: как в Go, нулевое значение `nil`, такой канал блокирует навсегда и используется в `select` для отключения ветки, а создаётся канал через `make`.

Где живёт объект:

- Если дескриптор не уходит в `task.Detach`, объект размещается в кадре создавшей его функции: структурированная конкурентность гарантирует, что задачи завершатся раньше. Ни кучи, ни счётчика ссылок не нужно, поэтому так работает и `core`.
- Иначе объект размещается в куче с атомарным счётчиком ссылок; это доступно только в `app` и `ui`.

### Реализация по профилям

| Профиль или цель | Как исполняются задачи |
| --- | --- |
| `core` | статические задачи: вытеснение между уровнями приоритета, внутри уровня — по очереди; размеры известны при компиляции |
| `app` | планировщик M:N поверх потоков ОС с асинхронным вводом-выводом (epoll, kqueue, IOCP, io\_uring) |
| `ui` | главный поток интерфейса и фоновые задачи; обновление UI только из главного |
| `web` | цикл событий браузера; потоки WebAssembly там, где доступны |
| DOS | кооперативные задачи: переключение при ожидании таймера, ввода-вывода и каналов |

### Задачи и потоки ОС

1. **Одна абстракция — задачи.** Потоки ОС в языке не видны: ими управляет планировщик, как в Go.
2. **`go` работает на всех целях.** Где есть несколько ядер и потоки ОС, задачи выполняются параллельно; где их нет (DOS, микроконтроллеры, браузер без потоков) — по очереди, кооперативно. Код одинаковый, меняется только скорость.
3. **Привязка к потоку ОС** для редких случаев — внешняя библиотека с данными, привязанными к потоку, графический контекст, главный поток интерфейса: `task.LockThread()`, как в Go.
4. **Долгие блокирующие вызовы внешних функций** планировщик сам выносит на отдельный поток, чтобы они не останавливали остальные задачи.

В кооперативном режиме задача, которая долго считает и ни разу не ждёт, задерживает остальные. Компилятор предупреждает о длинных циклах без точек ожидания внутри задач.

### Приоритеты задач

У задач есть фиксированные уровни приоритета: `Low`, `Normal`, `High`, а в профиле `core` дополнительно `Critical` для задач реального времени. Обычный `go` запускает задачу с приоритетом `Normal`; другой приоритет задаётся структурой параметров. Дочерние задачи по умолчанию наследуют приоритет родителя.

```go
go render()                                              // Normal
task.Go(task.Config{Priority: task.High}, readSensor)    // высокий
task.Go(task.Config{Priority: task.Low}, syncToCloud)    // фоновый
```

| Где | Что значит приоритет |
| --- | --- |
| микроконтроллеры (`core`) | задача выше уровнем вытесняет задачу ниже; внутри уровня — по очереди |
| `app` | подсказка планировщику; задачи с `task.LockThread()` получают соответствующий приоритет потока ОС |
| `ui` | главный поток интерфейса автоматически выше всех, фоновые задачи — `Low` |
| DOS, браузер | порядок выбора следующей задачи в кооперативном режиме |

- **Инверсия приоритетов.** `sync.Mutex` временно поднимает приоритет держателя блокировки до приоритета ожидающего. В `core` компилятор, видя всю программу, заранее вычисляет для каждого мьютекса наивысший приоритет его пользователей (протокол потолка приоритетов, как в RTIC): инверсия и взаимоблокировки исключены при компиляции.
- **Голодание.** В `app` и `ui` планировщик постепенно поднимает приоритет давно ждущих задач. В `core` компилятор предупреждает о задачах высокого приоритета без точек ожидания.
- **Цель на развитие:** вместе с оценкой WCET (раздел 13) и периодами задач — проверка при компиляции, что все задачи укладываются в свои сроки.

### Проверка

В тестах планировщик заменяется детерминированным, который перебирает чередования задач. Взаимоблокировки и неверный порядок операций находятся воспроизводимо, а не случайно.

## 9. Метапрограммирование

Макросов в Kern нет: они нарушают локальность рассуждений. Вместо них — вычисления при компиляции обычным кодом Kern и рефлексия типов во время компиляции. Новых ключевых слов не требуется: расширяется смысл `const` из Go.

### Вычисления при компиляции

Любая функция без эффектов может быть выполнена компилятором. Значение `const` может быть результатом такой функции, а не только литералом:

```go
const crcTable = makeCRCTable(0xEDB88320)     // [256]u32, вычислено при компиляции, лежит во flash

func makeCRCTable(poly u32) [256]u32 {
    var t [256]u32
    for i := range 256 {
        c := u32(i)
        for range 8 {
            if c&1 == 1 { c = poly ^ (c >> 1) } else { c >>= 1 }
        }
        t[i] = c
    }
    return t
}
```

Компилятор ограничивает время и память таких вычислений и сообщает, если предел превышен.

### Рефлексия при компиляции

Пакет `meta` даёт доступ к описанию типов, но только при компиляции: `meta.Fields(T)`, `meta.Variants(E)`, `meta.Name(T)`. Цикл по полям разворачивается компилятором. Так пишутся сериализация, сравнение, печать — без генерации текста и без рефлексии во время выполнения:

```go
func Encode[T any](w inout json.Writer, v T) {
    w.BeginObject()
    for const f := range meta.Fields(T) {
        w.Key(f.Name)
        Encode(w, f.Get(v))
    }
    w.EndObject()
}
```

`for const` — цикл, выполняемый при компиляции; это не новое слово, а сочетание существующих.

### Аргументы `...any`

Параметр `...any` — не срез интерфейсов, как в Go, а кортеж аргументов, типы которых известны при компиляции. Функция обходит его через `for const`, и для каждого набора типов в точке вызова создаётся свой экземпляр, как у дженериков. Так устроены `fmt`, логгер и параметры SQL-запросов:

```go
func Sprint(args ...any) string {
    var b strings.Builder
    for const a := range args {
        writeValue(b, a)                  // тип a известен при компиляции
    }
    return b.String()
}
```

- Неверный формат (`%d` для строки) — ошибка компиляции.
- Эффекты считаются точно для каждого вызова.
- Функция может проверять типы аргументов: `sql.Query` принимает `Untrusted`, но отвергает `Secret` без `secret.Expose`.
- Чтобы код не разрастался, тело такой функции делают тонким: для каждого аргумента оно вызывает общее нетипизированное ядро.

### Генераторы

Для внешних описаний (SVD-файлы, описания системных вызовов) используются генераторы — обычные программы Kern, которые `kern` запускает при сборке. Привязки к внешним библиотекам и системным API генераторов не требуют: они объявляются вручную (раздел 11).

- Генератор получает только эффекты `ReadInput` и `WriteOutput` на объявленные файлы; сеть и остальная файловая система недоступны.
- Результат детерминирован и кэшируется по хэшу входов.
- Сгенерированный код можно открыть и прочитать как обычный, в отличие от раскрытия макросов.

## 10. Безопасность данных

Два типа-обёртки превращают целые классы уязвимостей в ошибки компиляции: `Secret[T]` для секретов и `Untrusted[T]` для внешних данных. SQL-инъекции, XSS, обход путей и утечка паролей в логи становятся невозможными без явного действия.

### Secret\[T\]

Секрет — пароль, ключ, токен — нельзя случайно раскрыть.

| Ограничение | Что это предотвращает |
| --- | --- |
| не печатается через `fmt` и логгер (выводится `***`) | пароли в логах |
| нет оператора `==`; сравнение только `secret.Equal` за постоянное время | атаки по времени |
| память затирается нулями при освобождении | секреты в дампах памяти |
| не передаётся в сеть, файл или UI без `secret.Expose` с эффектом `ExposeSecret` | случайная отправка |

```go
func Login(user string, pass Secret[string]) (Session, error) {
    hash, err := db.PasswordHash(user)
    if err != nil {
        return Session{}, err
    }
    if !secret.Equal(crypto.Hash(pass), hash) {
        return Session{}, ErrDenied
    }
    log.Info("вход", user, pass)      // в лог попадёт: вход alice ***
    return newSession(user), nil
}
```

### Untrusted\[T\]

Всё, что пришло извне — тело HTTP-запроса, файл, ввод пользователя, переменные окружения, — стандартная библиотека возвращает как `Untrusted[T]`.

1. Опасные приёмники принимают только проверенные данные или параметры: SQL-запрос, путь к файлу, HTML, команда оболочки.
2. Проверка — функция, превращающая `Untrusted[string]` в осмысленный тип: `validate.Email(u) (Email, error)`, `fs.SafePath(root, u) (Path, error)`.
3. Параметризованный запрос принимает `Untrusted` безопасно, потому что значение не становится частью текста запроса.

```go
func Search(r http.Request) (http.Response, error) {
    q := r.Query("q")                                          // Untrusted[string]

    rows, err := db.Query("SELECT title FROM docs WHERE title LIKE ?", q)   // параметр: допустимо
    // db.Query("SELECT ... '" + q + "'")                    // ошибка компиляции: склейка с Untrusted

    if err != nil {
        return http.Response{}, err
    }
    return html.Render(resultsPage, rows), nil                 // html экранирует автоматически
}
```

### Постоянное время

Для криптографического кода есть ограничение `ensures secret.ConstantTime()`: внутри такой функции компилятор запрещает ветвления и обращения к памяти по индексу, зависящие от значений `Secret`. Это цель на развитие; на первом этапе — только проверка ветвлений.

## 11. Взаимодействие с внешним кодом

Kern вызывает внешний код по образцу purego в Go: без компилятора C, без разбора заголовков и без генераторов привязок. Внешняя функция объявляется обычной сигнатурой Kern, а её символ берётся из динамической библиотеки при запуске или из готового объектного файла при сборке. Цепочка сборки остаётся одним бинарником `kern`, и кросс-компиляция под любую цель не требует дополнительных инструментов.

### Объявление

```go
package sqlite

import "kern/ffi"

var lib = ffi.Library{
    linux:   "libsqlite3.so.0",
    macos:   "/usr/lib/libsqlite3.dylib",
    windows: "sqlite3.dll",
    android: "libsqlite3.so",
}

func sqlite3_open(path cstring, db inout ffi.Handle) i32 = lib.Symbol("sqlite3_open", ffi.Effects{File})
func sqlite3_close(db ffi.Handle) i32        = lib.Symbol("sqlite3_close", ffi.Effects{File})
```

Внешняя функция — это функция без тела, связанная с символом через `=`. Новых ключевых слов не требуется.

### Динамическая загрузка и статическая компоновка

Оба способа доступны везде, где это физически возможно, и объявляются одинаково — отличается только источник символов:

```go
var sqlite = ffi.Library{linux: "libsqlite3.so.0", macos: "/usr/lib/libsqlite3.dylib"}   // из системы при запуске
var zlib   = ffi.Static{armv7m: "lib/zlib/libz-armv7m.a", x86_64: "lib/zlib/libz-x86_64.a"}                                     // внутрь программы при сборке

func sqlite3_open(path cstring, db inout ffi.Handle) i32 = sqlite.Symbol("sqlite3_open", ffi.Effects{File})
func inflate(s inout ZStream, flush i32) i32                       = zlib.Symbol("inflate")
```

| Способ | Когда нужен | Где доступен |
| --- | --- | --- |
| `ffi.Library` | библиотека принадлежит системе: фреймворки iOS и macOS, `libc`, графические драйверы | Linux, Android, macOS, iOS, Windows |
| `ffi.Static` | программа поставляется одним файлом; закрытые драйверы производителей микроконтроллеров (например, Wi-Fi у ESP32) | все цели, включая DOS, микроконтроллеры и ядра |
| `ffi.At(адрес)` | функции в ПЗУ, BIOS, прошитые отдельно стеки (Nordic SoftDevice) | цели без ОС |

- Для статической компоновки `kern` содержит компоновщик объектных файлов ELF, Mach-O и COFF. Это компоновщик, а не компилятор: компилятор C по-прежнему не нужен.
- Объектный файл должен быть собран под ту же архитектуру и ABI, что и цель; `kern` проверяет это при сборке.
- Готовые объекты лежат в проекте. Их код нельзя прочитать, поэтому добавление и замену такого файла подтверждает человек.
- Лицензию объектного файла проверяет человек: например, LGPL при статической компоновке накладывает дополнительные обязательства.

### Правила

1. Эффекты внешней функции объявляет автор объявления. Компилятор не может их проверить, поэтому такие строки отмечаются в отчётах как непроверяемые, а семантический диф показывает их изменения отдельно.
2. Если `ffi.Effects` не указан, функция получает эффект `Foreign` — «может всё».
3. Внешнюю функцию можно вызывать только в пакете, где она объявлена; наружу пакет отдаёт обычную обёртку на Kern.
4. Динамическая библиотека загружается при старте программы. Если её нет, программа не запускается и сообщает, чего не хватает. Необязательная библиотека объявляется с `optional: true`, наличие проверяется `lib.Available()`.
5. Соглашение о вызовах берётся из описания цели — того же, по которому вызываются функции Kern.

### Обёртка

```go
type DB struct {
    h ffi.Handle
}

func Open(path string) (DB, error) {
    var h ffi.Handle
    rc := sqlite3_open(ffi.CString(path), h)        // inout: адрес передаётся на время вызова
    if rc != 0 {
        return DB{}, sqliteError(rc)
    }
    return DB{h}, nil
}
```

### Что можно передавать

| Тип Kern | На стороне внешнего кода |
| --- | --- |
| целые и дробные числа | соответствующие типы C |
| `inout T` | указатель на значение на время вызова (выходные параметры) |
| срез `[]T` | указатель на первый элемент; память закреплена на время вызова |
| `ffi.Handle` | непрозрачный указатель на объект библиотеки |
| `cstring` | `const char*` |
| структура с `layout c` | структура по значению; по указателю — через `inout` |
| `ffi.Callback(f)` | указатель на функцию Kern |

Указателей `*T` и операции `&x` в объявлениях внешних функций и при их вызове нет.

Как и в purego, число одновременно живых колбэков ограничено, а функции с переменным числом аргументов объявляются отдельно для каждого нужного набора аргументов.

### Один механизм для всех платформ

| Платформа | Откуда берётся символ |
| --- | --- |
| Linux, Android | `dlopen` / `dlsym` |
| macOS, iOS | `dlopen` / `dlsym`; системные фреймворки, рантайм Objective-C через `objc_msgSend` |
| Windows | `LoadLibrary` / `GetProcAddress` |
| Android, Java-API | указатели из таблицы функций JNI, те же объявления |
| web | импорт WebAssembly: `= js.Import("console", "log")` |
| DOS, микроконтроллеры, ядра | динамической загрузки нет: ffi.Static, `= ffi.At(адрес)` для функций в ПЗУ и таблицах загрузчика, прерывания через `asm` |

### Что сознательно не поддерживается

- разбор C-заголовков: объявления пишутся вручную, обычно ИИ по документации библиотеки;
- макросы и `inline`-функции C: их логика переписывается на Kern;
- компиляция C-исходников: в проекте лежат только код на Kern и готовые объектные файлы;
- экспорт кода Kern как C-библиотеки: на первом этапе колбэков достаточно.

### Что это даёт

- В поставке среды нет компилятора C, внешнего компоновщика и SDK других языков; исключение — подпись приложений iOS инструментами Apple.
- Кросс-компиляция под любую цель — один флаг `-target`.
- Сборка остаётся воспроизводимой и офлайн.
- Граница с внешним кодом видна сразу: все внешние функции — однострочные объявления в одном месте пакета.

## 12. Цели

Цель сборки — это сочетание трёх независимых описаний: архитектуры, платформы и формата бинарника. Все три — декларативные данные на Kern в стандартной библиотеке или в проекте; добавление новой архитектуры не требует изменения компилятора.

| Слой | Описывает | Примеры |
| --- | --- | --- |
| Архитектура | команды, регистры, размер слова, виды указателей, соглашения о вызовах | `i8086`, `x86_64`, `armv7m`, `avr`, `riscv32`, `riscv64`, `arm64`, `wasm32` |
| Платформа | что даёт окружение: эффекты, ABI, точку входа | `dos`, `bare`, `linux`, `windows`, `macos`, `web` |
| Формат | структуру выходного файла | `flat` (.COM), `mz` (.EXE), ELF, PE, Mach-O, `.wasm`, BIN, Intel HEX, UF2 |

### Описание цели

Описание цели — обычная константа на Kern в пакете цели: один парсер, проверка типов (опечатка в имени поля — ошибка компиляции) и вычисления при компиляции. Так же описываются архитектуры, манифесты приложений и системные вызовы. Файлы, которые ведёт инструмент (`kern.mod`, `REQUIREMENTS`), используют строчный формат в стиле `go.mod`: одна запись — одна строка, удобно читать в дифах.

```go
package doscom

import (
    "kern/arch"
    "kern/platform"
    "kern/target"
)

const Description = target.Desc{
    Arch:     arch.I8086,
    Platform: platform.DOS,
    Word:     16,                                        // int здесь 16-битный
    Pointers: target.Pointers{Near: 16, Far: 32},
    Formats:  []target.Format{target.Flat{Origin: 0x100, MaxSize: 65280}},
    Floats:   target.SoftFloat,                          // 8087 может не быть
    Provides: []Effect{Console, Video, File, Keyboard, StaticAlloc},
    Lacks:    []Effect{Network},
    OnPanic:  target.PrintAndExit,
}
```

### Пример: программа для DOS

```go
// main_i8086.kn
package main

profile core

import (
    "kern/arch/i8086"
    "kern/dos"
    "kern/encoding"
    "kern/unsafe"
)

type Cell struct {
    ch   u8
    attr u8
}

var screen = unsafe.Map[[2000]Cell](i8086.Far(0xB800, 0))

func PutChar(x, y u16, c u8, attr u8) {
    requires x < 80 && y < 25
    screen[y*80+x] = Cell{c, attr}
}

func main() {
    dos.Print(encoding.CP866("Привет из Kern!\r\n"))     // CP866, $ добавляется автоматически
    for i, c := range []u8("HELLO") {
        PutChar(u16(i)+10, 5, c, 0x1E)
    }
}
```

Низший уровень стандартной библиотеки — тонкие обёртки над прерываниями:

```go
// dos/print_i8086.kn
package dos

profile core

import "kern/arch/i8086"

func Print(s dstring) {
    i8086.Int(0x21, i8086.Regs{AH: 0x09, DX: s.ptr})
}
```

### Код под конкретную архитектуру

Цель выбирается при сборке флагом `-target`, а не в коде: в заголовке пакета есть только `profile`. Код, зависящий от архитектуры, устроен так:

1. **Свой пакет команд у каждой архитектуры** — `kern/arch/i8086`, `kern/arch/armv7m`, `kern/arch/riscv32`, `kern/arch/riscv64`, `kern/arch/x86_64`, `kern/arch/avr`. Пакет генерируется из описания архитектуры (раздел 17), поэтому команды, регистры и их типы всегда совпадают с тем, что знает компилятор. Это обычные функции: `i8086.Int(0x21, i8086.Regs{AH: 0x09})`, `armv7m.WFI()`, `x86_64.ReadCR2()`. Компилятор знает, какие регистры портит каждая команда и какие у неё эффекты.
2. **Суффикс архитектуры в имени файла**, как в Go: `print_i8086.kn`, `write_armv7m.kn`. Компилятор берёт файлы для текущей цели и пропускает остальные; импорт пакета команд разрешён только в файлах с его суффиксом.
3. **Блок `asm`** на синтаксисе архитектуры с входами и выходами через структуру — для редких длинных последовательностей (код старта, переключение контекста). Ассемблер для него генерируется из того же описания архитектуры.

Именованных аргументов, как и в Go, нет: параметры с именами передаются структурой (`i8086.Regs{...}`, `timer.Config{...}`), а неуказанные поля получают нулевые значения.

### Размер int

`int` — машинное слово цели: 16 бит на i8086, 32 на `wasm32` и Cortex-M, 64 на x86-64. В переносимом коде по умолчанию используются типы с явным размером: `i8`…`i64`, `u8`…`u64`.

### GPU: шейдеры и вычисления

Шейдеры и вычислительные ядра для GPU пишутся на Kern в ограниченном подмножестве профиля `core`: без рекурсии, без косвенных вызовов, без аллокаций, с эффектом `GPU`.

| Цель | Для чего |
| --- | --- |
| `spirv` | Vulkan, OpenCL |
| `wgsl` | WebGPU в браузере |
| `msl` | Metal на iOS и macOS |

```go
gpu func Blur(img []simd.F32x4, out gpu.Out[simd.F32x4]) {
    i := gpu.GlobalID().x
    if i == 0 || i+1 >= u32(len(img)) {
        return
    }
    out[i] = (img[i-1] + img[i] + img[i+1]) / simd.F32x4Splat(3)
}

gpu.Dispatch(Blur, len(img), img, out)       // запуск: по потоку на элемент
```

Ядро исполняется тысячами потоков одновременно, поэтому правила доступа к данным у него свои:

1. **Входные срезы** — обычные значения, доступные только для чтения.
2. **Выход** — параметр типа `gpu.Out[T]`, а не `inout`. Поток пишет только в ячейку со своим номером: `out[gpu.GlobalID().x] = v`. Гонок нет по построению. Индекс как функция от номера потока допустим, если решатель доказал, что функция взаимно однозначна; это цель на развитие.
3. **Номер потока назначает GPU**, поэтому предусловия на него не пишутся: границы проверяются в теле ядра. Предусловия ядра относятся к размеру запуска и проверяются в точке вызова `gpu.Dispatch`.
4. **Атомарные операции и разделяемая память рабочей группы** (`gpu.Atomic[T]`, `gpu.Shared[T]`) для редукций и гистограмм — цель на развитие.

Типы данных общие для CPU и GPU, поэтому буферы передаются без ручного описания раскладки на двух языках.

## 13. Встраиваемые системы

Прошивки пишутся в профиле `core`, а специфика микроконтроллеров выражена через уже существующие механизмы: описание цели, эффекты и семантику значений. Новым понадобилось только объявление `interrupt`.

### Память в описании цели

Разметка flash и RAM — часть описания цели, а не отдельного linker-скрипта. Переполнение любой области — ошибка компиляции с разбивкой по пакетам.

```go
package stm32f103c8

import (
    "kern/arch"
    "kern/platform"
    "kern/svd"
    "kern/target"
)

const Description = target.Desc{
    Arch:     arch.ARMv7M,
    Platform: platform.Bare,
    Word:     32,
    Memory: []target.Region{
        {Name: "flash", At: 0x0800_0000, Size: 64 * KiB, Exec: true},
        {Name: "ram",   At: 0x2000_0000, Size: 20 * KiB},
    },
    Stack:    2 * KiB,
    Formats:  []target.Format{target.ELF, target.BIN, target.HEX},
    Device:   svd.Load("STM32F103.svd"),
    Provides: []Effect{Gpio, Uart, Timers, Interrupts, StaticAlloc, Tasks},
    Lacks:    []Effect{File},
    OnPanic:  target.Reset,
}
```

### Механизмы

| Механизм | Как работает |
| --- | --- |
| Регистры из SVD | Типы регистров и битовых полей генерируются из файлов производителя; доступ автоматически `volatile`, запись недопустимых значений не компилируется; отображение регистров (unsafe.Map) генерируется, в коде пользователя unsafe нет |
| Владение периферией | Каждый экземпляр периферии — свой выведенный эффект; компилятор вычисляет, из каких контекстов он используется (ниже) |
| Прерывания | `interrupt` — функция без эффектов `Alloc`, `Block` и `Panic`; таблица векторов генерируется автоматически |
| Общие данные | Переменная, доступная из прерывания и основного кода, должна быть атомарной или защищённой критической секцией; периферия — по тем же правилам |
| Анализ стека | Компилятор считает максимальную глубину стека для `main` и каждого прерывания с учётом вложенности и сравнивает с `stack` |
| Задачи | `go` создаёт статическую задачу планировщика с приоритетами; её размер известен при компиляции |
| Константы во flash | Таблицы, CRC и делители тактовой частоты вычисляются при компиляции |

### Владение периферией

Периферия — отображение железа, поэтому доступна как глобальное значение пакета `device`: `device.TIM2`, `device.USART1`, `device.GPIOC.Pin13`. Единственность экземпляра проверяется не типами, а анализом всей программы, так же как выводятся эффекты:

1. **Каждый экземпляр периферии — свой эффект.** `TIM2`, `USART1`, а там, где железо позволяет менять пины независимо (регистры атомарной установки и сброса), и отдельный пин. Гранулярность задаёт описание устройства.
2. **Контексты исполнения** — `main`, каждая задача и каждый обработчик `interrupt`. Компилятор вычисляет, в каких контекстах достижим эффект каждого экземпляра.
3. **Один контекст** — доступ без синхронизации. **Несколько** — только внутри критической секции `for t := range device.TIM2.Lock() {...}`; потолок приоритета компилятор вычисляет сам, как для мьютексов (раздел 8).
4. **Фаза инициализации.** `main` начинается с запрещёнными прерываниями и задачами. Обращения до `interrupts.Enable()` или `task.Run()` не конфликтуют ни с чем: в этот момент других контекстов ещё нет.

Ошибка показывает оба контекста: `TIM2 используется в main (после interrupts.Enable) и в interrupt TIM2 без критической секции`. Скопировать периферию и тем обойти проверку нельзя: копия обозначает тот же экземпляр и несёт тот же эффект.

### Пример: светодиод по таймеру

```go
package main

profile core

import (
    "kern/atomic"
    "kern/cpu"
    "kern/device"
    "kern/gpio"
    "kern/interrupts"
    "kern/timer"
)

var ticks atomic.U32

func main() {
    led := device.GPIOC.Pin13.Output(gpio.PushPull)              // инициализация: прерывания ещё запрещены
    device.TIM2.Start(timer.Config{Freq: Hz(2), Interrupt: true})
    interrupts.Enable()

    for {                                                        // TIM2 здесь не используется: владеет прерывание
        if ticks.Load()%2 == 0 { led.Low() } else { led.High() }
        cpu.WaitForInterrupt()
    }
}

interrupt TIM2() {
    device.TIM2.ClearUpdateFlag()
    ticks.Add(1)
}
```

### Пример: задачи

```go
func main() {
    led := device.GPIOC.Pin13.Output(gpio.PushPull)
    uart := device.USART1.Open(Baud(115200))

    go blink(led)
    go echo(uart)
    task.Run()
}

func blink(led inout gpio.Output) {
    for {
        led.Toggle()
        task.Sleep(500 * Millisecond)
    }
}
```

| Семейство | Архитектура | Особенность |

| AVR (Arduino Uno) | 8-битная гарвардская | 2 КБ RAM, отдельные указатели на flash и RAM |
| STM32, RP2040, nRF52 | ARM Cortex-M | самый массовый класс |

### Реальное время

Для систем жёсткого реального времени компилятор оценивает наихудшее время выполнения (WCET) прерываний и задач. Модель тактов берётся из описания архитектуры, ограничение записывается как контракт:

```go
interrupt ADC1() {
    ensures wcet.Within(20 * time.Microsecond)
    sample := device.ADC1.Read()
    buffer.Push(sample)
}
```

Если доказать ограничение не удалось, компилятор показывает самый долгий путь выполнения. Для процессоров с кэшем и конвейером оценка консервативна; точный анализ — цель на развитие.

## 14. Операционные системы

На Kern можно писать операционные системы любого масштаба: от DOS-подобной системы для 8086 до микроядра для RISC-V и x86-64. Основу даёт профиль `core`; для ОС добавляются уровни привилегий, типизированные адреса, ловушки, описание системных вызовов и примитивы многопроцессорности. Новое контекстное слово одно — `trap`.

### Механизмы

| Механизм | Как работает |
| --- | --- |
| Уровни привилегий | Привилегированные команды (таблицы страниц, запрет прерываний, MSR) дают выведенный эффект `Privileged`, который разрешён только пакетам ядра (профиль и `kern.mod`); граница ядра и пользовательского режима видна в типах |
| Типизированные адреса | `PhysAddr` и `VirtAddr` — разные типы; перепутать физический и виртуальный адрес нельзя |
| Ловушки | `trap` объявляет обработчик исключения процессора (page fault, деление на ноль, недопустимая команда); правила эффектов — как у `interrupt` |
| Переключение контекста | Один примитив на `asm` для сохранения регистров и смены стека; вокруг — типизированный поток ядра с объявленным размером стека |
| Системные вызовы | ABI описывается данными; из одного описания генерируются таблица вызовов в ядре и обёртки для программ |
| Многопроцессорность | Атомарные операции с явным порядком памяти, данные на процессор, спин-блокировки; семантика значений исключает гонки между ядрами |
| Загрузка | Цели для загрузочного сектора BIOS, Multiboot, UEFI и Device Tree на ARM и RISC-V |

### Пример: обработчик page fault

```go
// mm/fault_x86_64.kn
package mm

profile core

import (
    "kern/arch/x86_64"
    "kern/sched"

    "myos/frames"
)

trap PageFault(frame inout TrapFrame, code PageFaultCode) {
    addr := VirtAddr(x86_64.ReadCR2())           // VirtAddr
    space := sched.Current().AddressSpace()

    switch space.Lookup(addr) {
    case Lazy{region}:
        phys, err := frames.Alloc()
        if err != nil {
            sched.Kill(sched.Current(), OutOfMemory)
            return
        }
        space.Map(addr.PageStart(), phys, region.Flags)
    case Unmapped:
        sched.Signal(sched.Current(), SegFault{addr})
    }
}
```

Компилятор не даст передать `VirtAddr` туда, где ожидается `PhysAddr`, и проверит, что разобраны все варианты результата `Lookup`.

### Пример: описание системных вызовов

```go
package kernos

import "kern/abi"

const Syscalls = abi.Table{
    Convention: abi.ByArch{X86_64: "syscall", RISCV64: "ecall", I8086: "int 0x80"},
    Calls: []abi.Call{
        abi.Fn[func(fd Handle, buf []u8) (usize, error)]{No: 1, Name: "Write", Effects: Console},
        abi.Fn[func(fd Handle, buf inout []u8) (usize, error)]{No: 2, Name: "Read", Effects: Console},
        abi.Fn[func(path string, mode OpenMode) (Handle, error)]{No: 3, Name: "Open", Effects: File},
        abi.Fn[func(code i32)]{No: 4, Name: "Exit"},
    },
}
```

Из этого описания ядро получает таблицу диспетчеризации, а программы — функции с эффектами. Вызов `Open` даёт программе эффект `File`; если цель или `kern.mod` его запрещают, сборка не пройдёт.

### Инварианты ядра в контрактах

Контракты позволяют записать и проверить инварианты, которые в обычных ядрах держатся на дисциплине:

```go
func (s inout AddressSpace) Map(v VirtAddr, p PhysAddr, f PageFlags) {
    requires v.IsPageAligned() && p.IsPageAligned()
    requires !(f.User && kernel.Owns(p))   // память ядра не отображается в пространство пользователя
    ensures  s.Translate(v) == Some(p)
    ...
}
```

Это не полная формальная верификация уровня seL4, но заметный шаг к ней, и контракты пишутся вместе с кодом, а не в отдельной системе доказательств.

### Возможности и микроядро

Эффекты Kern по сути и есть capabilities — та же модель, на которой построены seL4 и Zircon (Fuchsia). Драйвер получает только переданные ему порты, области памяти и прерывания; проверка выполняется при компиляции, а в микроядре дублируется во время выполнения.

### ОС как новая платформа

ОС, написанная на Kern, сама становится платформой в описаниях целей. Её системные вызовы видны приложениям как эффекты, а описание ABI — общий пакет для ядра и программ.

### Масштабы

| Вид | Цель | Пример |
| --- | --- | --- |
| DOS-подобная система | i8086, реальный режим | однозадачная система с файловой системой FAT |
| RTOS | Cortex-M, RISC-V 32 | планировщик с приоритетами, уровня FreeRTOS или Zephyr |
| Микроядро | x86-64, riscv64, arm64 | драйверы в пространстве пользователя, IPC по возможностям |
| Unikernel | x86-64 в виртуальной машине | приложение и минимальное ядро в одном образе |

## 15. Мобильные приложения

Приложения для iPhone и Android пишутся в профиле `ui` тем же кодом, что и веб-интерфейсы: `Update` и `View` не меняются, меняются цель сборки и набор доступных эффектов. Компиляция заранее (AOT) в машинный код arm64 соответствует требованиям обеих платформ, включая запрет JIT на iOS.

### Цели

| Цель | Архитектуры | Результат | Мост к системе |
| --- | --- | --- | --- |
| `ios` | arm64 | Mach-O в составе .ipa | рантайм Objective-C через внешние функции (раздел 11) |
| `ios-sim` | arm64, x86\_64 | .app для симулятора | то же |
| `android` | arm64, x86\_64 | .so в составе APK или AAB | таблица JNI через внешние функции (раздел 11) |

### Отрисовка интерфейса

Дерево `ui.Node` рисуется собственным рендером Kern — это единственный способ отрисовки на всех целях, как во Flutter. Нативных элементов интерфейса Kern не использует: их API огромны и пришлось бы описывать вручную на каждой платформе, Jetpack Compose недоступен из машинного кода, а у DOS и микроконтроллеров нативных элементов нет вовсе.

| Бэкенд рендера | Цели |
| --- | --- |
| GPU | Metal (iOS, macOS), Vulkan (Android, Linux), Direct3D или Vulkan (Windows), WebGPU (браузер) |
| Программный растеризатор | дисплеи микроконтроллеров, фреймбуфер, VGA в DOS |
| Текстовый режим | DOS 80×25, терминал |

Движок раскладки работает и в пикселях, и в символьных ячейках, поэтому один и тот же экран запускается в браузере, на iPhone и в DOS.

От платформы берётся только то, чего нельзя сделать самому, через внешние функции (раздел 11):

- **доступность:** дерево интерфейса экспортируется в VoiceOver, TalkBack и ARIA в браузере;
- **ввод текста:** системная клавиатура, IME, автозаполнение;
- **системные диалоги:** выбор файла, запросы разрешений, буфер обмена;
- **встраивание нативного вида** как исключение: карта, веб-страница, видеоплеер.

### Возможности устройства как эффекты

Системные API представлены эффектами: `Camera`, `Location`, `Notifications`, `Contacts`, `Photos`, `Bluetooth`, `Background`, `Network`.

Из эффектов приложения автоматически генерируются разрешения: записи `NS...UsageDescription` в Info.plist и `uses-permission` в AndroidManifest.xml. Забыть объявить разрешение или запросить лишнее невозможно: список разрешений — это объединение эффектов кода. Тексты-объяснения для пользователя задаются в манифесте приложения, и без них сборка не пройдёт.

### Жизненный цикл

Состояния приложения — явный `enum`, переходы обрабатываются исчерпывающим `switch`:

```go
type Lifecycle enum {
    Launching
    Active
    Inactive
    Background{deadline Duration}
    Terminating
}
```

Работа в фоне требует эффекта `Background`, и компилятор проверяет, что фоновые задачи укладываются в объявленные ограничения платформы.

### Пример

```go
package scanner

profile ui

import (
    "kern/camera"
    "kern/cmd"
    "kern/ui"
)

type State struct {
    codes []string
}

type Msg enum {
    Scan
    Scanned{code string}
    Clear
}

func Update(s State, m Msg) (State, Cmd) {
    switch m {
    case Scan:          return s, camera.ScanBarcode(Scanned)
    case Scanned{code}: return State{append(s.codes, code)}, cmd.None
    case Clear:         return State{}, cmd.None
    }
}

func View(s State) ui.Node {
    return ui.Column(
        ui.List(s.codes, ui.Text),
        ui.Row(
            ui.Button("Сканировать", Scan),
            ui.Button("Очистить", Clear),
        ),
    )
}
```

На iOS и Android эффект `Camera` даёт нативную камеру и разрешение в манифесте; в вебе — `getUserMedia` и запрос браузера.

### Манифест приложения

```go
package scanner

import "kern/app"

const Manifest = app.Desc{
    ID:      "com.example.scanner",
    Name:    "Сканер",
    Version: "1.2.0",
    Icon:    "assets/icon.svg",                 // размеры генерируются автоматически
    Usage: map[Effect]string{
        Camera: "Камера нужна для сканирования штрихкодов",
    },
    IOS:     app.IOS{MinVersion: "16.0", Team: "ABCDE12345"},
    Android: app.Android{MinSDK: 26},
}
```

### Привязки к системным API

Привязки к Objective-C, Swift и Java/Kotlin объявляются так же, как функции динамических библиотек (раздел 11), без генераторов и SDK. Каждой привязке приписан эффект, поэтому прямой вызов системного API не обходит контроль возможностей.

### Сборка, подпись и тесты

- Подпись приложения для iOS требует сертификатов Apple и, на практике, macOS с инструментами Xcode; для Android достаточно ключа подписи и Android SDK.
- `kern build -target ios` собирает .ipa, `kern build -target android` — AAB или APK.
- `kern run -emu ios-sim` и `kern run -emu android` запускают приложение в симуляторе и эмуляторе.
- Визуальные тесты рендерят экраны на обеих платформах и сравнивают с эталонами.

### Принципы

- Пакет без эффектов автоматически доступен во всех профилях.
- Все интерфейсы ввода-вывода (`Reader`, `Writer`) общие для всех профилей; реализации зависят от цели.
- Пакеты, специфичные для железа и платформ, — обычные пакеты на Kern в стандартной библиотеке или в проекте, а не код компилятора.
- В `core` нет скрытых аллокаций: функции, которым нужна память, принимают буфер явно.

## 17. Компилятор

Компилятор Kern — это не только транслятор, но и собеседник: он отдаёт машиночитаемую диагностику с исправлениями и отвечает на запросы о семантике проекта.

### Конвейер

1. **Разбор** исходника в дерево с каноническим форматированием.
2. **Типизированное дерево**: разрешение имён, вывод типов; эффекты выводятся по всей программе.
3. **Проверки**: эффекты против профиля и цели, контракты через встроенный решатель, исчерпывающие `switch`, владение.
4. **Общее SSA-представление** с эффектами, одинаковое для всех целей.
5. **Оптимизации**, не зависящие от архитектуры.
6. **Лоуеринг под архитектуру** по декларативным правилам выбора команд.
7. **Запись формата**: flat, MZ, ELF, PE, Mach-O, wasm, HEX, UF2.
8. **Отчёты**: размер по пакетам, глубина стека, карта памяти.

### Диагностика

Каждое сообщение — структура: место, код ошибки, причина, предлагаемые исправления в виде готовых правок. Человеку показывается читаемый текст, ИИ получает JSON. Проверка инкрементальная и укладывается в доли секунды для изменённой функции.

### Семантический API

Компилятор отвечает на запросы как сервис:

- кто вызывает эту функцию;
- какие эффекты достижимы из этой точки;
- что сломается, если изменить этот тип;
- какое условие контракта не доказано и почему;
- чем отличаются публичный API, эффекты и контракты двух версий кода.

### Решатель

Контракты проверяет собственный решатель: сначала на Go вместе с прототипом компилятора, затем на Kern. Внешних решателей вроде Z3 и cvc5 в среде нет, поэтому в поставке не появляется C++, а `kern` остаётся одним исполняемым файлом.

Возможности наращиваются по этапам:

| Этап | Что доказывается | Типичные контракты |
| --- | --- | --- |
| 1 | линейная целочисленная арифметика | диапазоны, границы массивов, `lo <= hi` |
| 2 | битовые векторы | отсутствие переполнения, `bits.WrappingAdd`, маски регистров |
| 3 | массивы и срезы | содержимое после копирования, инварианты циклов |
| 4 | `enum` и `Option` | какой вариант возможен в данной точке |
| 5 | ограниченные кванторы | «для всех i в диапазоне» |

- **Детерминизм.** Лимит задаётся числом шагов, а не временем, поэтому результат одинаков на любой машине.
- **Понятный отказ.** Если условие не доказано, компилятор называет его и показывает контрпример, если он найден.
- **Скорость.** Доказанные условия кэшируются локально по хэшу условия; при неизменном коде повторное доказательство не нужно.

### Добавление архитектуры

Новая архитектура описывается тремя пакетами данных, без правки компилятора:

1. **Модель машины**: регистры, размеры, выравнивание, виды указателей, соглашения о вызовах.
2. **Правила выбора команд**, например: сложение двух 16-битных значений → `ADD r16, r/m16`. Генератор кода собирается из правил автоматически.
3. **Формальная семантика команд** (по образцу языка Sail). Позволяет автоматически проверять корректность правил выбора команд. Из неё же генерируются ассемблер, пакет команд архитектуры и встроенный интерпретатор для тестов.

Формат бинарника — такой же плагин: формат `.COM` занимает около сотни строк, это плоский образ с началом в `0x100` без таблицы релокаций.

Формальная семантика особенно важна для работы ИИ: бэкенд можно написать по документации процессора, а машина проверит его на соответствие спецификации.

### Самосборка

Первая версия компилятора пишется на Go, затем компилятор переписывается на самом Kern. Это лучший тест языка на большой системной задаче.

1. **Этап 0.** Компилятор пишется на Go. Синтаксис Kern основан на Go, поэтому парсер, структуры данных и большая часть логики потом переносятся на Kern почти построчно. Кроме того, Go даёт быструю сборку, простую кросс-компиляцию, один исполняемый файл без зависимостей и purego как проверенный образец вызова внешнего кода.
2. **Этап 1.** Компилятор переписывается с Go на Kern (с помощью kern port) и собирается версией на Go.
3. **Этап 2.** Компилятор этапа 1 собирает сам себя; результат должен совпасть побайтово.
4. **Этап 3.** Версия на Go сохраняется в архиве для раскрутки с нуля и проверки на закладки в компиляторе.

## 18. Рантайм

Рантайм Kern маленький: в нём нет сборщика мусора, рефлексии и информации о типах во время выполнения. Он написан на самом Kern (профиль `core`), лежит исходниками и компонуется по частям — платишь только за то, что используешь. Программа без задач не содержит планировщика, а программа под DOS без задач получает лишь код старта и обработчик паники.

### Отличия от рантайма Go

| Компонент Go | В Kern |
| --- | --- |
| сборщик мусора | нет |
| рефлексия во время выполнения | нет, только при компиляции (`meta`) |
| информация о типах во время выполнения | нет, только отладочные таблицы в отдельном файле |
| планировщик горутин | свой для каждого профиля |
| растущие копированием стеки | нет: размер стека вычисляется статически, иначе резерв с защитной страницей |
| счётчики ссылок | встроенный код копирования при записи, а не отдельная служба |

### Состав по профилям

| Часть | `core` | `app` | `ui` |
| --- | --- | --- | --- |
| код старта | из описания цели: вектор сброса, точка входа .COM, Multiboot | точка входа ОС | точка входа платформы |
| память | только статическая, пулы фиксированного размера | аллокатор общего назначения и арены | то же |
| задачи | статический планировщик с приоритетами | M:N поверх потоков ОС с асинхронным вводом-выводом | то же плюс главный поток интерфейса |
| паника | по `OnPanic` цели: сброс, остановка, выход в DOS | сообщение со стектрейсом и завершение | то же |
| внешние функции | `ffi.At`, статическая компоновка | плюс загрузка динамических библиотек при старте | то же |
| интерфейс | — | — | рендер, раскладка, доступность, ввод текста |

Только при разработке, в выпускную сборку не попадают: детерминированный планировщик для тестов и интерпретатор для горячей перезагрузки.

### Стеки задач

1. **Размер стека задачи вычисляется статически.** Компилятор видит всю программу, поэтому для большинства задач максимальная глубина известна: рекурсии нет, косвенные вызовы ограничены известным набором функций.
2. **Если вычислить нельзя** (рекурсия, неограниченная глубина), задача в `app` получает резерв виртуальной памяти с защитной страницей: физическая память выделяется по мере использования, переполнение ловится, а не портит память. Компилятор сообщает, каким задачам понадобился такой резерв.
3. **В `core`** рекурсия в задачах и прерываниях без доказанной границы глубины — ошибка компиляции.

## 19. Пакеты

Пакет — каталог с исходниками, как в Go. Пакетного менеджера и внешних зависимостей нет. Программа импортирует только:

1. **Стандартную библиотеку** — пути под `kern/`: `kern/fmt`, `kern/time`, `kern/http`. Она поставляется вместе с `kern` и версионируется вместе с ним. В неё входят и описания целей и пакеты команд архитектур: `kern/target/stm32f103c8`, `kern/arch/i8086`.
2. **Пакеты самого проекта** — пути под именем модуля из `kern.mod`: `myprogram/forms`, `myprogram/logic`.

Других путей нет: импорт по внешнему адресу (`github.com/...`) — ошибка компиляции. Имя пакета в коде — последний элемент пути, как в Go: после `import "kern/fmt"` пишется `fmt.Sprint(...)`.

Два пространства не пересекаются, поэтому стандартная библиотека может расти, не ломая проекты: появление `kern/forms` никак не задевает `myprogram/forms`. По строке импорта сразу видно, свой это код или поставляемый с `kern`.

### Чужой код

Чужая библиотека переносится в проект как обычный код: копируется в каталог проекта (например, `myprogram/jsonparse`), импорты внутри неё переписываются под новый путь, при необходимости переводится с Go или C через `kern port` (раздел 21), и дальше живёт как код проекта — правится и проверяется наравне со своим.

- Лицензия копируется вместе с кодом; происхождение фиксирует человек.
- Зависимости библиотеки не подтягиваются. Если перенесённый код импортирует что-то ещё, компилятор сообщает об этом, и человек решает: перенести и это или переписать код без него.
- Эффекты перенесённого кода выводятся как у любого другого, поэтому сетевой вызов в «парсере JSON» виден в `kern query` и упирается в ограничения профиля.

### Свои цели и устройства

Новое устройство, платформа или архитектура описывается пакетом в проекте, например `myprogram/boards/myboard`. `-target` ищет описание сначала в проекте, затем в стандартной библиотеке.

### Что это даёт и чего стоит

- Сборка без сети тривиальна: весь код лежит в проекте и в `kern`.
- Нет решателя версий, ромбовидных зависимостей, подписей и реестров.
- Каждая внешняя зависимость — осознанное решение человека.
- Цена: исправления в оригинале переносятся вручную, а переиспользование кода между проектами — копированием.

Команда быстрого копирования внешней библиотеки в проект с записью источника возможна позже, но в текущий объём не входит.

## 20. Инструменты

Вся работа со средой идёт через одну команду `kern`, как `go` в Go. Каждая подкоманда выдаёт результат и в читаемом виде, и в JSON.

### Команды

| Команда | Что делает |
| --- | --- |
| `kern build [-target T]` | Сборка без обращения к сети |
| `kern check` | Типы, эффекты, контракты без генерации кода |
| `kern fmt` | Каноническое форматирование |
| `kern test` | Модульные, property-based и визуальные тесты |
| `kern run [-emu E]` | Запуск, в том числе в эмуляторе |
| `kern flash` | Прошивка устройства через SWD/JTAG или UF2 |
| `kern size` | Flash, RAM и стек по пакетам |
| `kern query` | Запросы к семантическому API |
| `kern diff` | Семантический диф двух версий кода: API, эффекты, контракты |

### Тестирование

- Тесты — обычные функции в файлах `_test.kn`, как в Go; примеры из документации тоже исполняются как тесты.
- `Clock`, `Random` и ввод-вывод подменяются в тестах: компилятор знает, какой код от них зависит.
- Детерминированный планировщик перебирает чередования задач для поиска гонок и взаимоблокировок.
- Запись и воспроизведение выполнения для отладки.
- UI-компоненты рендерятся в тесте и сравниваются с эталоном.

### Эмуляторы

Эмуляторы для тестов встроены в `kern` и не требуют сторонних программ. Интерпретатор каждой архитектуры генерируется из формального описания семантики её команд — того же, из которого строятся бэкенд, ассемблер и пакет команд (раздел 17).

| Цель | Встроенная проверка |
| --- | --- |
| 8086, Cortex-M, AVR, RISC-V | интерпретатор из описания архитектуры плюс модели периферии: таймер, UART, GPIO, текстовая видеопамять, `int 21h` |
| web | интерпретатор WebAssembly; интерфейс рендерится собственным рендером в изображение, браузер не нужен |
| iOS, Android | логика и интерфейс проверяются на машине разработчика тем же рендером |

Тесты проверяют наблюдаемое поведение: пин переключается с нужной частотой, UART выдал строку, на экране DOS появился текст, экран приложения совпал с эталоном. Встроенные эмуляторы не дают точности до такта, полной модели периферии и проверки системной интеграции (камера, разрешения, поведение настоящего iOS). Для этого внешние эмуляторы (DOSBox, QEMU, Renode), симуляторы Apple и Android и реальные устройства остаются опцией.

### Детерминизм

- Сборка воспроизводима побайтово при одинаковых исходниках и версии компилятора.
- Сборка никогда не обращается к сети.
- Версия языка фиксируется редакцией в `kern.mod`; переход на новую редакцию сопровождается автоматическими миграциями.

### Отладка

| Цель | Отладочная информация | Отладчик |
| --- | --- | --- |
| Linux, macOS | DWARF | встроенный в `kern debug`, GDB и LLDB через протокол |
| Windows | PDB / CodeView | то же |
| DOS | CodeView | через отладочный порт DOSBox |
| web | source maps, DWARF для WebAssembly | инструменты браузера |
| микроконтроллеры | DWARF + SVD | SWD/JTAG через `kern debug -probe` |

- Стектрейсы с именами функций и строками на всех целях, включая `core` (по таблице в отдельном файле, чтобы не занимать flash).
- Отладчик показывает значения типов Kern: `enum` с вариантом, `Option`, `Secret` как `***`.
- Запись и воспроизведение: `kern run -record` сохраняет недетерминированные входы, `kern debug -replay` повторяет выполнение точно.
- Отладчик доступен через машиночитаемый протокол, чтобы ИИ мог ставить точки останова и читать состояние.

### Горячая перезагрузка

Для профиля `ui` изменения в `View` и `Update` применяются к работающему приложению без перезапуска и с сохранением состояния. Если изменился тип `State`, среда предлагает функцию миграции или перезапуск.

| Где | Как работает |
| --- | --- |
| браузер, десктоп, симулятор iOS, Android (отладочная сборка) | подгрузка нового машинного кода |
| iOS-устройство (только отладочная сборка) | код интерфейса исполняется встроенным интерпретатором WebAssembly, поэтому его можно подменять; работает медленнее выпускной сборки |
| выпускные сборки | горячей перезагрузки нет: всё компилируется заранее, как требует App Store |

### Документация

`kern doc` генерирует документацию из исходников: сигнатуры, эффекты, контракты, примеры. Примеры в документации — исполняемые тесты, поэтому не устаревают. Для ИИ та же информация выдаётся в машиночитаемом виде.

### Дополнительные команды

| Команда | Что делает |
| --- | --- |
| `kern debug` | Отладка локально, на устройстве или в эмуляторе |
| `kern doc` | Документация в HTML и JSON |
| `kern dev` | Запуск с горячей перезагрузкой |
| `kern port` | Перенос кода с Go и C (раздел 21) |

## 21. Работа с ИИ

Среда Kern рассчитана на то, что основную часть кода пишет ИИ, а человек ставит задачи и проверяет результат. Для этого в среде есть три механизма: требования как исполняемые критерии, перенос существующего кода и машиночитаемая спецификация языка.

### Требования как исполняемые критерии

Требование и его проверка разделены. Текст требований лежит в строчном файле `REQUIREMENTS` в корне проекта, а проверки — обычные тесты в файлах `_test.kn`, как в Go. Отдельного синтаксиса для требований нет.

```
// REQUIREMENTS
AUTH-3  Пользователь входит по логину и паролю
        tests: TestLoginSuccess, TestLoginWrongPassword
AUTH-4  После пяти неудачных попыток вход блокируется на 15 минут
        tests: TestLockAfterFiveFailures, TestUnlockAfter15Minutes
```

```go
// auth_test.kn
func TestLockAfterFiveFailures(t inout testing.T) {
    for range 5 {
        _, err := Login("alice", wrongPassword)
        t.Expect(err == ErrDenied)
    }
    _, err := Login("alice", rightPassword)
    t.Expect(err == ErrLocked)
}
```

`kern test` проверяет связь: у каждого требования есть тесты, все они существуют и проходят. Текст требований и список тестов к ним — это спецификация, которую читает человек; тесты и код пишет ИИ.

### Перенос существующего кода

`kern port` переносит код с Go и C. ИИ выполняет перевод, компилятор проверяет результат, а тесты исходного проекта прогоняются на обеих версиях.

| Источник | Что переносится автоматически | Что требует решения |
| --- | --- | --- |
| Go | синтаксис, структуры, интерфейсы, горутины и каналы, обработка ошибок, пути импорта (`"fmt"` → `"kern/fmt"`) | указатели и `nil`-указатели, `init()`, `interface{}` |
| C | функции, структуры, арифметика | ручное управление памятью, препроцессор, неопределённое поведение |

Для Go перенос особенно реален из-за близкого синтаксиса. Без такого инструмента новый язык начинает с пустой экосистемы.

### Машиночитаемая спецификация

Спецификация языка, стандартной библиотеки и диагностик публикуется в виде, удобном для моделей: формальная грамматика, примеры к каждому правилу, коды ошибок с вариантами исправления. Она версионируется вместе с редакциями языка, поэтому ИИ работает по точной версии, а не по устаревшим знаниям.

### Протокол среды

Все инструменты `kern` — компилятор, семантический API, отладчик, тесты, эмуляторы — доступны через единый машиночитаемый протокол. ИИ работает со средой как с набором инструментов, а не через разбор текстового вывода.

## 22. Архитектура реализации

Прототип — один исполняемый файл `kern`, написанный на Go без cgo. Компилятор видит программу целиком (весь код лежит в проекте и стандартной библиотеке), но кэширует результаты по пакетам.

### Пакеты реализации

| Пакет | Ответственность |
| --- | --- |
| `syntax` | лексер, парсер, дерево, каноническое форматирование |
| `types` | разрешение имён, проверка типов, дженерики, `enum`, исчерпывающий `switch` |
| `effects` | вывод эффектов по графу вызовов всей программы, проверка границ |
| `verify` | условия из контрактов, встроенный решатель |
| `ir` | общее SSA-представление с эффектами |
| `lower` | семантика значений, копирование при записи, `enum`, проверки переполнения и границ |
| `arch/...` | описания архитектур; из них — выбор команд, ассемблер, пакеты команд, интерпретаторы |
| `link` | компоновщик и запись форматов: flat, MZ, ELF, PE/COFF, Mach-O, wasm, HEX, UF2 |
| `interp` | встроенные интерпретаторы для тестов |
| `diff` | семантический диф двух версий кода |
| `server` | машиночитаемый протокол и LSP |
| `cmd/kern` | командная строка |

### Вывод эффектов

Вывод идёт в два шага.

1. **Сводки по пакетам.** Граф вызовов пакета разбивается на компоненты сильной связности (рекурсия), затем обходится снизу вверх с объединением множеств эффектов до неподвижной точки. Вызов параметра даёт в сводке ссылку на его эффекты, а не конкретное множество. Сводка зависит только от пакета и сводок зависимостей, поэтому кэшируется по их хэшам.
2. **Подстановка по всей программе.** При сборке ссылки заменяются эффектами конкретных функций и реализаций, а открытые ссылки на интерфейсы — объединением реализаций, попавших в структуры данных. Этот шаг дешёвый и проверяет ограничения профилей, целей и обработчиков `interrupt`.

### Понижение семантики значений

| Конструкция | Как компилируется |
| --- | --- |
| `inout` | указатель на время вызова; компилятор гарантирует, что других доступов к значению в это время нет |
| большое значение в аргументе | передаётся по указателю без копии, если вызываемый его не изменяет |
| типы синхронизации | указатель на объект; в кадре создавшей функции, если дескриптор не уходит в `Detach`, иначе в куче с атомарным счётчиком |
| строки, срезы, словари | заголовок и буфер со счётчиком ссылок; запись в разделяемый буфер сначала копирует; счётчик атомарный только для значений, переданных между задачами |
| `enum` | тег и объединение вариантов; `Option[T]` без тега, если у `T` есть недопустимое значение |
| срез | указатель, длина и ёмкость размером в машинное слово |
| проверки переполнения и границ | переход к обработчику паники цели; удаляется, если решатель доказал безопасность |

### ABI

- Внутренний ABI Kern задаётся описанием архитектуры и может отличаться от C ради эффективности.
- Внешние функции и колбэки используют C ABI цели.
- Стабильность внутреннего ABI между версиями компилятора не обещается: пакеты всегда компилируются из исходников.

### Кэш сборки

Ключ кэша — хэш исходников пакета, хэши зависимостей, цель и версия компилятора. Повторная сборка без изменений сводится к компоновке.

## 23. Сборка и проекты

Проект — каталог с файлом `kern.mod`. Имя модуля — короткий идентификатор без точек и слэшей, оно же корень путей импорта пакетов проекта; имя `kern` зарезервировано. Переименование модуля — механическая правка всех импортов. В `kern.mod` записаны имя модуля, редакция языка, цели по умолчанию и ограничения эффектов для пакетов проекта.

### kern.mod

```
module  weather
kern    1.0
targets linux-x86_64, macos-arm64, web

effects (
    jsonparse/...  deny  {Network, File, Panic}
    kernel/...     allow {Privileged}
)
```

`effects` уточняет ограничения профилей для отдельных пакетов: `deny` запрещает эффекты, `allow` разрешает те, что по умолчанию закрыты (например, `Privileged`). Это главная защита для перенесённого чужого кода: парсер, которому запрещена сеть, не соберётся, если в нём появится сетевой вызов.

### Структура проекта

```
weather/
├── kern.mod
├── REQUIREMENTS
├── main.kn
├── server/
│   ├── server.kn
│   ├── server_linux.kn
│   └── server_test.kn
├── jsonparse/              // перенесённая чужая библиотека — обычный пакет проекта
└── internal/
```

Пакет — каталог.

### Выбор файлов

1. `_test.kn` — только при запуске тестов.
2. Суффикс платформы и архитектуры (`_linux`, `_dos`, `_i8086`, `_dos_i8086`) — только для соответствующей цели, как в Go.
3. Профиль пакета ограничивает, под какие цели он собирается вообще.

### Несколько целей

`kern build -target dos-com,stm32f103c8,web` собирает все цели за один запуск; не зависящие от цели проверки (типы, эффекты, контракты) выполняются один раз. Результаты — в `out/<цель>/`.

### Воспроизводимость

В выходных файлах нет меток времени и путей сборки. `kern build -verify` собирает дважды и сравнивает результат побайтово.

## 24. Протокол среды и редакторы

Все возможности `kern` доступны через один машиночитаемый протокол: JSON-RPC 2.0 поверх стандартного ввода и вывода, как у LSP. Его используют и ИИ, и редакторы.

- `kern serve` — сервер протокола для ИИ и инструментов.
- `kern lsp` — стандартный LSP для редакторов (VS Code, Neovim, JetBrains): ошибки с готовыми исправлениями, переход к определению, выведенные эффекты при наведении, форматирование.

### Операции для ИИ

| Операция | Что делает |
| --- | --- |
| `check` | типы, эффекты, контракты; диагностика с кодами и исправлениями |
| `query` | кто вызывает, откуда эффект, что сломается при изменении |
| `prove` | доказать условие контракта или вернуть контрпример |
| `test` | запустить тесты, в том числе во встроенных интерпретаторах |
| `run` | запустить программу на цели или в интерпретаторе, вернуть наблюдаемое поведение |
| `debug` | точки останова, пошаговое выполнение, чтение состояния |
| `diff` | семантический диф двух версий кода: API, эффекты, контракты |
| `requirements` | связь требований с тестами: требования без тестов, несуществующие и падающие тесты |

Ответы детерминированы; коды ошибок стабильны в пределах редакции языка. Схема протокола публикуется вместе со спецификацией.

## 25. Тестирование самой среды

Компилятор пишет в основном ИИ, поэтому проверки самого `kern` должны быть такими же механическими и решающими, как проверки пользовательского кода.

| Вид проверки | Что проверяет |
| --- | --- |
| набор соответствия | на каждое правило спецификации — примеры «компилируется» и «ошибка с кодом X»; общий для версии на Go и версии на Kern |
| эталонные программы | для каждой цели — программа и ожидаемое наблюдаемое поведение во встроенном интерпретаторе |
| перекрёстная проверка бэкендов | результат бэкенда исполняется в интерпретаторе архитектуры и сравнивается с интерпретацией IR |
| сравнение с Go | программы из общего подмножества (без `enum`, `inout`, контрактов) прогоняются через Go и Kern, вывод должен совпасть |
| фаззинг | парсер, проверка типов, решатель, компоновщик: случайные входы не должны ронять `kern` |
| проверка решателя | каждое «доказано» сопровождается сертификатом, который подтверждает небольшой независимый проверщик |
| самосборка | этапы 0–2 из раздела 17 и побайтовое совпадение результата |
| производительность | время компиляции, размер бинарников, скорость кода по целям; регрессии блокируют слияние |
| внешние оракулы | интерпретаторы архитектур — против QEMU и наборов тестов процессоров; интерпретатор WebAssembly — против официального набора тестов; вывод компоновщика — против стандартных утилит разбора форматов; внешние инструменты только в тестах среды, не в поставке |

## 26. Вне рамок

Эти возможности сознательно не входят в Kern. Предложения добавить их стоит отклонять, пока не изменится сам принцип, из-за которого они исключены.

| Не делаем | Почему |
| --- | --- |
| сборщик мусора | семантика значений и арены; предсказуемая память |
| макросы | нарушают локальность; есть вычисления при компиляции |
| исключения, `try`, `?` | обработка ошибок как в Go |
| перегрузка операторов, наследование, методы у встроенных типов | как в Go; простота |
| рефлексия во время выполнения | рефлексия только при компиляции |
| JIT | только заранее скомпилированный код; интерпретатор — лишь в отладке |
| компилятор C, разбор заголовков, генераторы привязок | внешний код в стиле purego |
| центральный реестр пакетов, прокси, облачные сервисы | независимость от сторонних сервисов |
| пакетный менеджер и импорт внешних библиотек | чужой код переносится в проект и становится его кодом; команда быстрого копирования — возможно, позже |
| нативные элементы интерфейса | собственный рендер |
| совместимость с исходниками Go без переноса | вместо этого `kern port` |
| стабильный бинарный ABI между версиями | пакеты всегда собираются из исходников |

## 27. Риски, решения и план прототипа

Главный риск — расползание: каждое расширение Go по отдельности разумно, а вместе они могут превратить язык в C++. Прототип должен как можно раньше проверить, что одно подмножество языка компилируется в три очень разных мира. Объём среды огромен, поэтому план (ниже) разбит на мелкие шаги с автоматическими критериями готовности.

### Риски

| Риск | Смягчение |
| --- | --- |
| Расползание синтаксиса | Закрытый перечень новизны (раздел 3): каждая новая конструкция — отдельное решение в таблице ниже |
| Объём среды: от DOS до iOS слишком много для одной команды | Мелкие шаги с автоматическими критериями готовности; независимые реализации как оракулы; описания целей и платформ — данные на Kern, которые может писать ИИ |
| Собственный решатель не доказывает сложные контракты | Наращивание возможностей по этапам; инварианты и `assert` в сложных местах; лимит по шагам, а не по времени |
| Сегментная память 8086 усложняет SSA и оптимизации | Вид указателя встречается только внутри `unsafe` и пакетов архитектур; простой генератор кода достаточен для .COM |
| Семантика значений непривычна Go-разработчикам | Хорошие сообщения компилятора, `kern port`, примеры переноса с Go |
| Мало обучающих данных для ИИ по новому языку | Синтаксис близок к Go; машиночитаемая спецификация с примерами к каждому правилу |
| Многослойная стандартная библиотека | Профили и эффекты честно показывают, что доступно на цели |
| Объявление внешней функции не совпадает с реальной библиотекой | Объявления собраны в одном месте пакета; тесты на границе; изменения объявлений отдельно в семантическом дифе |
| Требования магазинов приложений и подпись под iOS | Сборка через инструменты Apple на macOS; без JIT, только AOT |
| Prompt injection в чужом коде, который ИИ переносит в проект | Механические проверки решающие; эффекты перенесённого кода видны в инструментах |

### Принятые решения

| Вопрос | Решение |
| --- | --- |
| Контракты | Отдельные позиционные строки `requires`, `ensures`, `invariant`; без блока `contract` |
| Пути импорта | Стандартная библиотека под kern/ (kern/fmt, kern/arch/i8086), проект под именем модуля (myprogram/forms); других путей нет; имя модуля — идентификатор без точек, kern зарезервировано |
| Пакеты | Пакетного менеджера и внешних импортов нет; стандартная библиотека с kern; чужой код копируется в проект и становится его кодом |
| Бюджет новизны | Закрытый перечень конструкций в разделе 3, а не только число ключевых слов |
| Семантика invariant | Инвариант цикла — инвариант заголовка, на выходе подставляется конечное значение индекса; инвариант типа — на границах функций; тип, чьё нулевое значение нарушает инвариант, нулевого значения не имеет |
| Обработка ошибок | Как в Go, `if err != nil`; без `try` |
| Решатель | Собственный, сначала на Go, затем на Kern; без Z3 и cvc5 |
| Сборщик мусора | Нет; копирование при записи и арены |
| Описания целей и манифестов | Константы на Kern; `kern.mod`, `REQUIREMENTS` — строчный формат как у `go.mod` |
| Переполнение в `core` | Через эффект `Panic`; поведение паники задаёт цель |
| Внешний код | В стиле purego; `ffi.Library` и `ffi.Static` везде, где физически возможно |
| Отрисовка UI | Только собственный рендер |
| Происхождение и утверждение кода | Вне архитектуры: человек проверяет результат обычными средствами; механизма утверждений нет |
| Язык компилятора | Go, затем Kern |
| Название и расширение | Kern, для поиска и адресов kernlang; файлы `.kn` |
| Изменение частей значения | Срезы, поля и словари — как в Go; свои контейнеры — итератором range-over-func с inout-доступом (for s := range m.Lock()); без проекций и методов с func(inout T) |
| Эффекты | Выводятся компилятором; слова uses нет; ограничения только на границах; сводки по пакетам с параметрическими ссылками, эффект принадлежит тому, кто передал функцию |
| Глобальное состояние | Только атомарные типы, мьютексы и отображения железа; инициализация константой; эффект Global |
| Указатели | Только внутри unsafe в профиле core; для внешних функций — inout, срезы и ffi.Handle |
| Каналы | Отправка логически копирует значение, как присваивание; без семантики перемещения |
| Запись из GPU-ядра | gpu.Out[T] с записью только в ячейку своего потока; входы только для чтения; предусловия — на gpu.Dispatch; атомарные и shared — позже |
| inout в go | Исключительное заимствование до конца функции-родителя; непересекающиеся части среза — с доказательством решателя; в Detach запрещено |
| Разделение между задачами | chan, Mutex, RWMutex, atomic — разделяемые дескрипторы; всё остальное — значения; объект в кадре создателя, если не уходит в Detach |
| Именованные аргументы | Нет, как в Go; параметры передаются структурой |
| Код под архитектуру | Генерируемый пакет команд на архитектуру и суффикс в имени файла; цель задаётся флагом -target, директив target и arch в коде нет |
| Требования | Текст в строчном файле REQUIREMENTS, проверки — обычные тесты; без отдельного синтаксиса |
| Эмуляторы | Встроенные интерпретаторы из описаний архитектур; внешние эмуляторы и симуляторы — опция |
| Горячая перезагрузка | Везде в отладке; на iOS-устройстве через встроенный интерпретатор; выпускные сборки без неё |
| Задачи и потоки | Только задачи (go) на всех целях; потоки ОС скрыты планировщиком; task.LockThread() для редких случаев |
| Приоритеты задач | Уровни Low, Normal, High (+ Critical в core) через task.Go; защита от инверсии и голодания |
| Отсутствие значения | Как в Go: результат функции — пара «значение, ok»; в полях — Option[T] с методом Get() (T, bool); без сужения типа |
| Нулевые значения | Как в Go; у Option — None, у enum — первый вариант, если он без данных, иначе нулевого значения нет |
| Аргументы `...any` | Кортеж, известный при компиляции; обход через for const и meta; экземпляр на набор типов; значений any во время выполнения нет |
| nil | Литерал пустого значения интерфейсов, срезов, словарей и каналов; вызов метода у интерфейса требует доказанной непустоты; идиома ошибок Go без изменений |
| Литералы и особые типы | Без префиксов литералов и числовых параметров типов: encoding.CP866(...), fixed.Q16, simd.F32x4, wrap.U32 |
| Профили | Три: core (без ОС), app (под ОС), ui (интерфейсы); тонкие ограничения — эффектами в kern.mod |
| Отображение железа | Один раз через unsafe.Map, дальше обычное безопасное значение; регистры — из SVD без unsafe в коде пользователя |
| Владение периферией | Без device.Take() и перемещения; экземпляр периферии — эффект, контексты вычисляются по всей программе; общий доступ — критическая секция с потолком приоритета; до interrupts.Enable() — фаза инициализации |
| Свои эффекты и ограничения | effect.Declare и effect.Mark; ограничение функции — строка ensures (effect.Without, secret.ConstantTime, wcet.Within); особое имя в ensures только result |
| Методы встроенных типов | Нет, как в Go; bits.WrappingAdd, bits.CheckedAdd, conv.Narrow — обычные функции-дженерики |
| Циклическая арифметика | Типы пакета wrap (wrap.U8…wrap.I64) с переносящими операторами, как simd и fixed; смешивание с обычными целыми только явно |
| Рантайм и стеки задач | Рантайм на Kern, компонуется по частям; стек задачи вычисляется статически, иначе резерв с защитной страницей в app; в core неограниченная рекурсия запрещена |

### План

План покрывает весь объём среды. Он разбит на мелкие шаги, каждый из которых можно сделать и проверить отдельно. Компилятор пишется на Go; после шага самосборки (фаза 9) он живёт на Kern.

**Правила работы по плану:**

1. **Шаг — единица работы и проверки.** У каждого шага есть автоматический критерий готовности; следующий шаг, зависящий от него, не начинается, пока критерий не выполнен.
2. **Каждый шаг пополняет постоянный набор тестов**: набор соответствия, эталонные программы, фаззинг (раздел 25). Регрессия любого прежнего теста блокирует слияние.
3. **Где есть независимая реализация — она оракул.** Go для общего подмножества, интерпретатор IR для бэкендов, QEMU и наборы тестов процессоров для интерпретаторов архитектур, официальный набор тестов WebAssembly. Внешние инструменты используются только в тестах самой среды и в поставку не входят.
4. **Каждое «доказано» решателя подтверждается сертификатом**, который проверяет небольшой независимый проверщик.
5. Пока встроенные интерпретаторы не готовы, на первых шагах допустимы DOSBox и QEMU.
